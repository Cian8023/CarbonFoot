# 第一部分：从零到一 · App 怎么启动

## 第 0 步：点图标之后发生了什么

```
你点了「碳足迹」图标
        ↓
系统创建进程，拉起 EntryAbility
        ↓
EntryAbility.onCreate()   ← 第一个执行的方法
        ↓
AppInit.bootstrap(context)  只做三件事：
  ① 记住 context（后面读资源、开数据库都要用）
  ② AppStorage 写入 mainTab=0（默认首页）
  ③ AppStorage 写入 tick=0（刷新信号）
        ↓
EntryAbility.onWindowStageCreate()
        ↓
windowStage.loadContent('pages/Index')   ← 加载首页
        ↓
Index 页面开始构建 → 你看到界面
```

**大白话**：

> `EntryAbility` 是「开门的人」。它不干活，只把门打开、把钥匙交给 `AppInit`。
>
> **为什么 `onCreate` 里不直接初始化数据库？** 因为初始化是异步的、要几百毫秒。放在这里会拖慢启动，用户会看到白屏。所以只「记下环境」，真正的加载交给页面去 `await`。

## 第 1 步：四个初始化，只做一次

`AppInit.ensure()`（`common/AppInit.ets:28`）被第一个页面调用时，执行四步：

```typescript
AppInit.initPromise = (async () => {
  await DBHelper.init(ctx);          // ① 建表、建索引、补列
  await SeedService.seed(ctx);       // ② 灌入 12 任务 + 9 徽章
  await CalculationService.init(ctx);// ③ 加载 factors.json（19 个因子）
  await KnowledgeService.init(ctx);  // ④ 加载 knowledge.json（16 篇文章）
})();
```

**四步分别干什么**：

| 步 | 做什么 | 大白话 |
|---|---|---|
| ① | `CREATE TABLE` 5 张表 + 2 索引 | 把账本准备好，分好类 |
| ② | 把任务和徽章的「定义」写进库 | 把 12 条任务规则、9 枚徽章的判定条件抄进账本首页 |
| ③ | 读 `factors.json` 到内存 | 把「骑行 180 g/km」这张换算表背下来 |
| ④ | 读 `knowledge.json` 到内存 | 把 16 篇文章装进内存 |

**关键：`initPromise` 缓存**

```typescript
if (AppInit.initPromise === null) {
  AppInit.initPromise = (async () => {...})();
}
return AppInit.initPromise;   // 后续调用直接拿这个 Promise
```

**为什么需要**：5 个 Tab 会同时 `aboutToAppear`。没有缓存 → 同时发起 5 次建表 → 数据库锁冲突。有缓存 → 第 2~5 次直接等第一次完成。

**这叫「幂等初始化」**：调用一次和调用一百次，结果一样。

## 第 2 步：数据库建表（含一个隐形坑）

`DBHelper.init()`（`db/DBHelper.ets:63`）执行 6 条 DDL：

```sql
CREATE TABLE IF NOT EXISTS t_behavior_record (...)      -- 行为记录
CREATE TABLE IF NOT EXISTS t_points_record (...)        -- 积分流水
CREATE TABLE IF NOT EXISTS t_task (...)                 -- 任务定义
CREATE TABLE IF NOT EXISTS t_task_completion (...)      -- 任务完成记录
CREATE TABLE IF NOT EXISTS t_badge (...)                -- 徽章
CREATE INDEX IF NOT EXISTS idx_behavior_time ON ...     -- 时间索引
CREATE INDEX IF NOT EXISTS idx_points_time ON ...       -- 时间索引
```

**然后是一段容易被忽略的代码**（第 79-80 行）：

```typescript
DBHelper.sourceReady = await DBHelper.ensureColumn(DBHelper.store,
  't_behavior_record', 'source', "TEXT DEFAULT 'manual'");
```

**为什么需要**：`CREATE TABLE IF NOT EXISTS` 只判断「表存不存在」，**不判断「列全不全」**。

```
老用户手机上的表已存在 → 整条 CREATE 语句被跳过
→ 新加的 source 列永远不会创建
→ 查询时报 no such column: source
→ 整个 App 崩
```

**`ensureColumn` 的解法**：

```
① PRAGMA table_info(t_behavior_record)  问数据库：你有哪些列？
② 遍历列名，找有没有 source
③ 没有 → ALTER TABLE ADD COLUMN source TEXT DEFAULT 'manual'
④ 有 → 跳过
```

**大白话**：

> 你有一本手写的账本，第一版 9 栏。第二版设计了 10 栏的新表格。
>
> 如果直接给老用户发新模板，**没人会把旧账本重新抄一遍**——旧本子还是 9 栏。
>
> 正确做法：**先翻一下旧本子，看有没有「来源」这一栏。没有，就手动加一栏。**

## 第 3 步：灌种子数据

`SeedService.seed()` 把 `tasks.json` 和 `badges.json` 里的定义写进数据库。

**关键：用 `insertIfAbsent`（不存在才插入）**

```typescript
await TaskRepo.insertIfAbsent(code, title, description, ...);
```

**为什么不是直接 INSERT**：每次启动都会跑 seed。如果用 INSERT，启动 10 次就有 120 条任务。

**`insertIfAbsent` 内部先 SELECT 判断，不存在才 INSERT。** 这叫幂等。

# 第二部分：从零到一 · 录一条行为

## 完整九步

```
① 你在录入页选「出行 → 骑行」，输入 6，点提交
        ↓
② Record.ets 收集参数（7 个）
        ↓
③ BehaviorService.submit()  唯一入口
        ↓
④ 三重校验：类型存在？数值有限正数？不超上限？
        ↓
⑤ 算减排：round(6 × 180) = 1080 克
        ↓
⑥ 算积分：max(1, floor(1080/100)) = 10 分
        ↓
   ┏━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┓
⑦ ┃ beginTx() 开事务              ┃
   ┃ 写 t_behavior_record          ┃
   ┃ 写 t_points_record            ┃
   ┃ commitTx() 提交                ┃
   ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┛
        ↓
⑧ 事务外：判 12 个任务 → 检 9 枚徽章
        ↓
⑨ bumpTick() 广播 + scheduleReport() 异步报家庭组
```

## 第 ③ 步：为什么页面不直接写数据库

`pages/Record.ets:164`：

```typescript
const result = await BehaviorService.submit(this.selType, this.selSub,
  this.parseValue(), sub.unit, sub.factor, ts, this.noteText);
```

**页面只做三件事**：

| 做什么 | 为什么在页面 |
|---|---|
| 检查时间不能超过现在 | 这是 UI 交互，要弹 Toast |
| 取出选中的子类型 | 页面自己的状态 |
| 把 7 个参数打包传下去 | **页面只管收集，不管计算** |

**页面没有算减排量、没有算积分、没有碰数据库。**

## 第 ④ 步：三重校验为什么在 Service 层

```typescript
const sub = CalculationService.findSub(type, subType);
if (sub === null) throw new Error('未知的行为类型');           // ①
if (!isFinite(value) || value <= 0) throw new Error('数值必须大于 0');  // ②
if (value > sub.max) throw new Error(`超出单次上限：最多 ${sub.max} ${sub.unit}`);  // ③
```

**因为 `submit()` 有三个调用方**：

```
手动录入（Record.ets）
AI 识别（AiRecognize.ets）
平台导入（SettingsDetail.ets）
```

**校验写在页面里要写 3 遍，还可能漏。放在 Service，三条路都绕不过。**

**三道各挡什么**：

| 校验 | 挡什么 | 举例 |
|---|---|---|
| ① 类型存在 | 因子库没这个类型 | AI 识别出「滑板车」 |
| ② 有限正数 | `NaN` / `Infinity` / 0 / 负数 | `parseFloat('abc')` = NaN |
| ③ 不超上限 | 手误多打几个 0 | 骑行填 60000 km |

## 第 ⑤⑥ 步：两个公式

**减排量**（`BehaviorService.ets:28`）：

```typescript
const grams = Math.round(value * factor);   // round(6 × 180) = 1080
```

**为什么 `round` 不是 `floor`**：`floor` 会让每条记录都少算一点，误差累积。

**积分**（`CalculationService.ets:71`）：

```typescript
Math.max(1, Math.floor(grams / 100))   // max(1, floor(1080/100)) = 10
```

**为什么 `Math.max(1, ...)` 兜底**：光盘一餐 50~100 克，`floor(50/100) = 0`。用户认真记录却 0 分，会挫败。**保底 1 分是产品决策，不是技术必需。**

## 第 ⑦ 步：事务（最核心）

```typescript
DBHelper.beginTx();
try {
  const id = BehaviorRepo.insertSync(record);      // 写行为表
  if (points > 0) {
    await PointsService.addPointsTx('behavior', id, ..., points);  // 写积分表
  }
  DBHelper.commitTx();
} catch (e) {
  DBHelper.rollbackTx();
  throw e as Error;
}
```

**为什么两笔写必须一个事务**：

```
如果分开写：
  写行为表成功 ✓
  写积分表失败 ✗
  → 历史页有记录，但积分没加
  → 用户看到「减了 1.08 kg 但没得分」
  → 这个烂账无法自愈
```

**大白话**：

> 你去银行转 100 元给朋友。
>
> **正确**：扣你的 100 和加他的 100 是**同一个操作**，要么都成，要么都不成。
>
> **错误**：先扣你的，再加他的。加失败了呢？你的钱消失了。

**`addPointsTx` 的 `Tx` 是什么意思**：

```
Tx = "expects Transaction"  请在事务里调用我
```

**不是「我自带事务」**，而是「我需要一个事务包着」。所以 `addPoints`（自带事务）内部调用的就是 `addPointsTx`：

```typescript
static async addPoints(...) {
  DBHelper.beginTx();                          // 开
  try {
    await PointsService.addPointsTx(...);      // 调那个"不带事务的"
    DBHelper.commitTx();                       // 提交
  } catch (e) {
    DBHelper.rollbackTx();                     // 回滚
    throw e as Error;
  }
}
```

**判断规则只有一条**：**当前是否已经在别人的事务里。在，调 `addPointsTx`；不在，调 `addPoints`。**

## 第 ⑧ 步：事务外的三段

```typescript
const newBadges: string[] = [];
try {
  await TaskService.evaluateAll();              // 判 12 个任务
  const badges = await BadgeService.checkAll(); // 检 9 枚徽章
  for (const b of badges) newBadges.push(b);
} finally {
  bumpTick();                                   // 广播刷新
}
```

**三个设计要点**：

**① 顺序不能颠倒**
「任务达人」徽章判定条件是 `tasks_done >= 10`，依赖 `t_task_completion` 表。**任务先判定，徽章才可能解锁。**

**② 必须在事务外**
`evaluateAll()` 内部自己 `beginTx`。放进来就是嵌套事务，鸿蒙 RDB 不支持。

**③ `finally` 保证 `bumpTick` 一定执行**
这是修过的真实缺陷（DF-50）：

```
事务已提交 → 数据确定落库
如果 evaluateAll 抛异常 → bumpTick 被跳过
→ 数据改了但界面不刷新
→ 用户以为保存失败，再点一次 → 重复记录
```

## 第 ⑨ 步：广播 + 异步上报

```typescript
} finally {
  bumpTick();                        // 广播：数据变了
}
SyncService.scheduleReport();        // 异步：报家庭组（不 await）
```

**`bumpTick` 的实现**（`Constants.ets:48`）：

```typescript
let tickCounter: number = 0;
export function bumpTick(): void {
  tickCounter += 1;
  AppStorage.setOrCreate(Constants.KEY_TICK, tickCounter);
}
```

**7 个页面同时监听这个值**：

| 页面 | 行 | 回调 |
|---|---|---|
| Index（首页） | 87 | `refresh()` |
| Record（录入） | 15 | `onDataTick()` |
| History（历史） | 25 | `refresh()` |
| Tasks（任务） | 21 | `refresh()` |
| Settings（我的） | 16 | `refresh()` |
| Badges（徽章） | 20 | `refresh()` |
| Knowledge（科普） | 13 | `refresh()` |

**写法都一样**：

```typescript
@StorageLink('tick') @Watch('refresh') tick: number = 0;
```

**翻译**：「`tick` 和全局绑定。全局变了我就变，我一变就调 `refresh()`。」

**为什么不用 `Date.now()`**：同一毫秒两次调用值相同，`@StorageLink` 认为没变，`@Watch` 不触发。**改成递增计数（DF-49）。**

**`scheduleReport()` 为什么不 await**：同步是「锦上添花」，失败不该影响本地录入。**这是降级设计。**

# 第三部分：从零到一 · 数据怎么读出来

## 首页 refresh 的六步

`pages/Index.ets:161`：

```
① await AppInit.ensure()  等初始化
        ↓
② BehaviorRepo.all()  一次查全部记录
        ↓
③ Promise.all()  9 个查询并行发起
        ↓
④ 内存里算：今日 / 本月 / 趋势 / 饼图 / 周报
        ↓
⑤ 赋值给 @State → ArkUI 自动重绘
        ↓
⑥ CardSnapshot.save()  存桌面卡片快照
```

## 关键 1：只查一次全表

```typescript
const records = await BehaviorRepo.all();
```

**不是「只查今天」。** 为什么：

趋势图要 5 年、月目标要本月、周报要本周和上周、饼图要当前档位。**一次全查，内存里算，比拼多次 SQL 快。**

**数据量**：一天 5 条，一年 1800 条。内存遍历毫秒级。

## 关键 2：9 个查询并行

```typescript
const pBalance = PointsService.getBalance();
const pPending = TaskService.pendingCount();
const pStreak = BadgeService.currentStreak();
// ... 共 9 个
await Promise.all([pBalance, pPending, pStreak, ...]);
```

**代码注释原文**：

```
各页数据互不依赖，并行取齐再逐一赋值，避免十几次串行 await
把首帧拖住（切 Tab / 路由转场时尤其明显）
```

| 写法 | 耗时 |
|---|---|
| 串行 9 次 | 9 × 10ms = **90ms** |
| 并行 | max(10ms) ≈ **10ms** |

**差 9 倍，用户能感知。**

## 关键 3：算今日要加 `<= now` 上界

```typescript
if (r.createdAt >= todayStart && r.createdAt <= now) {
  todaySum += r.reductionG;
}
```

**为什么要 `<= now`**：防未来时间的脏数据。代码注释说这是「与历史页修改入口的校验互为兜底」，**双保险**。

## 关键 4：统计是纯函数

```typescript
this.trend = StatsService.trend(records, this.trendKind);
this.pie = StatsService.categoryShare(records, StatsService.rangeStart(this.trendKind));
this.monthG = StatsService.monthSum(records);
this.weekly = StatsService.weekReport(records);
```

**全部是「传入 records，返回结果」的纯函数**。不查库、不写库、无副作用。

**好处**：好测试（给一组数据验证输出）、好复用（首页和历史页都能用）。

## 关键 5：赋值触发重绘

```typescript
this.todayG = todaySum;    // @State 变量
this.balance = balance;
```

**ArkUI 的响应式**：`@State` 一赋值，用到它的 UI 部分自动重绘。**不需要手动调「刷新界面」。**

# 第四部分：核心 · 双模拟器家庭组多端同步

**这是 E1 创新点，也是答辩最可能深挖的地方。**

## 4.1 先搞清楚要解决什么问题

### 问题：两台模拟器互不相通

```
模拟器 A                      模拟器 B
独立虚拟机                    独立虚拟机
自己的数据库                  自己的数据库
自己的 App 沙箱                自己的 App 沙箱
```

**它们是完全隔离的两个环境。** A 录了 6 公里骑行，B 完全不知道。

### 目标：让 A 和 B 的数据合并

```
A：我减了 15.00 kg
B：我减了 4.78 kg
            ↓
    家庭合计 19.78 kg
```

## 4.2 为什么不用鸿蒙的分布式软总线（必答）

**先明确答案：这个项目完全没用软总线，用的是应用层 HTTP。**

我查过代码，`distributedDataObject`、`distributedKVStore`、`deviceManager` 一个都没用。

**三个硬障碍**：

| 障碍 | 具体是什么 |
|---|---|
| **NAT 隔离** | 模拟器跑在 QEMU 虚拟机里，网络是 NAT 模式。软总线的设备发现依赖**多播/广播包**，而 NAT 会把这些包隔离掉，出不去 |
| **双实例互相看不见** | 同一台电脑开两个模拟器，各自独立 NAT，**互相发现不了对方** |
| **同账号互信做不全** | 软总线要求两台设备登录同一个华为账号并建立互信，模拟器里这个流程走不完 |

**代码里本来就写了这段注释**（`SyncService.ets:52-53`）：

```typescript
/**
 * 注：分布式软总线（distributedDataObject）在模拟器上受 NAT 隔离与同账号互信限制不可用，
 * 故采用应用层同步。
 */
```

**大白话**：

> 软总线相当于「两个人碰一碰手机直接传」。
>
> 但模拟器是「两个关在不同房间里的人」，**房间之间没有门**（NAT 隔离），喊话也听不到（多播被拦）。
>
> 所以换个办法：**两个人都给同一个中间人打电话**（宿主机上的服务），由中间人转达。

## 4.3 方案：应用层 HTTP 中转

### 整体架构

```
┌──────────────────────┐         ┌──────────────────────┐
│  模拟器 A            │         │  模拟器 B            │
│  App 沙箱独立         │         │  App 沙箱独立         │
│  数据库独立           │         │  数据库独立           │
│                      │         │                      │
│  SyncService         │         │  SyncService         │
│  deviceId: dev-aaa   │         │  deviceId: dev-bbb   │
└──────────┬───────────┘         └──────────┬───────────┘
           │                                │
           │ 都访问 10.0.2.2:8081           │
           │ （QEMU 的宿主机固定别名）        │
           ↓                                ↓
      ┌────────────────────────────────────────┐
      │  宿主机（你的电脑）                     │
      │  node sync/server.js 8081              │
      │  数据落盘：sync/data.json               │
      └────────────────────────────────────────┘
```

### 关键：`10.0.2.2` 是什么

| 地址 | 谁访问它 | 它指向谁 |
|---|---|---|
| `127.0.0.1` | 电脑上的浏览器 | **电脑自己** |
| `127.0.0.1` | **模拟器里的 App** | **模拟器自己**（不是电脑！） |
| `10.0.2.2` | **模拟器里的 App** | **宿主机（你的电脑）** |

**`10.0.2.2` 是 QEMU 模拟器硬编码的一个特殊地址**，专门用来让模拟器访问宿主机。

**这是模拟器厂商定的规则，不是你的 IP。** 所以换任何电脑都能用。

### 三个候选地址依次尝试

```typescript
private static readonly EMULATOR_HOST = 'http://10.0.2.2:8081';
private static readonly LOOPBACK_HOST = 'http://127.0.0.1:8081';

const raw = [configured.trim(), EMULATOR_HOST, LOOPBACK_HOST];
```

| 顺序 | 地址 | 什么时候用 |
|---|---|---|
| ① | 用户配置的地址 | 真机连 Wi-Fi 时手填电脑 IP |
| ② | `10.0.2.2:8081` | **模拟器默认走这个** |

## 4.4 服务端做了什么

`sync/server.js` 只有 186 行，5 个接口。

### 数据结构：一个嵌套的对象

```javascript
db = {
  "CF952298": {                    // 邀请码 = 组的 key
    createdAt: 1762...,
    members: {
      "dev-aaa": {                 // 设备号 = 成员的 key
        deviceId: "dev-aaa",
        name: "我的设备",
        totalG: 15000,
        balance: 172,
        weekG: 3200,
        updatedAt: 1762...
      },
      "dev-bbb": {
        deviceId: "dev-bbb",
        name: "妈妈",
        totalG: 4780,
        balance: 95,
        weekG: 1200,
        updatedAt: 1762...
      }
    }
  }
}
```

### 五个接口

| 接口 | 方法 | 干什么 | 关键逻辑 |
|---|---|---|---|
| `/api/family/create` | POST | 建组 | 邀请码已存在 → 返回 409 |
| `/api/family/join` | POST | 加入 | 组不存在 → 返回 404 |
| `/api/family/report` | POST | **上报快照** | `members[deviceId] = snapshot`（**覆盖写**） |
| `/api/family/members?code=` | GET | 拉成员 | 返回该组所有成员 |
| `/api/family/leave` | POST | 退出 | 组空了自动解散 |

### 最关键的一行：覆盖写

```javascript
db[code].members[b.deviceId] = snapshotOf(b);
//                  ↑ 用 deviceId 做 key，直接赋值 = 覆盖
```

**为什么是「覆盖」不是「追加」**：

```
如果追加：
  A 第一次上报 → 列表有 1 个我
  A 第二次上报 → 列表有 2 个我
  A 上报 100 次 → 100 个我  ← 崩了

用覆盖：
  A 上报 1 次 → members["dev-aaa"] = {...}
  A 上报 100 次 → members["dev-aaa"] = {...}  ← 还是 1 条
```

**这是「幂等写入」**：同一个设备报告多少次，都只有一个槽位。

### `snapshotOf()` 的防线

```javascript
function snapshotOf(b) {
  return {
    deviceId: String(b.deviceId || ''),
    name: String(b.name || '成员'),
    totalG: Number(b.totalG) || 0,     // ← 转数字，坏值变 0
    balance: Number(b.balance) || 0,
    weekG: Number(b.weekG) || 0,
    updatedAt: Date.now()              // ← 服务器时间，不是客户端传的
  };
}
```

**两道防线**：

| 防线 | 挡什么 |
|---|---|
| `Number(x) \|\| 0` | 客户端传了字符串 `"abc"` → 变成 0，不会污染统计 |
| `updatedAt: Date.now()` | **用服务器时间**，不用客户端时间。客户端时钟不准也不会错 |

### 落盘：`persist()`

```javascript
function persist() {
  try {
    fs.writeFileSync(DATA_FILE, JSON.stringify(db, null, 2), 'utf8');
  } catch (e) {
    console.error('[warn] 落盘失败：', e.message);
  }
}
```

**每次写操作后立即落盘**。为什么：

```
如果只在内存：重启服务 → 所有组消失
立即落盘：重启服务 → 从 data.json 恢复

启动时读取（server.js:18-25）：
  db = JSON.parse(fs.readFileSync(DATA_FILE, 'utf8'));
  catch (e) { db = {}; }   ← 文件不存在或损坏，当空库，不崩
```

```
        ↓
```

```
⑦ persist()
⑧ 终端打印：[22:33:20] 上报 CF952298 我的设备 totalG=16080
```

**关键：为什么不用 `setTimeout` 防抖**

代码注释里写得很清楚（`SyncService.ets:314-319`）：

```
注意：不能用 setTimeout 做延迟合并——应用切到后台后定时器会被冻结，
用户"录完就切到另一台设备"时上报会永远发不出去。这里改为立即上报，
用 reporting 标志把并发调用合并成"进行中 + 结束后补一次"。
```

**这是真实踩过的坑**：

```
早期版本：录入后 setTimeout(800ms) 再上报
问题场景：用户录完 → 立刻切到另一台手机
结果：App 进入后台 → 定时器被系统冻结 → 上报永远不执行
     → 另一台手机永远看不到这条数据
```

**现在的方案：立即上报 + `reporting` 标志合并**

```typescript
static scheduleReport(): void {
  if (SyncService.reporting) {
    SyncService.pendingReport = true;    // 正在报 → 标记「报完再补一次」
    return;
  }
  SyncService.runReport();               // 没在报 → 立刻发起
}

private static async runReport(): Promise<void> {
  SyncService.reporting = true;
  try {
    await SyncService.reportSnapshot();
  } catch (e) {
    // 静默失败：家庭页仍可手动「立即同步」
  } finally {
    SyncService.reporting = false;
    if (SyncService.pendingReport) {
      SyncService.pendingReport = false;
      SyncService.scheduleReport();      // 结束后补一次
    }
  }
}
```

**这个模式叫「进行中 + 待补标记」**：

```
用户快速录 3 条：
  第 1 条 → 立即上报（reporting = true）
  第 2 条 → reporting 为 true → pendingReport = true，直接返回
  第 3 条 → 同上，pendingReport 已经是 true
  第 1 条报完 → reporting = false → 发现 pendingReport → 再报一次
  → 总共只发 2 次请求，而不是 3 次
```

## 4.6 一个必须讲清楚的点：去重

`mergedStats()` 的核心（`SyncService.ets:370-405`）：

```typescript
const myId = await SyncService.deviceId();
const cached = await SyncService.listMembers();
const myG = await BehaviorRepo.sumAllReduction();   // ← 本机数据实时算
const myBalance = await PointsService.getBalance();

const mine: FamilyMember = { deviceId: myId, totalG: myG, local: true };
const all: FamilyMember[] = [mine];

for (const m of cached) {
  if (m.deviceId === myId) {
    continue;      // ← 跳过自己
  }
  all.push(m);
}
```

**为什么要跳过自己**：

**服务端返回的列表包含你自己。** 如果不去重：

```
我(16.08) + 我(16.08) + 妈妈(4.78) = 36.94 kg   ← 错了，多算了一倍自己
正确：16.08 + 4.78 = 20.86 kg
```

**注意 `myG` 是实时从数据库算的，不是从缓存读的。** 为什么：

```
缓存可能过期（上次同步时的数据）
本机数据永远是最新的 → 直接查库
```

**代码注释也说明了**：

```typescript
// 本机积分取真实余额：含任务/阅读奖励与兑换扣减，不能再用减排量反推
const myBalance = await PointsService.getBalance();
```

**为什么不能「用减排量反推积分」**：因为积分还有任务奖励、阅读奖励、兑换扣减。**减排量只对应「行为积分」这一部分。**

## 4.7 离线降级

**同步服务没启动会怎样**：

```typescript
static async pullMembers(): Promise<boolean> {
  const resp = await SyncService.callGet(...);
  if (resp === null || resp.code !== 200) {
    SyncService.online = false;      // ← 标记离线
    return false;
  }
  ...
}
```

**界面表现**：

| 状态 | 显示 |
|---|---|
| 在线 | 「已同步 · 3 分钟前」 |
| 离线 | 「离线 · 显示本地缓存」 |

**缓存从哪来**：上次成功 `pullMembers()` 时存进 preferences 的 `KEY_MEMBERS`。

```typescript
// 每次成功拉取都会缓存
await store.put(SyncService.KEY_MEMBERS, JSON.stringify(list));
```

**所以离线时仍能看到成员列表，只是数据是上次同步的。**

**这是降级设计**：同步失败不影响主功能（记账），只是看不到最新数据。

## 4.8 为什么设备号不会撞（关键前提）

`deviceId()`（`SyncService.ets:73`）：

```typescript
let id = await store.get(SyncService.KEY_DEVICE, '') as string;
if (id === '') {
  id = 'dev-' + Date.now().toString(36) + '-' + Math.floor(Math.random() * 1000000).toString(36);
  await store.put(SyncService.KEY_DEVICE, id);

```

**两个保证**：

| 保证 | 说明 |
|---|---|
| 存在**各自的 preferences** | 两台模拟器 App 沙箱独立，各存各的 |
| 生成用**时间戳 + 随机数** | 即使同一毫秒，随机数也不同 |

**生成的 ID 长这样**：

```

     ↑时间戳  ↑随机数
```

**⚠️ 但有一个坑：不要用「克隆模拟器」**

DevEco Studio 有「克隆/复制模拟器」功能。如果克隆时把 App 数据一起复制了，`deviceId` 会完全相同。结果：

```

模拟器 B 上报 → members["dev-same"] = { totalG: 4780 }   ← 覆盖了 A
```

**正确做法**：两台模拟器各自全新安装 App，不要克隆已装过 App 的镜像。

# 第五部分：答辩问答

## Q1：整体架构怎么分层的？

> 四层：**页面层**（`pages/`，只管收集参数和显示）、**服务层**（`service/`，校验、计算、业务逻辑）、**数据层**（`db/`，唯一写 SQL 的地方）、**存储**（.db 文件 + Preferences + AppStorage）。
>
> 关键约束：**`pages/` 下 14 个文件没有一个 import `DBHelper` 或 `Repository`。** 页面不碰数据库。

## Q2：录一条记录，数据怎么走？

> 九步。页面收集 7 个参数 → `BehaviorService.submit()` 三重校验 → 算减排（`round(value × factor)`）→ 算积分（`max(1, floor(g/100))`）→ **事务内写两张表** → 提交 → 事务外判任务 → 检徽章 → `bumpTick()` 广播。
>
> 第 5 步的事务是核心：行为和积分是绑定账，要么都成，要么都败。

## Q3：为什么要开事务？

> 行为和积分是一对绑定账。不开事务，可能「写行为成功、写积分失败」，用户看到「减了 1.08 kg 但没得分」，这个烂账无法自愈。
>
> 这跟银行转账一个道理：扣你和加对方必须一起成。

## Q4：`addPointsTx` 的 `Tx` 是什么意思？

> `Tx = expects Transaction`，**表示「请在事务里调用我」，不是「我自带事务」**。
>
> `addPoints`（自带事务）内部调用的就是 `addPointsTx`。判断规则只有一条：当前是否已经在别人的事务里。

## Q5：多端同步为什么不用鸿蒙分布式软总线？

> 三个硬障碍。**一是 NAT 隔离**：模拟器在 QEMU 里，软总线的设备发现依赖多播广播，NAT 会拦掉。**二是双实例互相看不见**：同一台电脑两个模拟器各自独立 NAT。**三是同账号互信在模拟器里做不全。**
>
> 所以用应用层 HTTP 中转。**这是环境约束下的工程选择，不是能力不足。**

## Q6：双模拟器证明了什么？不能证明什么？

> **能证明**：跨设备数据合并这个业务能力跑通了。两台设备的数据真的在互相流动，服务端的 `data.json` 里有两条独立的成员记录。
>
> **不能证明**：鸿蒙的分布式能力。这需要真机。我在文档和 PPT 里写的都是「应用层多端同步」，没有说「分布式」。

## Q7：两台模拟器怎么找到服务？IP 是写死的吗？

> **没有写死任何 IP。** 三个候选地址：用户配置的、`10.0.2.2:8081`、`127.0.0.1:8081`。
>
> `10.0.2.2` 是 **QEMU 模拟器硬编码的宿主机别名**，不是具体 IP。模拟器里访问它，就是访问你的电脑。`127.0.0.1` 在模拟器里指的是模拟器自己，所以用不了。
>
> **因为 `10.0.2.2` 是相对地址，换任何电脑都能用，不需要改代码。**

## Q8：为什么设备号不会撞？

> 两个保证：**存各自的 preferences**（App 沙箱独立）、**生成用时间戳 + 随机数**。
>
> 但要注意：不能用「克隆模拟器」并保留 App 数据，那样设备号会完全相同，服务端会把两份数据当成一个人互相覆盖。

## Q9：上传的是原始记录吗？

> **不是。只传 4 个汇总数字**：`totalG`（累计减排克数）、`balance`（积分余额）、`weekG`（本周减排）、`updatedAt`。
>
> **为什么传快照不传原始记录**：
> 1. 隐私最小化 —— 对方看不到你录了什么行为、什么时间录的
> 2. 传输量小 —— 一次几百字节，不是几 MB
> 3. 统计口径单点 —— 本机自己算好再传，避免两端算法不一致

## Q10：为什么用 `deviceId` 做 key 覆盖写？

> 因为要**幂等**。同一设备上报 100 次，如果每次追加，成员列表会有 100 个我。
>
> 用 `deviceId` 做 key 直接赋值，覆盖旧值，只有一条。

## Q11：为什么不用 `setTimeout` 防抖上报？

> 因为**应用切到后台后定时器会被系统冻结**。用户「录完立刻切到另一台手机」时，上报永远发不出去。
>
> 改成「立即上报 + `reporting` 标志合并并发」：正在报时标记待补，报完再补一次。用户快速录 3 条，只发 2 次请求。

## Q12：服务端有没有鉴权？这是不是一个缺陷？

> **没有鉴权，这是真实的不足。** `/api/family/members?code=xxx` 只校验邀请码存在，不校验请求者身份。知道邀请码就能读这一组的数据。
>
> 而且数据是**明文 JSON**，打开 `data.json` 就能看到所有人的减排量。
>
> **这是有意的取舍**，因为定位是局域网内家庭场景，信任边界是「同一个家庭」。真要上公网，需要补三样：token 鉴权、HTTPS、落盘加密。**这三项都在传输和存储层，`SyncService` 的接口不用改。**

## Q13：离线了怎么办？

> 降级。`pullMembers()` 失败时标记 `online = false`，界面显示「离线 · 显示本地缓存」。
>
> 缓存是上次成功拉取时存进 preferences 的成员列表。**所以离线仍能看到成员，只是数据是上次同步的。**
>
> 同步失败不影响记账这个主功能。

## Q14：`mergedStats` 为什么要跳过自己？

> 服务端返回的列表**包含你自己**。不去重的话，`我 + 我 + 妈妈 = 多算了一倍自己`。
>
> 代码里用 `if (m.deviceId === myId) continue;` 跳过。
>
> 另外本机的 `totalG` 是**实时从数据库算**的，不是从缓存读——本机数据永远最新。

## Q15：这个同步方案有什么局限？

> 三个。
>
> **一是没有鉴权、没有加密**，只适合局域网家庭场景。
>
> **二是 `joinGroup()` 后没有立即 `reportSnapshot()`**，新成员刚加入时别人看到的是 0 kg，要等录入或手动同步才更新。**这行代码应该补在 `joinGroup()` 末尾。**
>
> **三是只同步汇总数字，不能同步明细**。设计如此（隐私考虑），但如果要做「家庭共同账本」就需要传明细，那时要重新考虑数据量和冲突合并。

# 附：一句话总结

> **启动**：EntryAbility 开门 → AppInit 只初始化一次 → 建表、灌种子、读因子和文章。
>
> **写入**：页面收集 → Service 校验算数 → **一个事务写两张表** → 广播 + 异步上报。
>
> **读取**：一次全表 + 9 个并行查询 → 内存里算统计 → 赋值给 `@State` 自动重绘。
>
> **同步**：两台模拟器都访问宿主机 `10.0.2.2:8081` → 各自上报汇总快照 → 服务端按 `deviceId` 覆盖存 → 各自拉取并去重求和。
>
> **核心三条：事务保证两笔写原子、因子快照保证历史不可变、`deviceId` 保证幂等不重复。**
