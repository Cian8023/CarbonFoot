## 第一步：先搞懂「多端同步」到底要解决什么问题

### 场景

你和妈妈各自用一台手机，都装了这个 App。

```
你的手机                          妈妈的手机
┌──────────┐                    ┌──────────┐
│ 你今天    │                    │ 妈妈今天  │
│ 骑行 6km  │                    │ 骑行 4km  │
│ 减排 1.08kg│                   │ 减排 0.72kg│
└──────────┘                    └──────────┘

        问题：谁的手机都不知道对方的数据
```

**想要的效果**：两台手机都能看到「我家一共减排了多少」。

```
你的手机                          妈妈的手机
┌──────────┐                    ┌──────────┐
│ 家庭总减排 │                    │ 家庭总减排 │
│  1.80 kg  │  ←─── 一样 ───→   │  1.80 kg  │
│           │                    │           │
│ 我    1.08│                    │ 我    0.72│
│ 妈妈  0.72│                    │ 你    1.08│
└──────────┘                    └──────────┘
```

### 核心难点

两台手机是**完全独立的设备**，各自有各自的存储。它们之间没有任何天然的连接。

**所以必须有人帮它们「传话」。**

---

## 第二步：「传话人」是谁

有三种选择：

| 方案                  | 做法                  | 可行性                               |
| ------------------- | ------------------- | --------------------------------- |
| **A. 手机直接对话**       | 两台手机用蓝牙/WiFi 直连，自己传 | 鸿蒙的「分布式软总线」走这条路，但**模拟器做不到**（后面解释） |
| **B. 找第三方中转**       | 都发到微信/服务器，再从上面取     | 需要联网、需要账号，演示环境不方便                 |
| **C. 自己架一台「传话服务器」** | 在电脑上跑一个小程序，两台手机都连它  | ✅ **本项目用的方案**                     |

**我们选了 C。**

## 第三步：C 方案长什么样

```
        ┌─────────────────────────────────┐
        │   你的电脑（宿主机）             │
        │                                 │
        │   sync/server.js                │
        │   监听端口 8081                  │
        │                                 │
        │   就像一个「公共白板」：          │
        │   ┌───────────────────────────┐ │
        │   │ 家庭组 CF123456           │ │
        │   │ ├─ 设备A: 1.08kg, 108分   │ │
        │   │ └─ 设备B: 0.72kg, 72分    │ │
        │   └───────────────────────────┘ │
        └─────────────────────────────────┘
                 ↑                ↑
        ┌────────┘                └────────┐
        │  ① 上报我的数据                    │  ① 上报我的数据
        │  ③ 读走别人的数据                  │  ③ 读走别人的数据
        │                                  │
   ┌──────────┐                     ┌──────────┐
   │ 模拟器 A  │                     │ 模拟器 B  │
   │ （你）    │                     │ （妈妈）  │
   └──────────┘                     └──────────┘
```

**用大白话说**：

- 电脑上开了一块「公共白板」
- 你的手机在白板上写下「我减排了 1.08kg」
- 妈妈的手机在白板上写下「我减排了 0.72kg」
- 然后两台手机都抬头看白板，就知道全家是多少

**这就是「多端同步」的全部本质。**

## 第四步：为什么不用鸿蒙原生的「分布式软总线」

这是评委最可能问的，也是你最容易答错的。

### 软总线是什么

鸿蒙系统自带一个能力：两台华为设备靠近，就能「碰一碰」传文件、共享剪贴板。这叫**分布式软总线**。

**它是最「正统」的方案**，但本项目**没有用**。

### 为什么不能用

三个硬障碍，全部来自**模拟器环境的限制**：

**障碍 1：模拟器是虚拟机，网络被隔离**

```
你的电脑（真实网络）
   │
   ├── NAT 转换（像一层单向玻璃）
   │
   ├─→ 模拟器 A（虚拟机 1，内部 IP 10.0.2.15）
   │
   └─→ 模拟器 B（虚拟机 2，内部 IP 10.0.2.15）  ← 和 A 一样的 IP！
```

两个模拟器各自是一个虚拟机，IP 地址一样但互不相通。软总线靠「广播喊话」来找附近设备，**这些喊话包被 NAT 挡住了**。

**障碍 2：两个模拟器互相「看不见」**

软总线要工作，前提是两台设备能互相发现。但两个虚拟机各自独立，**谁也不知道对方存在**。

**障碍 3：软总线要求「同一个华为账号 + 互相信任」**

这个信任关系需要在真机上登录账号、扫码确认。**模拟器里做不全**。

### 结论

**软总线在模拟器上跑不起来。这不是我偷懒，是环境限制。**

代码里这段话就是证据（`SyncService.ets` 第 52 行）：

```typescript
/**
 * 注：分布式软总线（distributedDataObject）在模拟器上受 NAT 隔离与同账号互信限制不可用，
 * 故采用应用层同步。
 */
```

### 答辩怎么说

> 我**没有**用软总线，用的是应用层 HTTP 同步。原因是模拟器的 QEMU 网络做了 NAT 隔离，软总线的设备发现依赖多播广播，这些包出不去；同机两个模拟器各自独立 NAT，互相看不见；同账号互信在模拟器里也做不全。
>
> 所以我实现的&#x662F;**「多端数据合并」这个业务能力**，用 HTTP 中转代替软总线传输。**双模拟器证明的是业务逻辑跑通了，不能证明鸿蒙分布式能力**，那需要真机。

**主动说出「不能证明什么」，比含糊其辞可信得多。**

## 第五步：开始讲代码（从最简单的开始）

### 5.1 先认识四个「概念」

| 概念        | 是什么          | 在我们项目里                    |
| --------- | ------------ | ------------------------- |
| **设备 ID** | 每台手机的唯一身份证   | `dev-mw0gt4j0-9frv` 这种字符串 |
| **家庭组号**  | 一家的共同暗号      | `CF123456` 这种 6 位数字       |
| **快照**    | 某台设备当前的「成绩单」 | 减排多少、积分多少、本周多少            |
| **接口**    | 服务器提供的服务入口   | `/api/family/report` 这种路径 |

### 5.2 设备 ID 是怎么来的

**文件**：`SyncService.ets` 第 73-82 行

```typescript
static async deviceId(): Promise<string> {
  const store = await SyncService.getStore();
  let id = await store.get('device_id', '') as string;
  if (id === '') {
    // 第一次运行，生成一个
    id = 'dev-' + Date.now().toString(36) + '-' + Math.floor(Math.random() * 1000000).toString(36);
    await store.put('device_id', id);
    await store.flush();
  }
  return id;
}
```

**逐行翻译成人话**：

```
第 1 行：拿到手机的「记事本」（preferences 存储）
第 2 行：翻到「device_id」这一页，看看有没有记过号
第 3 行：如果空白（第一次运行）
第 5 行：  就用「当前时间 + 随机数」拼一个号出来
第 6-7 行：写进记事本，保存好
第 9 行：把号给你
```

**为什么必须存起来**：  
如果不存，每次打开 App 都生成新号，服务器会认为「每次都是新成员来了」，成员列表里会冒出无数个「我的设备」。

**`toString(36)` 是什么**：  
把数字转成 36 进制（0-9 + a-z），这样数字更短。

```
时间戳 1793696906081 → "mw0gt4j0"（9 个字符）
```

比写 13 个数字好看。

### 5.3 建组：生成一个家庭暗号

**文件**：`SyncService.ets` 第 152-176 行

```typescript
static async createGroup(): Promise<string> {
  const id = await SyncService.deviceId();      // ① 拿自己的设备号
  const name = await SyncService.getNickname();  // ② 拿自己的昵称

  for (let i = 0; i < 3; i++) {                  // ③ 最多试 3 次
    const code = 'CF' + Math.floor(100000 + Math.random() * 900000);  // ④ 生成 6 位随机号
    const body = JSON.stringify({ code: code, deviceId: id, name: name });
    const resp = await SyncService.callPost('/api/family/create', body);  // ⑤ 发给服务器

    if (resp === null) {
      throw new Error('同步服务不可达...');       // ⑥ 服务器没开
    }
    if (resp.code === 200) {                     // ⑦ 服务器说「建成功了」
      const g: FamilyGroup = { code: code, createdAt: Date.now() };
      await SyncService.saveGroup(g);            // ⑧ 自己也记下来
      await SyncService.reportSnapshot();        // ⑨ 顺便上报一次自己的数据
      await SyncService.pullMembers();           // ⑩ 拉一次成员列表
      return code;                               // ⑪ 返回暗号给界面显示
    }
    if (resp.code !== 409) {                     // ⑫ 不是「重复」其他错误
      throw new Error('创建家庭组失败：HTTP ' + resp.code);
    }
    // 409 表示这个暗号已经被别人占了，循环再试一次
  }
  throw new Error('邀请码连续冲突，请重试');
}
```

**为什么最多试 3 次**：  
6 位数字有 90 万种组合，实际用户量很小，撞号概率极低。试 3 次还撞，说明运气太差或者服务器有问题。

**为什么是「客户端生成暗号，服务器校验」而不是「服务器生成」**：  
因为客户端生成可以做「乐观 UI」——立刻就显示出暗号，不用等服务器返回。如果服务器说撞了，再换一个。

### 5.4 服务器怎么处理建组请求

**文件**：`sync/server.js` 第 88-104 行

```javascript
if (p === '/api/family/create' && req.method === 'POST') {
  const b = await readBody(req);              // ① 读出请求里的内容
  const code = String(b.code || '').trim().toUpperCase();  // ② 取出暗号，转大写

  if (code === '') {
    return sendJson(res, 400, { code: 400, msg: 'code required' });
  }
  if (db[code]) {                             // ③ 这个暗号已经存在？
    return sendJson(res, 409, { code: 409, msg: 'code exists' });
  }

  db[code] = { createdAt: Date.now(), members: {} };  // ④ 在内存里新建一个组
  if (b.deviceId) {
    db[code].members[b.deviceId] = snapshotOf(b);     // ⑤ 把建组的人放进去
  }
  persist();                                  // ⑥ 写到硬盘 data.json

  return sendJson(res, 200, { code: 0, data: { code, members: membersOf(code) } });
}
```

**`db` 是什么**：  
就是一个普通的 JavaScript 对象（类似字典），长这样：

```javascript
{
  "CF952298": {
    "createdAt": 1793696906081,
    "members": {
      "dev-mw0gt4j0-9frv": {
        "deviceId": "dev-mw0gt4j0-9frv",
        "name": "我的设备",
        "totalG": 15004,
        "balance": 163,
        "weekG": 4010,
        "updatedAt": 1793703040790
      }
    }
  }
}
```

**用大白话说**：这就是那块「公共白板」的内容，用 JSON 格式记着。

**`persist()` 是干什么的**：

```javascript
function persist() {
  fs.writeFileSync(DATA_FILE, JSON.stringify(db, null, 2), 'utf8');
}
```

把内存里的数据**写到硬盘上的 `data.json` 文件**。这样服务器重启了，数据还在。

**注意 `String(...).trim().toUpperCase()`**：  
用户可能输入「cf123456」或「 CF123456 」，统一转成「CF123456」。避免大小写和空格导致找不到组。

### 5.5 加入组：输入暗号

**文件**：`SyncService.ets` 第 179-199 行

```typescript
static async joinGroup(code: string, name: string): Promise<string> {
  const id = await SyncService.deviceId();
  const body = JSON.stringify({ code: code, deviceId: id, name: name });
  const resp = await SyncService.callPost('/api/family/join', body);

  if (resp === null) return 'offline';       // 服务器没开
  if (resp.code === 404) return 'notfound';  // 暗号不存在
  if (resp.code !== 200) return 'error';     // 其他错误

  await SyncService.setNickname(name);       // 记住这个昵称
  const g: FamilyGroup = { code: code, createdAt: Date.now() };
  await SyncService.saveGroup(g);            // 自己也记下来「我加入了 CF123456」
  await SyncService.reportSnapshot();        // ← 注意！这里没有上报？看下面
  await SyncService.pullMembers();           // 拉成员列表
  return 'ok';
}
```

**等等，这里有个细节**：

`joinGroup` 里**没有调 `reportSnapshot()`**。为什么？

因为服务端在处理 `join` 请求时，已经把请求体里的 `name` 存成成员快照了（`server.js` 第 113-116 行）：

```javascript
if (b.deviceId) {
  db[code].members[b.deviceId] = snapshotOf(b);   // 直接用请求里的数据建成员
  persist();
}
```

|                                                   |   |                                           |
| ------------------------------------------------- | - | ----------------------------------------- |
| 但 `snapshotOf(b)` 里 `totalG` 是 \`Number(b.totalG) |   | 0`，而 join 请求里没传 `totalG\`，所以**存进去的全是 0**。 |

**所以加入后必须马上上报一次真实数据**，否则成员列表里你会显示「0 kg」。

**代码里的实际做法**：`joinGroup` 之后，界面上会调 `syncNow()`，里面包含 `reportSnapshot()`。**这是一个隐患——如果用户加入后不点同步，会一直显示 0。**

> 这是个可以改进的点。正确做法是把 `reportSnapshot()` 加进 `joinGroup` 末尾。

### 5.6 上报数据：把自己的成绩单交上去

**这是整个同步的核心。**

**文件**：`SyncService.ets` 第 202-224 行

```typescript
static async reportSnapshot(): Promise<boolean> {
  const group = await SyncService.getGroup();     // ① 我在哪个组？
  if (group === null) return false;               // 没加入任何组就直接返回

  const id = await SyncService.deviceId();        // ② 我的设备号
  const name = await SyncService.getNickname();   // ③ 我的昵称

  // ④ 从本地数据库算出三个数字
  const totalG = await BehaviorRepo.sumAllReduction();  // 累计减排（克）
  const balance = await PointsService.getBalance();     // 积分余额
  const weekG = await SyncService.localWeekG();         // 本周减排

  // ⑤ 打包成 JSON
  const body = JSON.stringify({
    code: group.code, deviceId: id, name: name,
    totalG: totalG, balance: balance, weekG: weekG
  });

  // ⑥ 发给服务器
  const resp = await SyncService.callPost('/api/family/report', body);

  if (resp === null || resp.code !== 200) {
    SyncService.online = false;                   // 失败了，标记离线
    return false;
  }
  SyncService.online = true;                      // 成功了，标记在线
  SyncService.lastSyncAt = Date.now();            // 记下同步时间
  return true;
}
```

**三个数字从哪来**：

| 数字        | 怎么算的                | 代码位置                      |
| --------- | ------------------- | ------------------------- |
| `totalG`  | 把本地数据库所有行为记录的减排量加起来 | `Repository.ets` 第 162 行  |
| `balance` | 查积分流水最后一条的余额        | `Repository.ets` 第 250 行  |
| `weekG`   | 把本周的记录筛出来再加         | `SyncService.ets` 第 357 行 |

**关键点：上报的是「汇总后的数字」，不是原始记录**

你看，发上去的只有 3 个数字，**没有**把每条骑行记录都发上去。

**为什么不发原始记录**：

1. 数据量太大（一个月几百条记录）
2. 隐私问题（没必要让别人知道你几点骑车）
3. 家里只需要知道「谁减了多少」，不需要流水明细

**这就是「快照」的含义**：只传结果，不传过程。

### 5.7 服务器怎么存

**文件**：`sync/server.js` 第 143-156 行

```javascript
if (p === '/api/family/report' && req.method === 'POST') {
  const b = await readBody(req);
  const code = String(b.code || '').trim().toUpperCase();

  if (!db[code]) {                                  // 组不存在
    return sendJson(res, 404, { code: 404, msg: 'group not found' });
  }
  if (!b.deviceId) {                                // 没带设备号
    return sendJson(res, 400, { code: 400, msg: 'deviceId required' });
  }

  db[code].members[b.deviceId] = snapshotOf(b);      // ★ 关键这一行
  persist();
  return sendJson(res, 200, { code: 0, data: membersOf(code) });
}
```


**★ 这一行是整个同步最关键的一行**：

```javascript
db[code].members[b.deviceId] = snapshotOf(b);
```

**翻译成人话**：

> 在「CF123456 这个组」的「成员名单」里，找到「你这个设备号」那一格，**用新数据覆盖掉旧的**。

**为什么用「覆盖」而不是「新增」**：  
如果用新增，你上报 10 次就有 10 条记录，成员列表会变成 10 个「我的设备」。

**用设备号当「钥匙」直接覆盖，天然保证一个设备只有一条记录。** 这是幂等的（重复操作结果一样）。

**`snapshotOf()` 做了什么**（第 63-72 行）：

```javascript
function snapshotOf(b) {
  return {
    deviceId: String(b.deviceId || ''),    // 空的话给空串
    name: String(b.name || '成员'),        // 没名字就叫「成员」
    totalG: Number(b.totalG) || 0,        // 不是数字就当 0
    balance: Number(b.balance) || 0,
    weekG: Number(b.weekG) || 0,
    updatedAt: Date.now()                  // 服务器时间，不是客户端时间
  };
}
```

**为什么要做这些转换**：  
客户端可能发来脏数据（字符串、null、undefined）。服务器**不能信任客户端**，必须自己校验一遍。

**为什么 `updatedAt` 用服务器时间**：  
客户端的手机时间可能是错的（用户手动改过）。用服务器时间才能判断「这条数据是不是最新的」。

### 5.8 拉取数据：看别人的成绩

**文件**：`SyncService.ets` 第 227-263 行

```typescript
static async pullMembers(): Promise<boolean> {
  const group = await SyncService.getGroup();
  if (group === null) return false;

  const resp = await SyncService.callGet('/api/family/members?code=' + group.code);
  if (resp === null || resp.code !== 200) {
    SyncService.online = false;
    return false;
  }

  try {
    const parsed = JSON.parse(resp.body) as MembersResp;
    const list: FamilyMember[] = [];
    for (const r of parsed.data) {           // 遍历服务器返回的每个成员
      list.push({
        deviceId: r.deviceId,
        name: r.name,
        totalG: r.totalG,
        balance: r.balance,
        weekG: r.weekG,
        updatedAt: r.updatedAt,
        local: false                          // 标记：这些不是我自己的
      });
    }
    // ★ 存到本地缓存
    await store.put('family_members', JSON.stringify(list));
    await store.flush();

    SyncService.online = true;
    SyncService.lastSyncAt = Date.now();
    return true;
  } catch (e) {
    return false;
  }
}
```

**为什么要把别人的数据存到本地**：

因为**断网的时候还要能显示**。

```
有网时：拉到数据 → 存本地 → 显示
断网时：拉不到 → 用本地存的旧数据 → 显示「离线」
```

这就是「离线降级」。

**`local: false` 是什么意思**：

标记「这条数据是别人同步来的，不是我自己的」。  
后面算合计的时候，要避免把自己的数据算两次（服务器也会返回你自己的快照）。

### 5.9 合并：算出家庭总数

**这是最容易出错的地方。**

**文件**：`SyncService.ets` 第 370-405 行

```typescript
static async mergedStats(): Promise<MergedStats> {
  const myId = await SyncService.deviceId();         // ① 我是谁
  const cached = await SyncService.listMembers();    // ② 从缓存读成员列表

  // ③ 我自己的数据，实时从本地数据库算（保证最新）
  const myG = await BehaviorRepo.sumAllReduction();
  const myBalance = await PointsService.getBalance();
  const selfName = `我（本机）`;
  const mine: FamilyMember = {
    deviceId: myId,
    name: selfName,
    totalG: myG,
    balance: myBalance,
    weekG: await SyncService.localWeekG(),
    updatedAt: Date.now(),
    local: true                                      // ★ 标记是我自己
  };

  // ④ 先放自己
  const all: FamilyMember[] = [mine];

  // ⑤ 再加别人
  for (const m of cached) {
    if (m.deviceId === myId) {                       // ★★ 关键去重！
      continue;                                       // 如果是我自己，跳过
    }
    all.push(m);
  }

  // ⑥ 累加
  let totalG = 0;
  let totalPoints = 0;
  for (const m of all) {
    totalG += m.totalG;
    totalPoints += m.balance;
  }

  // ⑦ 按减排量从大到小排
  all.sort((a, b) => b.totalG - a.totalG);

  return { members: all, totalG: totalG, totalPoints: totalPoints };
}
```

**★★ 第 ⑤ 步的去重是整个功能最容易出 bug 的地方**：

服务器返回的成员列表里**包含你自己**。如果不去重：

```
合计 = 我(1.08) + 我(1.08) + 妈妈(0.72) = 2.88 kg   ← 错了！
正确应该是 1.08 + 0.72 = 1.80 kg
```

**所以必须用设备号判断「这条是不是我自己」，是就跳过。**

**为什么自己的数据要「实时算」而不是用缓存**：

```
你刚录了一条行为 → 立刻上报 → 服务器更新
                  ↓
              但这时候拉取列表可能还没完成
                  ↓
              如果用自己的缓存，会显示旧数字
```

**所以自己的数据永远从本地数据库实时算，保证自己看到的永远是最新的。**

### 5.10 什么时候自动上报

**这是代码里最有意思的一段注释。**

**文件**：`SyncService.ets` 第 314-344 行

```typescript
private static reporting: boolean = false;
private static pendingReport: boolean = false;

/**
 * 录入后触发上报。
 * 注意：不能用 setTimeout 做延迟合并——应用切到后台后定时器会被冻结，
 * 用户"录完就切到另一台设备"时上报会永远发不出去。这里改为立即上报，
 * 用 reporting 标志把并发调用合并成"进行中 + 结束后补一次"。
 */
static scheduleReport(): void {
  if (SyncService.reporting) {        // 如果正在上报
    SyncService.pendingReport = true; // 记一笔「还有一次要报」
    return;
  }
  SyncService.runReport();            // 否则立刻开始
}

private static async runReport(): Promise<void> {
  SyncService.reporting = true;       // 打上「正在上报」的标记
  try {
    const g = await SyncService.getGroup();
    if (g !== null) {
      await SyncService.reportSnapshot();
    }
  } catch (e) {
    // 静默失败
  } finally {
    SyncService.reporting = false;    // 清掉标记
    if (SyncService.pendingReport) {  // 如果期间有新请求
      SyncService.pendingReport = false;
      SyncService.scheduleReport();    // 再跑一次
    }
  }
}
```

**这段注释讲了一个真实的 bug**：

**早期版本用的是「延迟 800 毫秒再上报」**（防抖）：

```typescript
// 旧代码（已废弃）
setTimeout(() => { reportSnapshot() }, 800);
```

**问题**：如果你录完行为，**立刻切到另一台手机**，这个 800 毫秒的定时器**会被系统冻结**（应用切到后台，系统会暂停它）。

结果：**上报永远发不出去**，另一台设备看不到你的新数据。

**改成现在这样**：

- **立刻上报**，不延迟
- 用 `reporting` 标记防止并发（同时发起多个请求会导致服务器数据乱序）
- 如果上报中又来了新请求，标记 `pendingReport`，等当前这次结束后**补一次**

**用大白话说**：

> 不能「等我 1 秒钟再发」，因为你可能这一秒就切走了，我就发不出去了。  
> 改成「马上发」。如果正在发的时候又来一条，就排队，发完这条再发那条。

### 5.11 断网了怎么办

**文件**：`SyncService.ets` 第 105-114 行 + 116-140 行

```typescript
/** 同步服务候选地址：配置 → 模拟器宿主别名 → 本机回环 */
private static candidates(configured: string): string[] {
  const raw: string[] = [configured.trim(), 'http://10.0.2.2:8081', 'http://127.0.0.1:8081'];
  const out: string[] = [];
  for (const u of raw) {
    if (u !== '' && out.indexOf(u) < 0) {   // 非空且不重复
      out.push(u);
    }
  }
  return out;
}
```

**`10.0.2.2` 是什么**：

这是模拟器的特殊地址，**固定指向「宿主机」**（你的电脑）。

```
模拟器里的 127.0.0.1  →  指向模拟器自己（不是你的电脑！）
模拟器里的 10.0.2.2   →  指向你的电脑
```

**所以 App 会依次尝试三个地址**：

```
① 用户在设置里填的地址（如果有）
② http://10.0.2.2:8081   ← 模拟器找电脑
③ http://127.0.0.1:8081  ← 真机上找本机
```

**哪个通就用哪个，全不通就返回 null（表示离线）。**

## 第七步：五个设计决策（答辩时能讲出这些，显得你真懂）

### 决策 1：为什么传「快照」不传「原始记录」

|      | 传快照     | 传原始记录       |
| ---- | ------- | ----------- |
| 数据量  | 3 个数字   | 几百条记录       |
| 隐私   | 只知道总数   | 知道几点骑车      |
| 冲突处理 | 直接覆盖，简单 | 要判断哪条是新的，复杂 |

**结论**：家庭场景只需要知道「谁减了多少」，不需要流水。

### 决策 2：为什么用「设备号」做主键

如果不用设备号，怎么知道「这条数据是谁的」？

- 用名字？名字可以重复（两个人都叫「妈妈」）
- 用顺序？顺序会乱

**设备号是唯一且稳定的标识**，用它做「钥匙」，重复上报自动覆盖。

### 决策 3：为什么服务端用 JSON 文件存，不用数据库

|     | JSON 文件      | 数据库     |
| --- | ------------ | ------- |
| 部署  | 只要有 Node 就能跑 | 要装数据库   |
| 演示  | 打开文件就能看到数据   | 要连数据库工具 |
| 数据量 | 几百个家庭组没问题    | 更适合大规模  |

**这是演示项目，不是生产系统。** 用 JSON 文件让评委能亲眼看到数据长什么样，这是优势。

### 决策 4：为什么「立刻上报」而不是「延迟合并」

前面讲过：延迟的定时器会被系统冻结。

**这是一个真实踩过的坑，不是理论推导。**

### 决策 5：为什么自己的数据要从本地实时算

服务器返回的列表可能滞后（你刚录完，上报可能还没完成）。  
**自己看到的数字必须是最新的**，所以自己的部分永远本地算。

## 第八步：可能被追问的问题

### Q1：这算「分布式」吗

**严格说不算。**

这是**应用层多端同步**。分布式通常指「设备之间直接通信，无需中心服务器」。我们用了中心服务器，所以是「客户端-服务器」架构。

**答辩时说**：

> 我实现的是**应用层多端同步**，不是系统级分布式。PPT 和文档里写的也是「应用层多端同步」，没有说是分布式。

### Q2：为什么不用真机演示

**答**：

> 真机需要两台设备登录同一华为账号并建立互信，演示环境不具备。而且我的方案是应用层 HTTP，**真机上同样能跑**——把地址从 `10.0.2.2` 换成电脑的局域网 IP 即可。

### Q3：如果两台设备同时上报会冲突吗

**答**：

> 不会。因为用设备号做 key，各自覆盖自己的格子，互不干扰。就像白板上每人写自己那一行。

**但有个真实限制**：如果同一台设备在两个地方同时上报（比如登录了两次），后到的会覆盖先到的。这是「最后写入者胜」（Last Write Wins）策略，家庭场景可以接受。

### Q4：数据安全吗

**答**：

> 这是局域网内的演示服务，没有做鉴权。生产环境需要加：① HTTPS 传输 ② 用户身份验证 ③ 家庭组密码。这些是明确的改进方向。

**主动说不足，比装作完美可信。**

### Q5：为什么 `joinGroup` 之后要单独上报一次

**答**：

> 因为 join 接口只登记了设备号和昵称，没有带减排数据。所以服务端存的是 0，必须紧接着调一次 `reportSnapshot()` 把真实数据补上。

**这个点如果被问到，说明评委看了代码，你要能立刻答出来。**
