# 一、先用一个比喻看懂整体

## 你的 App 像一个「记账公司」

```
┌──────────────────────────────────────────────┐
│  前台（页面层 pages/）                        │
│  「我要记一笔骑行 6 公里」                     │
│  「我要看这个月减了多少」                      │
└────────────────┬─────────────────────────────┘
                 ↓ 交给
┌──────────────────────────────────────────────┐
│  业务部（服务层 service/）                     │
│  「先检查合不合法 → 算减排量 → 算积分」         │
│  「开一张事务单，两笔账一起记」                 │
└────────────────┬─────────────────────────────┘
                 ↓ 交给
┌──────────────────────────────────────────────┐
│  档案室（数据层 db/）                          │
│  把数据真正写进硬盘上的数据库文件               │
└──────────────────────────────────────────────┘
```

**前台不碰数据库，业务部不写 SQL，档案室只管存取。**

这是**分层**。好处是：改界面不影响算法，改算法不影响存储。

## 数据在三种地方存着

| 存储 | 存什么 | 存在哪 | 类比 |
|---|---|---|---|
| **RDB（关系数据库）** | 行为记录、积分流水、任务、徽章 | 硬盘上的 `.db` 文件 | 正式账本，永久保存 |
| **Preferences** | 昵称、月目标、卡片顺序、AI 密钥 | 系统的键值存储 | 便利贴，小配置 |
| **AppStorage** | 当前 Tab、刷新信号 | **内存**，关 App 就没了 | 白板，临时状态 |

**为什么要三种**：

- 账目要能查询、能统计 → 必须用数据库
- 昵称就一个字符串 → 用数据库太重，用便利贴（Preferences）刚好
- 「现在是第几个 Tab」关掉 App 就没意义 → 放内存（AppStorage）最快

# 二、数据存在哪：三张核心表

## 表 1：`t_behavior_record`（行为记录）

**每录一条行为，这里多一行。**

```sql
CREATE TABLE t_behavior_record (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,  -- 编号，自动递增
  type         TEXT NOT NULL,    -- 大类：出行
  sub_type     TEXT NOT NULL,    -- 子类：骑行
  value        REAL NOT NULL,    -- 数值：6
  unit         TEXT NOT NULL,    -- 单位：km
  factor       REAL NOT NULL,    -- 系数：180（快照！）
  reduction_g  INTEGER NOT NULL, -- 减排：1080 克
  created_at   INTEGER NOT NULL, -- 时间戳
  note         TEXT,             -- 备注
  source       TEXT DEFAULT 'manual'  -- 来源：手动/AI/平台
)
```

**一条真实数据长这样**：

```
id=11 | type=出行 | sub_type=骑行 | value=6 | unit=km
factor=180 | reduction_g=1080 | created_at=1762... | note= | source=manual
```

**读法**：「出行-骑行，6 公里，按 180 g/km 算，减排 1080 克，手动录入」

## 表 2：`t_points_record`（积分流水）

**每次加减分，这里多一行。注意：是「流水」，不是「余额」。**

```sql
CREATE TABLE t_points_record (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  source        TEXT NOT NULL,    -- 来源：behavior/task/read/exchange
  ref_id        INTEGER NOT NULL, -- 关联的记录 id
  action        TEXT NOT NULL,    -- 描述：「骑行 6km，减排1.08kg」
  points        INTEGER NOT NULL, -- 本次变动：+10 或 -5
  balance_after INTEGER NOT NULL, -- 变完之后是多少：172
  created_at    INTEGER NOT NULL
)
```

**为什么存「变完之后」而不是只存「变动」**：

```
流水：
  +62 → balance_after=162
  +1  → balance_after=163
  +15 → balance_after=178

问：现在多少分？
答：看最后一条的 balance_after = 178。一次查询搞定。
```

如果只存变动，问余额就要 `SUM(points)` 全表求和。**存 `balance_after` 是空间换时间。**

## 表 3、4、5

| 表 | 存什么 | 谁灌进去的 |
|---|---|---|
| `t_task` | 12 个任务定义 | 启动时从 `tasks.json` 灌入 |
| `t_task_completion` | 任务完成记录（哪期完成过） | 达标瞬间插入 |
| `t_badge` | 9 枚徽章定义 + 解锁状态 | 启动时从 `badges.json` 灌入 |

# 三、写链路：提交一条记录，数据怎么流

**这是全项目最重要的一条链路。答辩必讲。**

## 全景图

```
①你在录入页选「出行-骑行」，输入 6，点提交
        ↓
②Record.ets  收集参数
        ↓
③BehaviorService.submit()  ← 唯一入口
        ↓
   ┌────┴────────────────────────────┐
   │ 三重校验（类型/数值/上限）        │
   │ 算减排：6 × 180 = 1080 g        │
   │ 算积分：1080 / 100 = 10 分      │
   └────┬────────────────────────────┘
        ↓
   ┏━━━━━━━━━━━━━━━━━━━━━━━━━━┓
   ┃ 事务开始 beginTx()        ┃
   ┃  写 t_behavior_record    ┃
   ┃  写 t_points_record      ┃
   ┃ 提交 commitTx()          ┃
   ┗━━━━━━━━━━━━━━━━━━━━━━━━━━┛
        ↓ 事务外
④判任务达标 → 检徽章 → bumpTick() 广播 → 异步报家庭
        ↓
⑤7 个页面同时刷新，首页数字变了
```

## 逐层拆解

### 第 ① 层：页面收集（`pages/Record.ets:150-185`）

```typescript
const ts = this.customTs > 0 ? this.customTs : Date.now();
if (ts > Date.now()) {
  promptAction.showToast({ message: '时间不能晚于当前时刻' });
  return;
}
const sub = this.currentSub();
const result = await BehaviorService.submit(this.selType, this.selSub,
  this.parseValue(), sub.unit, sub.factor, ts, this.noteText);
```

**页面只做三件事**：

| 做什么 | 为什么在页面做 |
|---|---|
| 时间不能超过现在 | 这是 UI 交互问题，用户看到的是 Toast |
| 取出选中的子类型 | 是页面自己的状态 |
| 把 7 个参数打包传给 Service | **页面不负责算，只负责传** |

**关键：页面没有算减排量、没有算积分、没有碰数据库。** 它只收集。

### 第 ② 层：为什么参数是 7 个

```typescript
submit(type, subType, value, unit, factor, ts, note, source)
```

| 参数 | 来源 | 为什么要单独传 |
|---|---|---|
| `type` / `subType` | 用户选的 | 用来查因子库 |
| `value` | 用户输的 | 数值 |
| `unit` | **因子库里的** | AI 识别可能给不同单位 |
| `factor` | **因子库里的** | ★ 见下 |
| `ts` | 用户选的（可补录） | 可以补录昨天的 |
| `note` | 用户写的 | 备注 |
| `source` | 调用方指定 | 区分手动/AI/平台 |

**`factor` 为什么不在 Service 里自己查？**

因为 `submit()` 有三个调用方，各自的系数来源不同：

```
Record.ets      → sub.factor（因子库）
AiRecognize.ets → 可能带模型建议的系数
SettingsDetail  → 可能带平台返回的系数
```

**如果 Service 自己去查因子库，就对不上调用方传的数值了。** 所以由调用方传进来，Service 只负责「用你给的系数算」。

### 第 ③ 层：三重校验（`BehaviorService.ets:18-27`）

```typescript
const sub = CalculationService.findSub(type, subType);
if (sub === null) {
  throw new Error('未知的行为类型');        // 校验 1
}
if (!isFinite(value) || value <= 0) {
  throw new Error('数值必须大于 0');        // 校验 2
}
if (value > sub.max) {
  throw new Error(`超出单次上限：最多 ${sub.max} ${sub.unit}`);  // 校验 3
}
```

**为什么要三重**：

| 校验 | 挡住什么坏数据 | 举例 |
|---|---|---|
| 类型存在 | 因子库里没有的类型 | AI 识别出「滑板车」，因子库没这个 |
| 数值有限正数 | `NaN`、`Infinity`、0、负数 | `parseFloat('abc')` = NaN |
| 不超上限 | 手误多打几个 0 | 骑行填 60000 km |

**`!isFinite(value)` 一个判断拦两种**：`NaN` 和 `Infinity` 都能通过 `typeof === 'number'`，但都不是有效数值。

**为什么放在 Service 层而不是页面层**：

`submit()` 有 3 个调用方（手动、AI、平台导入）。校验写在页面里要写 3 遍，还可能漏。**放在 Service，三条路都绕不过。**

### 第 ④ 层：算两笔数（`BehaviorService.ets:28-41`）

```typescript
const grams: number = Math.round(value * factor);
// ...
const points = CalculationService.valueToPoints(grams);
```

**第一个公式：减排量**

```
grams = round(value × factor)
      = round(6 × 180)
      = 1080 克
```

**为什么 `Math.round` 不是 `floor`**：`floor` 会系统性偏小，每条记录都少算一点，误差累积。

**第二个公式：积分**（`CalculationService.ets:71-76`）

```typescript
Math.max(1, Math.floor(grams / 100))
//  = max(1, floor(1080/100))
//  = max(1, 10) = 10 分
```

**为什么 `Math.max(1, ...)` 兜底**：光盘一餐 50~100 克，`floor(50/100) = 0`。用户认真记录却 0 分，会挫败。**保底 1 分是产品决策。**

### 第 ⑤ 层：事务（`BehaviorService.ets:43-56`）★ 最核心

```typescript
DBHelper.beginTx();                          // ① 开事务
try {
  const id = BehaviorRepo.insertSync(record); // ② 写行为表
  record.id = id;
  if (points > 0) {
    await PointsService.addPointsTx('behavior', id, ..., points);  // ③ 写积分表
  }
  DBHelper.commitTx();                        // ④ 提交
} catch (e) {
  DBHelper.rollbackTx();                      // ⑤ 出事全撤回
  throw e as Error;
}
```

**为什么两笔写必须在一个事务里**：

```
如果分开写：
  写行为表成功 ✓
  写积分表失败 ✗
  → 结果：历史页有记录，但积分没加
  → 用户看到「减了 1.08 kg 但没得分」
  → 这个烂账无法自愈
```

**用一个比喻**：

> 你去银行转账 100 元给朋友。
>
> **正确的做法**：扣你的 100 和加他的 100 是**同一个操作**，要么都成，要么都不成。
>
> **错误的做法**：先扣你的，再试着加他的。加失败了呢？你的钱消失了。

**`if (points > 0)` 的用意**：不写「0 分」的垃圾流水。什么时候 0 分？`grams` 极小时（节水 0.001 升 × 0.3 = 0.0003 g，round 成 0）。

**为什么用 `addPointsTx` 而不是 `addPoints`**：

```typescript
addPointsTx()  // 不自带事务，假定调用方已开
addPoints()    // 自带 beginTx/commitTx
```

鸿蒙 RDB **不支持事务嵌套**。已经 `beginTx()` 了，再调 `addPoints()` 会在事务里再开事务，直接报错。

### 第 ⑥ 层：事务外的三段（`BehaviorService.ets:58-71`）

```typescript
const newBadges: string[] = [];
try {
  await TaskService.evaluateAll();       // 判任务
  const badges = await BadgeService.checkAll();  // 检徽章
  for (const b of badges) newBadges.push(b);
} finally {
  bumpTick();                            // 广播刷新
}
SyncService.scheduleReport();            // 异步报家庭
```

**三个设计要点**：

**① 顺序不能颠倒**

「任务达人」徽章的判定条件是 `tasks_done >= 10`，依赖 `t_task_completion` 表。**任务必须先判定，徽章才可能解锁。**

**② 必须在事务外**

`evaluateAll()` 内部自己 `beginTx`。如果放在上面的事务里，就是嵌套事务，鸿蒙不支持。

**③ 用 `try-finally` 而不是 `try-catch`**

这是修过的真实缺陷（DF-50）：

```
事务已经提交 → 数据确定落库
如果 evaluateAll 抛异常 → bumpTick 被跳过
→ 数据改了但界面不刷新
→ 用户以为保存失败，再点一次 → 重复记录
```

**`finally` 保证 `bumpTick` 一定执行。**

**`scheduleReport()` 为什么不 await**：同步是「锦上添花」，失败不该影响本地录入。**这叫降级设计。**

### 第 ⑦ 层：广播刷新（`common/Constants.ets:48`）

```typescript
let tickCounter: number = 0;

export function bumpTick(): void {
  tickCounter += 1;
  AppStorage.setOrCreate(Constants.KEY_TICK, tickCounter);
}
```

**这一行代码，让 7 个页面同时刷新。**

**为什么用递增计数而不是 `Date.now()`**：

```
Date.now() 版：
  15:23:45.123 → 第一次 bumpTick，tick = 1762...
  15:23:45.123 → 第二次 bumpTick（同一毫秒），tick 还是 1762...
  → @StorageLink 认为值没变 → 不通知 → 不刷新 ✗

递增计数版：
  tick = 1 → tick = 2 → 每次必变 ✓
```

**这是修过的缺陷（DF-49）。**

# 四、读链路：首页数字怎么出来的

## 全景图

```
①你打开 App 或切回首页
        ↓
②HomeView.refresh() 被调用
        ↓
③await AppInit.ensure()  等初始化完成
        ↓
④BehaviorRepo.all()  一次性取全部行为记录
        ↓
⑤并行发起 9 个查询（Promise.all）
  积分 / 待办数 / 连续天数 / 月目标 / 卡片顺序
  昵称 / 任务进度 / 推荐任务 / 建议
        ↓
⑥在内存里算：
  todayG   = 遍历 records 累加今天的
  monthG   = StatsService.monthSum()
  trend    = StatsService.trend()  分桶聚合
  pie      = StatsService.categoryShare()
  weekly   = StatsService.weekReport()
        ↓
⑦赋值给 @State 变量 → ArkUI 自动重绘
        ↓
⑧存一份快照给桌面卡片
```

## 关键代码（`pages/Index.ets:161-240`）

### 第一步：只查一次全表

```typescript
const records: BehaviorRecord[] = await BehaviorRepo.all();
```

**注意：查的是全部记录，不是「今天的」。**

**为什么**：趋势图要 5 年的数据、月目标要本月、周报要本周和上周、饼图要当前档位。**一次全查，内存里算，比拼多次 SQL 快。**

**数据量估算**：一天 5 条，一年 1800 条。1800 条记录在内存里遍历，毫秒级。**这个量级下，内存计算远比多次 SQL 高效。**

### 第二步：9 个查询并行（`Index.ets:166-180`）

```typescript
const pBalance: Promise<number> = PointsService.getBalance();
const pPending: Promise<number> = TaskService.pendingCount();
const pStreak: Promise<number> = BadgeService.currentStreak();
const pGoal: Promise<number> = PrefsService.getMonthlyGoalKg();
// ... 共 9 个

await Promise.all([pBalance, pPending, pStreak, pGoal, ...]);
```

**代码注释原文**：

```
各页数据互不依赖，并行取齐再逐一赋值，避免十几次串行 await
把首帧拖住（切 Tab / 路由转场时尤其明显）
```

**对比**：

| 写法 | 耗时 |
|---|---|
| 串行 `await` 9 次 | 9 × 每次 10ms = **90ms** |
| 并行 `Promise.all` | max(10ms) ≈ **10ms** |

**差 9 倍。** 用户能感知到 90ms 的卡顿。

### 第三步：内存里算今日（`Index.ets:191-203`）

```typescript
const todayStart = DateUtil.startOfDay(now);
let todaySum = 0;
let todayCount = 0;
for (const r of records) {
  if (r.createdAt >= todayStart && r.createdAt <= now) {
    todaySum += r.reductionG;
    todayCount++;
  }
}
```

**注意条件是「>= 今天0点」而且「<= 现在」**。

**为什么加 `<= now` 上界**：防脏数据。如果数据库里有未来时间的记录（比如用户改时间时出了 bug），不加这个上界就会算进今天。**代码注释里明说了这是「与历史页修改入口的校验互为兜底」——双保险。**

### 第四步：调统计服务（`Index.ets:207-210`）

```typescript
this.trend = StatsService.trend(records, this.trendKind);
this.pie = StatsService.categoryShare(records, StatsService.rangeStart(this.trendKind));
this.monthG = StatsService.monthSum(records);
this.weekly = StatsService.weekReport(records);
```

**全部是「传入 records，返回结果」的纯函数**。不查库、不写库、无副作用。

**这是好设计**：纯函数好测试（给一组数据，验证输出对不对），也好复用（首页和历史页都能用）。

### 第五步：赋值触发重绘（`Index.ets:198-220`）

```typescript
this.todayG = todaySum;      // @State 变量
this.balance = balance;
this.trend = this.trend;     // 数组也是 @State
```

**ArkUI 的响应式**：`@State` 变量一赋值，用到它的 UI 部分自动重绘。**不需要手动调「刷新界面」。**

### 第六步：存快照给桌面卡片（`Index.ets:228-236`）

```typescript
await CardSnapshot.save({
  todayG: todaySum,
  monthPct: ...,
  streak: this.streak,
  balance: this.balance,
  updatedAt: Date.now()
});
```

**为什么需要这一步**：桌面卡片由**系统进程**渲染，不能访问 App 的数据库。只能 App 把数据序列化到 Preferences，卡片去读。

# 五、刷新链路：改完为什么别的页面也会变

## 全景图

```
你在历史页改了一条记录的数值
        ↓
BehaviorService.updateRecord()
        ↓
事务提交（数据库变了）
        ↓
bumpTick()   ← 关键
        ↓
AppStorage['tick'] 从 5 变成 6
        ↓
  ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┐
  ↓     ↓     ↓     ↓     ↓     ↓     ↓
首页  录入  历史  任务  我的  徽章  科普
refresh 各自重新查库、重新算、重新赋值
        ↓
7 个页面同时显示新数据
```

## 7 个监听者（已核查）

| 页面 | 行 | 回调方法 |
|---|---|---|
| `Index.ets`（首页） | 87 | `refresh()` |
| `Record.ets`（录入） | 15 | `onDataTick()` |
| `History.ets`（历史） | 25 | `refresh()` |
| `Tasks.ets`（任务） | 21 | `refresh()` |
| `Settings.ets`（我的） | 16 | `refresh()` |
| `Badges.ets`（徽章） | 20 | `refresh()` |
| `Knowledge.ets`（科普） | 13 | `refresh()` |

**写法都一样**：

```typescript
@StorageLink('tick') @Watch('refresh') tick: number = 0;
```

**翻译成人话**：

> 「`tick` 这个变量，和全局存储里的 `tick` 绑定。全局一变，我这边也变。我这边一变，就调用 `refresh()`。」

## 为什么用广播而不是「各自通知」

**方案 A（广播，现在的做法）**：

```typescript
bumpTick();   // 一行代码，7 个页面全知道
```

**方案 B（各自通知）**：

```typescript
// 在 BehaviorService 里
homeView.refresh();
historyView.refresh();
tasksView.refresh();
...
// → BehaviorService 要 import 所有页面 → 循环依赖
// → 加个新页面要改 BehaviorService
```

**广播的价值：解耦。** `BehaviorService` 不知道有谁在听，它只喊一声「数据变了」。谁关心谁自己响应。

## 一个隐蔽的坑：`ForEach` 的 key

**广播能触发 `refresh()`，但 `refresh()` 算完新数据后，界面不一定会更新。**

这是修过的真实缺陷（DF-48）。原因是这样的：

```typescript
// 历史页的分组列表（改前）
ForEach(this.groups, (g) => {...}, (g) => g.label + '#' + g.items.length)
//                                          ↑ key = "今天#1"
```

**`key` 的作用**：ArkUI 用 `key` 判断「这个元素变了没有」。key 没变 → 认为没变 → **直接复用旧的，不重新渲染**。

```
改前：1 条记录，key = "今天#1"
改成 30：还是 1 条记录，key = "今天#1"
→ key 完全相同 → ArkUI 复用整个分组 → 内层卡片不重新渲染 → 显示旧值
```

**改成含内容的 key**：

```typescript
(g) => g.label + '#' + g.items.map(r => r.id + '_' + r.value + '_' + r.reductionG).join(',')
// key = "今天#11_30_1800"
```

**这样值一变，key 就变，ArkUI 就会重新渲染。**

**这个坑的启发**：广播只负责「通知」，能不能正确渲染，还取决于 UI 层的 key 设计。**两件事都要对。**

```
┌───────────────────────────────────────────────────────────────┐
│  你在界面上做了什么                                             │
└──────────────────────────┬────────────────────────────────────┘

│  │   ④ 事务：写行为表 + 写积分表                             │  │

└──────────────────────────┬────────────────────────────────────┘
                           ↓
┌──────────────────────────┴────────────────────────────────────┐
│  数据层  db/*.ets                                              │

└──────────────────────────┬────────────────────────────────────┘
                           ↓
┌──────────────────────────┴────────────────────────────────────┐

└───────────────────────────────────────────────────────────────┘
```

## 三条链路对照表

| | 写链路 | 读链路 | 刷新链路 |
|---|---|---|---|
| 触发 | 点提交/删除/修改 | 进页面/切 Tab | 任何写操作完成后 |
| 入口 | `BehaviorService.submit()` | `HomeView.refresh()` | `bumpTick()` |
| 碰数据库吗 | **写**（事务内两表） | **读**（一次全表 + 9 并行） | 读（各自 refresh） |
| 算数吗 | 算（减排 + 积分） | 算（统计聚合） | 算（同上） |
| 输出 | 数据库变了 | `@State` 变了 | 7 个页面都更新 |
| 关键文件 | `BehaviorService.ets` | `Index.ets` + `StatsService.ets` | `Constants.ets:48` |

# 七、五个关键设计（答辩重点）

## ① 分层：页面不碰数据库

**现象**：`pages/` 下 14 个文件，**没有一个 import `DBHelper` 或 `Repository`**。

**为什么**：

| 好处 | 具体 |
|---|---|
| 可测试 | Service 可以脱离 UI 单独测 |
| 可替换 | 换数据库只改 `db/` 层 |
| 防重复 | 校验、计算只有一处实现 |

## ② 事务：两笔写必须原子

**核心代码**（`BehaviorService.ets:43-56`）：

```typescript
DBHelper.beginTx();
try {
  写行为表;
  写积分表;
  DBHelper.commitTx();
} catch (e) {
  DBHelper.rollbackTx();
  throw e;
}
```

**答辩说法**：

> 行为和积分是一对绑定账。分两次写会出现「记录在列表里但积分没加」的烂账。这像转账，扣你的钱和给对方加钱必须一起成。

## ③ 因子快照：历史不可变

`t_behavior_record` 存了 `factor`（当时系数）和 `reduction_g`（结果）。

**为什么**：因子库以后可能修订（骑行 180 → 170）。如果没有快照，历史记录会被「追溯改写」，用户三月的账目莫名变少。

**价值**：让因子库可以持续迭代，不必担心破坏已有账目。

## ④ 事件溯源：余额是流水的推导

**余额不存在独立字段**，查最后一条流水的 `balance_after`。

```typescript
static async getBalance(): Promise<number> {
  return await PointsRepo.lastBalance();   // SELECT ... ORDER BY id DESC LIMIT 1
}
```

**好处**：不可能出现「余额和流水对不上」——余额本身就是流水的推导结果。

**代价**：每次读余额要一次索引查询，可接受。

## ⑤ 降级：失败不阻断主流程

| 场景 | 降级方式 |
|---|---|
| 同步服务连不上 | 用本地缓存显示成员，标「离线」 |
| 碳普惠远端不可用 | 用内置 5 个权益，标「本地演示」 |
| AI 识别失败 | 返回明确原因，**绝不编造结果** |
| 补列失败 | `sourceReady=false`，写入不带该列，App 照常用 |
| 桌面卡片快照 | 定时刷新，读不到旧数据也不崩 |

**统一原则**：**主流程（记一笔）必须成功，附属功能（同步/识别/卡片）可以降级。**

# 八、可能被问的 15 个问题

## Q1：数据存在哪？为什么不全放数据库？

> 分三种。**账目类**（行为、积分、任务、徽章）放 RDB，因为要查询和统计；**配置类**（昵称、目标、卡片顺序）放 Preferences，一个字符串用数据库太重；**临时状态**（当前 Tab、刷新信号）放 AppStorage 内存，关 App 就没意义。
>
> 分三种是为了匹配各自的访问模式，不是随意选择。

## Q2：录一条记录，数据怎么走？

> 九步。页面收集参数 → `BehaviorService.submit()` 校验 → 算减排量 → 算积分 → **事务内写两张表** → 提交 → 事务外判任务 → 检徽章 → `bumpTick()` 广播。
>
> 关键在第 5 步：两笔写在一个事务里，要么都成要么都败。

## Q3：为什么要开事务？不开会怎样？

> 行为和积分是一对绑定账。不开事务，可能「写行为成功、写积分失败」，用户看到「减了 1.08 kg 但没得分」，这个烂账无法自愈。
>
> 这跟银行转账一个道理：扣你和加对方必须一起成。

## Q4：为什么算减排要传 `factor` 参数，不在函数里查？

> 因为 `submit()` 有三个调用方：手动录入、AI 识别、平台导入。它们的系数来源不同——手动用因子库，AI 可能带模型给的值，平台可能带对方算好的值。
>
> 如果 Service 自己查因子库，就和调用方传的数值对不上了。所以由调用方传，Service 只负责「用你给的系数算」。

## Q5：为什么积分有两个方法（`addPoints` / `addPointsTx`）？

> 区别是**事务边界**。`addPointsTx` 不自带事务，必须被调用方的事务包住；`addPoints` 自带事务。
>
> 判据只有一条：**当前是否已经在别人的事务里**。在，就调不带事务的；不在，就调自带事务的。
>
> 搞反了会事务嵌套，鸿蒙 RDB 不支持。

## Q6：为什么不把所有积分都塞进 `BehaviorService`？

> 三个原因。**一是依赖成环**：`TaskService` 依赖 `PointsService`，`BehaviorService` 依赖 `TaskService`，如果 `PointsService` 反过来依赖 `BehaviorService` 就成环了。
>
> **二是语义无关**：积分有四个来源——行为、任务、阅读、兑换。后三个和行为记录毫无关系。
>
> **三是事务粒度不匹配**：碳普惠兑换里有 HTTP 请求，可能 5 秒。硬套本地事务会锁住数据库 5 秒，其他写入全阻塞。
>
> **积分逻辑其实是统一的**，统一在 `PointsRepo`——全项目只有这一处写流水表。分散的只是「什么时候该加分」这个业务判断。

## Q7：首页那么多数据，性能怎么保证？

> 两个优化。
>
> **第一，只查一次全表**。`BehaviorRepo.all()` 取全部记录，今日数、本月数、周报、趋势图、饼图全部从这一份数据在内存里算。数据量估算：一天 5 条，一年 1800 条，内存遍历毫秒级。
>
> **第二，9 个独立查询并行**。用 `Promise.all` 并发发起积分、待办数、连续天数、月目标等 9 个查询。串行要 90ms，并行约 10ms，差 9 倍。

## Q8：改了一条记录，为什么首页也变了？

> 靠 `bumpTick()` 广播。写操作完成后，`bumpTick()` 把 AppStorage 里的 `tick` 递增。**7 个页面都用 `@StorageLink('tick') @Watch('refresh')` 监听它**，值一变各自重新查库、重新算、重新赋值。
>
> 这样 `BehaviorService` 不需要知道有谁在听，它只喊一声「数据变了」。**加新页面不用改 `BehaviorService`。**

## Q9：`bumpTick` 为什么不用 `Date.now()`？

> 因为同一毫秒内两次调用，`Date.now()` 返回相同值，`@StorageLink` 认为没变化，`@Watch` 不触发，界面就不刷新。
>
> 改成模块级的单调递增计数，每次调用必然变化。**这是修过的真实缺陷（DF-49）。**

## Q10：为什么 `bumpTick()` 放在 `finally` 里？

> 因为事务已经提交，数据确定落库。如果后面的 `evaluateAll()` 抛异常，`bumpTick()` 被跳过，就会出现「数据改了但界面不刷新」，用户以为保存失败，可能再点一次造成重复记录。
>
> 用 `finally` 保证它一定执行。**这是修过的真实缺陷（DF-50）。**

## Q11：什么是因子快照？为什么需要？

> `t_behavior_record` 里存了 `factor` 字段，这是**录入当时的系数**，不是当前系数。
>
> 因为因子库以后会修订。如果没有快照，历史记录会被新因子「追溯改写」，用户三月的 1.08 kg 变成 1.02 kg，账目莫名变少。
>
> 这是**不可变事实**的设计：已经发生的记录不该被后来的规则改变。发票、银行流水都是同样逻辑。

## Q12：余额怎么存的？会不会和流水对不上？

> 余额**不存在独立字段**，而是查最后一条流水的 `balance_after`。
>
> 所以不可能对不上——余额本身就是流水的推导结果。这是**事件溯源的简化版**。
>
> 代价是每次读余额要一次索引查询，可接受。

## Q13：`ensureColumn` 是干什么的？

> 解决数据库升级问题。`CREATE TABLE IF NOT EXISTS` 只判断「表存不存在」，不判断「列全不全」。老用户的表已存在，新加的 `source` 列永远不会创建，查询就报 `no such column`。
>
> 所以要先 `PRAGMA table_info` 查有哪些列，缺了才 `ALTER TABLE ADD COLUMN`。加过了就跳过，反复执行安全。
>
> 失败时返回 `false` 而不是抛异常，写入时不带该列，App 继续能用。

## Q14：数据链路有单点故障吗？

> 有，是**数据库文件本身**。SQLite 是单文件数据库，文件损坏就全丢。
>
> 缓解手段是导出功能：`ExportService.backupJson()` 可以全量导出 JSON，用户自己保存到任意位置。这是「用户自己掌握备份」的设计。
>
> 更彻底的方案是接入云端同步，但那会引入隐私问题，当前定位是本地优先。

## Q15：如果让你重构数据层，你会改什么？

> 三个方向。
>
> **一是加 `factor_ver` 字段**。现在记录里存的是系数数值，没有存因子库版本号。加了就能查询「哪些记录用的是 v2026.11 的系数」。
>
> **二是趋势聚合下推到 SQL**。现在 `StatsService.trend()` 是把全部记录取到内存再分桶。数据量大了（比如 10 万条）会慢。可以用 `GROUP BY strftime(...)` 让数据库做聚合。
>
> **三是给 `Repository` 加缓存层**。首页每次切 Tab 都全表查一次，如果记录没变可以复用上次结果。现在靠内存计算够快，但记录量上去后需要缓存。

# 附：一句话总结

> **数据链路就是三步：**
>
> **写** —— 页面收集参数 → Service 校验并算数 → **一个事务写两张表** → 广播刷新。
>
> **读** —— 一次全表 + 9 个并行查询 → 内存里算统计 → 赋值给 `@State` → ArkUI 自动重绘。
>
> **刷新** —— `bumpTick()` 递增一个数字 → 7 个页面监听到 → 各自重新查库。
>
> **核心设计只有一条：卡在数据库上的两笔写必须原子，算出来的数字必须可追溯。**
