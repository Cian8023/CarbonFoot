## 一、整体链路（必须能背下来）

### 1.1 录入一条行为，系统内部发生了什么

这是评委最爱问的「讲一下完整链路」。按顺序说这九步：

```
① 用户在录入页选大类、选子类型、输数值
        ↓
② CalculationService.findSub() 查因子库，拿到该子类型的系数与单次上限
        ↓
③ BehaviorService.submit() 统一防御校验
        · 类型存在？  · 数值 > 0 且有限？  · 是否超单次上限？
        ↓
④ 计算减排量：grams = round(value × factor)
        ↓
⑤ 计算积分：points = max(1, floor(grams / 100))
        ↓
⑥ 【开启事务】写 t_behavior_record + 写 t_points_record
        · 任一失败 → rollback 全部回滚
        ↓
⑦ 【提交事务】
        ↓
⑧ 事务外：TaskService.evaluateAll() 判定任务 → BadgeService.checkAll() 检测徽章
        ↓
⑨ 通知全局刷新（bumpTick） + 异步上报家庭同步服务
```

**大白话**  
你输个「骑行 6 公里」，系统先去表里查「骑行每公里算 180 克」，乘出来 1080 克。然后觉得 1080 克该给 10 积分。接下来**在同一个数据库事务里**同时记两笔账：一笔是「你骑了 6 公里」，一笔是「你得了 10 分」。这两笔要么都成功，要么都失败，绝不会出现「记了行为没给分」这种烂账。做完之后再去看看任务有没有达标、徽章有没有解锁。

### 1.2 为什么必须放在同一个事务里

**专业表述**  
行为记录与积分流水构成一对「行为账—积分账」的绑定关系。若分两次独立提交，在写入行为成功、写入积分失败时会出现数据不一致：用户看到记录在列表里，但积分没增加。因此用 `beginTransaction / commit / rollBack` 包住两笔写入，保证原子性。

**大白话**  
就像银行转账，扣你钱和给对方加钱必须一起成，不能扣了你的钱对方没收到。我这里是「记行为」和「给积分」必须一起成。

## 二、五层架构（评委看结构的地方）

### 2.1 分层与依赖方向

```
┌──────────────────────────────────────┐
│ 页面层 pages/     14 个文件           │  10 个路由页 + 5 个内嵌 Tab 视图
├──────────────────────────────────────┤
│ 组件层 components/ 4 个文件           │  图表、选择器、徽章动画、空态
├──────────────────────────────────────┤
│ 服务层 service/   14 个文件           │  业务规则唯一归属地
├──────────────────────────────────────┤
│ 基础设施 common/ 7 + utils/ 3 +       │  主题、常量、偏好、安全存储、
│ network/ 1 + model/ 1                 │  日期/生态/百分比工具、HTTP
├──────────────────────────────────────┤
│ 数据层 db/         2 个文件           │  DBHelper（建表/事务）+ Repository（4 个 Repo）
└──────────────────────────────────────┘
       依赖方向：只允许上层调下层，禁止反向
```

**大白话**  
最上面是界面，最下面是数据库。规矩是「上面能叫下面，下面不能叫上面」。这样改界面不会碰坏算账逻辑，改算账逻辑也不会影响界面。

### 2.2 为什么账务规则只放在服务层

**专业表述**  
页面层只做「收集输入、展示结果」，所有数值上限、时间校验、任务回退规则都下沉到 Service 层。原因是同一业务逻辑有多个入口：手动录入页、AI 识别确认、平台数据导入三条路径最终都调用 `BehaviorService.submit()`。若校验写在页面层，三个入口要各写一遍，必然漏掉一个。

**大白话**  
你记一笔碳有三个入口：手输、拍照识别、从平台导入。如果「不能超过 100 公里」这个限制写在界面里，那得写三遍，早晚漏一处。放到底层统一拦，谁进来都过这道关卡。

## 三、数据层详解

### 3.1 五张表

| 表                   | 存什么      | 关键字段                                                                         | 为什么单独建表             |
| ------------------- | -------- | ---------------------------------------------------------------------------- | ------------------- |
| `t_behavior_record` | 每笔低碳行为   | type / sub_type / value / **factor** / **reduction_g** / created_at / source | 行为账主表               |
| `t_points_record`   | 每笔积分变动   | source / ref_id / action / points / **balance_after**                        | 积分账，可完整追溯余额变化       |
| `t_task`            | 12 个任务定义 | code / period / **check_json** / points                                      | 任务规则可改而不改代码         |
| `t_task_completion` | 任务完成记录   | task_id / completed_at                                                       | **区分「已发过奖」与「还没达标」** |
| `t_badge`           | 9 枚徽章    | code / condition_type / condition_value / unlocked                           | 解锁状态持久化             |

两个索引：`idx_behavior_time`、`idx_points_time`，分别加速按时间区间统计。

**大白话**  
五张表就像五本账。第一本记你干了什么，第二本记你得了多少分，第三本记有哪些任务，第四本记你完成过哪些任务（否则每次打开 App 都重复发奖），第五本记你的徽章。给「时间」加了索引，就像给账本做了日期目录，翻某段时间的记录会快很多。

### 3.2 为什么要单独开 `t_task_completion` 表

**专业表述**  
不能靠「行为记录里有没有符合条件的记录」来判断任务是否已发奖。因为任务发奖后用户可能删除行为记录，此时行为记录消失但积分已发放。所以必须有独立的完成记录表，记录「这个任务在本周期内已经发过奖」，实现幂等发放。

**大白话**  
假设你今天骑够 5 公里拿了 10 分，然后你把那条记录删了。如果系统只看「有没有骑够 5 公里」，就会认为你没完成，你的 10 分就凭空多出来了。所以必须单独记一下「这个任务今天已经发过奖」，不管记录删不删，都认这个记录。

### 3.3 因子快照（一个容易被忽略的设计）

**专业表述**  
`t_behavior_record` 表里同时存了 `factor` 字段。这不是冗余，而是**因子快照**。当因子库后续修订（比如骑行的 180 g/km 调到 170），历史记录重算时仍用录入当时的 180，保证历史数据的减排量不会因为因子更新而凭空变化。

代码位置 `BehaviorService.updateRecord()` 第 127 行：

```typescript
// 用记录内因子快照重算：因子库后续修订或子类型下架不影响历史记录修订
const newG = Math.round(newValue * rec.factor);
```

**大白话**  
你三月份骑车记了 1.08 公斤。到了九月我把「骑行系数」从 180 改成 170。如果你去改三月份那条记录，系统应该还按 180 算，不能变成 1.02 公斤。所以每条记录都把它当时的系数一起存下来。

## 四、核算引擎

### 4.1 因子库结构

`resources/rawfile/factors.json`，四大类共 **19 个子类型**：

| 大类   | 子类型数 | 单位          | 代表系数                                      |
| ---- | ---- | ----------- | ----------------------------------------- |
| 出行   | 7    | km          | 骑行/步行 180、公交 80、地铁 100、拼车 50、新能源 60、私家车 0 |
| 节水节电 | 3    | L / kWh / 次 | 节水 0.3、节电 785、关空调 800                     |
| 旧物回收 | 6    | kg / 件      | 纸类 1300、塑料 600、玻璃 240、衣物 3300、电子 20000    |
| 光盘行动 | 3    | 次           | 早餐 50、午餐 100、晚餐 100                       |

每个子类型带五个元数据字段：`factor`（系数）、`max`（单次上限）、`note`（单位说明）、`basis`（适用条件）、`source`（出处）、`year`（整理年份）。

**大白话**  
这个表就是「换算字典」。你输入的行为和数值，拿这个字典一查就知道该算多少碳。每个条目还配了「这个单位具体指什么」「系数从哪来的」，用户点开详情能看到，不怕你问。

### 4.2 计算与积分折算

```typescript
// 减排量：克 CO₂e
grams = Math.round(value * sub.factor)

// 积分：每 100 克 1 分，不足 100 克按 1 分保底
points = Math.max(1, Math.floor(grams / 100))
```

**为什么最低给 1 分**：光盘行动一餐只有 50~100 克，按 100 克 1 分算会出现 0 分，用户会觉得「记了也没奖励」，挫伤积极性。

**大白话**  
骑车 6 公里 × 180 克 = 1080 克，够 10 个 100 克，给 10 分。但如果你就吃了顿光盘午餐，只有 100 克，也给 1 分，让你至少看到点反馈。

### 4.3 私家车系数为什么是 0

`私家车 factor = 0`。因为本应用记的是「**减排**」，开私家车本身就是基准情景，减排量为 0。保留这个选项是为了让用户完整记录出行方式，但开车不计入减排。

**大白话**  
我算的是「你比别人少排了多少」。你开车是正常排放，不算减排，所以是 0。但你要是拼车，省了一半，那就算 50 克/公里。

## 五、账务一致性（技术含量最高的部分）

这部分是答辩的重点，能讲透说明你真的懂业务。

### 5.1 三条写链路的对称性

| 链路     | 方法               | 事务内做什么                      | 事务外做什么             |
| ------ | ---------------- | --------------------------- | ------------------ |
| **提交** | `submit()`       | 插行为记录 + 发行为积分               | 判任务达标 → 检徽章 → 上报同步 |
| **修改** | `updateRecord()` | 改记录 + 按**差额**补正积分 + 撤销不达标任务 | 重判任务（可能新达标要发奖）     |
| **删除** | `deleteById()`   | 删记录 + **冲减**行为积分 + 撤销不达标任务  | —                  |

**大白话**  
你记一笔、改一笔、删一笔，这三件事都得对称处理。记的时候给分，改的时候按差值补差，删的时候把分收回去。而且改动导致的「任务不再达标」，也得把任务奖励收回来。

### 5.2 修改为什么用「差额」而不是「删了重录」

**专业表述**  
修改时计算 `newPoints - oldPoints` 的差额，只写一笔差额流水。若采用「删除后重新插入」，会在流水里产生「冲减一笔 + 发放一笔」两条冗余记录，用户看积分明细会困惑，且 `ref_id` 关联会断。

代码（`updateRecord` 第 136 行）：

```typescript
const diff = newPoints - oldPoints;
if (diff !== 0) {
  await PointsService.addPointsTx('behavior', id,
    `修改记录：${rec.subType} ${newValue}${rec.unit}，积分${diff > 0 ? '补发' : '扣回'}`, diff);
}
```

**大白话**  
你把 6 公里改成 8 公里，只补 2 公里对应的分，而不是「退 10 分再给 12 分」。这样流水干净，就一条「修改记录，补发 2 分」。

### 5.3 事务边界：一个必须讲清的坑

**专业表述**  
`addPoints()` 自带事务，`addPointsTx()` 不自带。在 `beginTx` 内部只能调 `addPointsTx`，绝不能再调 `addPoints`，否则会嵌套事务导致 `beginTransaction` 报错或提交时机错乱。

同理，`TaskService.evaluateAll()` 内部自己开了事务，所以**不能**在 `BehaviorService` 的 `beginTx` 里调用它。代码里 `submit()` 是先 commit 事务、再调 `evaluateAll()`，就是为了避开这个坑。

**大白话**  
事务就像一把锁。你锁着门的时候不能再锁一次。所以「给积分」有两个版本：一个是「我会自己锁门」（`addPoints`），一个是「你锁好门了我直接用」（`addPointsTx`）。我在事务里只能用后者。

### 5.4 灰盒校验：四项闭合关系

评委如果问「你怎么证明账是对的」，答这个：

| 校验项       | 方法                               | 期望结果 |
| --------- | -------------------------------- | ---- |
| 行为 ↔ 积分对称 | 累加所有行为应得积分，对比流水中 behavior 类积分的总和 | 相等   |
| 积分余额链     | 逐条累加流水增减值，对比每条的 `balance_after`  | 完全吻合 |
| 任务回退      | 删除达标记录后，检查完成记录与积分是否都撤销           | 都撤销  |
| 徽章解锁      | 累计量达阈值后，检查 `unlocked` 状态         | 正确解锁 |

**大白话**  
我想了四个办法自证清白：第一，所有行为的分数加起来，应该等于积分记录里的总数；第二，积分记录每一条都写了「变动后余额」，我从前到后加一遍，应该跟写的一致；第三，删了记录任务分要退回去；第四，够了门槛徽章要亮。

## 六、积分与任务体系

### 6.1 四种积分来源

| source     | 中文   | 触发              |
| ---------- | ---- | --------------- |
| `behavior` | 低碳行为 | 每次录入行为          |
| `task`     | 任务奖励 | 任务达标自动发放        |
| `read`     | 阅读奖励 | 首次读完一篇科普（5 分/篇） |
| `exchange` | 积分兑换 | 兑换碳普惠权益（负数）     |

### 6.2 12 个任务的判定机制

任务是**数据驱动**的，不是硬编码：

```json
{
  "code": "ride_5km",
  "period": "daily",
  "checkJson": "{\"subTypes\":[\"骑行\"],\"target\":5,\"unit\":\"km\",\"matchType\":\"sum\"}"
}
```

`matchType` 有两种：

- `sum`：按数值累加（骑行 5 公里 = 今天所有骑行记录数值之和 ≥ 5）
- `count`：按记录笔数（光盘一次 = 今天有 1 笔光盘记录）

**大白话**  
任务定义写在 JSON 里，不在代码里。想加个新任务，改 JSON 就行，不用重新编译。判断方式有两种：一种是「加起来够不够」，比如骑行总里程到 5 公里；一种是「次数够不够」，比如光盘吃了几顿。

### 6.3 周期重置与幂等

- 日任务：每天 0 点重置判定窗口（`DateUtil.startOfDay`）
- 周任务：每周一 0 点重置（`DateUtil.startOfWeek`）
- 同一任务同一周期只发一次：靠 `t_task_completion` 表 + `completionsBetween()` 判重

**大白话**  
每天零点、每周一零点，任务自动重新开始。同一个任务这轮发过奖了就不会再发，靠第四本账（完成记录）看着。

### 7.2 最大余数法（一个真实踩过的坑）

**现象**：饼图百分比标签出现过合计 99%（51 + 39 + 9）。

**根因**：逐项四舍五入，误差累积。

**解法**：先全部向下取整，算出与 100 的差额，再按小数部分从大到小逐项补 1。

```typescript
// PercentUtil.split()
const f = Math.floor(raw);        // 先向下取整
assigned += f;
const rest = 100 - assigned;      // 算出差额
order.sort((a, b) => fracs[b] - fracs[a]);  // 按小数部分降序
for (let k = 0; k < rest; k++) {
  nums[order[k]] += 1;            // 逐项补 1
}
```

**额外处理**：大于 0 但不足 1% 的项单独标记为 `small`，显示「<1%」，不参与整数份额分配，避免出现「0%但明明有数值」的荒谬显示。

**大白话**  
三个数各占 51.1%、39.5%、9.4%，各自四舍五入变成 51、40、9，加起来 100，没问题。但换成 51.1、39.4、9.5，四舍五入是 51、39、10，加起来还是 100。可中间有些组合会变成 99 或 101，评委一看就觉得你算错了。我的办法是：先全部抹掉小数，看差多少，再按小数大的优先补，保证永远是 100。

### 7.3 首帧性能优化

**问题**：首页四个 Canvas 同时绘制，首帧超 300ms，出现横向撕裂。

**解法**：延迟到进入可视区才首次绘制（代码注释原话：「延迟到进入可视区再首次绘制：首页一次挂多个 Canvas」）。

```typescript
// 可见区触发，避免首帧多 Canvas 抢占
if (!this.painted) { ... }
```

**大白话**  
四个图一起画，手机忙不过来，第一眼会卡一下。改成一屏画一个，滚到哪画到哪，就顺了。

### 7.4 单位统一

**问题**：图内数值在不同量级时自动在 g / kg / t 之间切换，同一张图上出现两种量纲。

**解法**：图内统一用 kg 单一量纲，内部存储仍用克（保证整数精度）。

**大白话**  
同一张图里一会儿写「1080 克」一会儿写「1.08 公斤」，看着乱。统一都写公斤，但后台还是按克存，不丢精度。

## 八、四项创新拓展

### 8.1 E1 家庭多端同步

**技术路线**：应用层 HTTP 同步，不用分布式软总线。

**为什么不用软总线**（评委必问）：

| 障碍   | 说明                       |
| ---- | ------------------------ |
| 设备发现 | QEMU NAT 隔离多播/广播，软总线发现不通 |
| 双实例  | 同机两个模拟器各自独立 NAT，互相看不见    |
| 互信组网 | 同账号互信在模拟器里做不全            |

因此改为：两台设备都连宿主机上的同步服务（`sync/server.js`，端口 8081），各自 POST 上报本机快照，服务端按组号聚合，各自 GET 拉取成员列表。

**三个关键设计点**：

1. **持久化设备标识**：首次启动生成 `dev-xxx` 并存入 preferences，服务端按设备 ID **覆盖**而非新增，保证重复上报不产生重复成员。
2. **录入后立即上报**：不用 `setTimeout` 防抖。早期版本用 800ms 防抖，但应用切后台后定时器被系统冻结，导致「录完就切到另一台设备」时上报永远发不出去。
3. **退出即通知移除**：`leave` 接口 + 清空本地缓存，不留「幽灵组」。

**离线降级**：服务不可达时，已建组的设备继续显示本地缓存的成员数据，页面标记「离线（显示本地缓存）」；建组/加入明确报错，不建幽灵组。

**大白话**  
两台设备要同步，最正统的做法是用鸿蒙的分布式软总线。但模拟器上这条路走不通——两个模拟器互相看不见，也没法建立信任关系。所以我改成两台设备都连我电脑上的一个小服务，各自把数据报上去，再从服务上拉别人的。为什么录完立刻报？因为如果设个延迟，你录完马上切到另一台手机，这个延迟任务在后台会被系统冻住，数据永远发不出去。

### 8.2 E2 AI 视觉识别

**两条识别路径**：

| 路径       | 输入              | 输出                     |
| -------- | --------------- | ---------------------- |
| **票据提取** | 行程单、电费单、外卖单、水费单 | 直接读出里程/用量（数值取自原文，不是推测） |
| **场景候选** | 普通生活照片          | 最多 3 个候选行为 + 置信度       |

**批量能力**：单次最多选 9 张，串行识别，逐张反馈进度（避免用户以为卡死），汇总成一张确认卡。

**四条设计约束**：

1. **最多 9 张**：相册一次选 9 张，串行识别约 40~50 秒
2. **进度可见**：显示「正在识别 n/N」
3. **结果需确认**：汇总卡片，每条可改可删，点「全部录入」才写库
4. **失败不编造**：区分四类失败原因（未配置 / 密钥无效 / 网络异常 / 无法解析），提供「重试」与「去手动录入」出口

**技术细节**：图片转 Base64 → 调 OpenAI 兼容的视觉接口（默认 deepseek-flash，也支持 glm-4v-flash、qwen-vl-max）→ 用 `json_object` 约束输出格式降低解析失败率 → 网络抖动或 5xx 自动重试一次。

**大白话**  
不想手输就拍照。拍一张行程单，它能直接读出「12.6 公里」这个数字——注意是读出来的，不是猜的。拍一张生活照，它可能给你三个猜测，让你自己点。识别结果不会自动入库，必须你点确认。识别失败了会告诉你为什么失败，不会瞎编一个数糊弄你。


### 8.3 E3 碳普惠平台对接

**接口适配器模式**：`PlatformSourceService` 定义了数据源适配器接口，当前只有 HTTP 实现（对接本地 `mock/server.js`）。

**五种接口**：

- `GET /api/benefits` 权益列表
- `POST /api/exchange` 兑换（服务端库存真实递减）
- `GET /api/orders` 兑换流水
- `GET /api/behavior` 平台行程数据（供导入）
- `GET /api/health` 健康检查

**降级策略**：地址为空/不可达/返回异常时，自动降级为「内置模拟池」（`InclusiveService.mockBenefits()`）。两种模式下扣积分、写流水、权益入库的本地记账逻辑完全一致，区别只在权益数据来源。

**如何区分**：权益 id 前缀是 `bus_2`（远端）还是 `mock_bus`（降级）。

**大白话**  
碳普惠是真实世界的碳积分体系。我给它留了对接接口，本地写了个模拟服务。真连上了，你看到的是「公交券」这种真实权益；没连上，我看到的是「内置模拟权益」，功能照样能走完，只是数据是假的。怎么看连没连上？看权益编号是不是 `mock_` 开头。

### 8.4 E4 智能服务

**两个能力**：

1. **任务推荐**：`RecommendService` 统计近 14 天各子类型的频次与减排量，用规则引擎推荐「你最可能完成的任务」，并给出理由（如「你最近 7 天骑行了 3 次，完成「每日骑行 5 公里」只差 2 公里」）。
2. **年度报告**：`AnnualReport` 页汇总全年数据——总减排量、分类占比、最高单日、连续天数、里程碑时间轴。

**另外还有桌面卡片**：`EntryFormAbility` + `WidgetCard.ets`，2×2 卡片直接显示今日减排与目标进度。

**大白话**  
它会读你的历史数据，猜你明天最可能做什么，然后推荐对应的任务——不是随机推，是「你上周骑了三次车，再骑两公里就能拿奖」这种。另外做了个桌面小卡片，不用打开 App 就能看到今天减排了多少。

## 十二、老师可能提的问题（含参考答案）

### Q1：为什么不用关系型数据库的联表查询，全部在代码里 JOIN？

**答**：鸿蒙 RDB 支持 JOIN，但本项目数据量小（单用户，日均几十条），跨表查询主要在统计页，用代码聚合比写复杂 SQL 更易读易改。另外 `StatsService` 需要先查记录再按周/月分组，SQL 的 `strftime` 分组在跨年周计算上不如 `DateUtil.startOfWeek()` 可控。

**大白话**：数据量不大，几百条记录，代码里算比写 SQL 清楚。而且「每周从周一算起」这件事，用 SQL 写很别扭，代码里算更准。

### Q2：事务是怎么保证的？会不会有并发问题？

**答**：用 RDB 的 `beginTransaction / commit / rollBack`。并发方面，鸿蒙应用是单进程单线程 UI 模型，写操作由用户交互串行触发，不存在真正的并发写。`addPointsTx` 内部读 `lastBalance()` 再算新余额，在事务内保证了读写一致。

**大白话**：这个 App 只有一个用户，你不可能同时点两次提交，所以不存在并发。事务的主要作用是「要么全成要么全败」，防止写入一半崩了。

### Q3：AI 识别失败的兜底逻辑是什么？

**答**：四类失败分别处理——未配置 Key 提示去设置、密钥无效提示重新填写、网络异常提供重试、无法解析提示改手动录入。所有失败**都不编造数据**，`fail()` 方法统一返回 `ok: false`。另外代码里提到「端侧特征识别」兜底，保证路演无网络也能演示。

**大白话**：识别失败就明说失败，告诉你为什么，不会瞎猜一个数糊弄。

### Q4：多端同步为什么不用分布式软总线？

**答**：见 8.1。三条硬性障碍：QEMU NAT 隔离多播、双实例独立 NAT、同账号互信在模拟器不可用。所以改用应用层 HTTP 中转。这是环境约束下的工程选择，不是能力不足。

**大白话**：不是不知道正统做法，是模拟器上确实走不通。评委要是能用两台真机现场试，这条路是通的。

### Q5：积分体系为什么每 100 克 1 分？这个比例怎么定的？

**答**：参考了国内碳普惠平台的常见兑换比例（如深圳「碳普惠」、蚂蚁森林的能量值），结合本应用的行为量级测算。日均减排 2~~3 kg 对应 20~~30 分，一个月约 600~900 分，与「兑换一张公交券需 100 分」的设定匹配，保证一周能换到实物激励。

**大白话**：算过账的。你一天骑车节能减 2 公斤碳，得 20 分，一周 140 分能换张公交券。如果比例太高，一周只能换 1 分，没人有动力。

### Q6：这个项目里 AI 帮你做了多少？

**必须如实答**：AI 用于代码提示、文案润色、UI 素材生成等辅助环节。业务架构、数据模型、账务一致性规则、因子库取值、测试用例设计由本人完成并逐项验证。每个模块我都能讲清实现细节（然后当场演示讲某一模块的代码）。

**大白话**：AI 帮我写了不少代码，但「这个 App 该怎么设计、账怎么算、数据怎么存」是我自己想的。你随便指一个文件，我能给你讲这一行在干什么。

### Q7：如果用户疯狂刷记录，积分会不会暴涨？

**答**：三层防御——① 单次录入上限（每个子类型有 `max` 字段，如骑行最多 100 km）；② 未来时间拦截（`newTs > Date.now()` 直接抛错）；③ 数值必须是有限正数（`isFinite && > 0`）。三层校验都在 `BehaviorService`，三个入口（手输 / AI / 平台导入）都绕不过。

**大白话**：你输「骑行 9999 公里」会被拦，说「最多 100 公里」。你把时间改成明天也会被拦。这三个检查写在最底层，从哪条路进来都得过。

### Q8：因子数据的来源是什么？可靠吗？ 

**答**：公开核算资料整理，版本 2026.11。**明确标注为非官方认证口径**，不用于碳交易、碳核查或合规申报。每个子类型带 `source` 和 `year` 字段，详情页可见。这是诚实的设计——赛道要求的是「减排指南」，不是「碳核查工具」。

**大白话**：系数是从公开资料整理的，不是官方认证的。界面上写得很清楚「这是估算值，不能拿去碳交易」。不吹牛，反而更可信。

### Q9：为什么首页四个图表要分 Tab 而不是并排？

**答**：屏幕宽度有限（1440 px），并排会导致每个图宽度不足 300 px，柱状图的分组标签会挤在一起无法阅读。分 Tab 后每个图独占全宽，可读性优先。

**大白话**：手机屏幕就那么宽，四个图挤一排每个都看不清。分开放，一个图占满宽度，看着舒服。

### Q10：桌面卡片是怎么实现数据更新的？

**答**：`EntryFormAbility` 通过 `CardSnapshot` 把首页数据序列化写 preferences，卡片渲染时读快照。数据变化时 `bumpTick()` 触发，卡片在下次刷新周期读取新快照。

**大白话**：卡片不直接读数据库，读的是一份「快照」。App 里数据一变就把快照更新，卡片下次刷新就能看到新的。
