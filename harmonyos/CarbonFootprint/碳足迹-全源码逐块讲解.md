# 一、启动与初始化（3 个文件）

## 1.1 `entryability/EntryAbility.ets`（31 行）

**这是整个 App 的入口。系统拉起应用时，第一个执行的就是它。**

| 代码块                                 | 行       | 干什么                                                           | 对应 App 操作  |
| ----------------------------------- | ------- | ------------------------------------------------------------- | ---------- |
| `onCreate()`                        | 8       | 调用 `AppInit.bootstrap(this.context)`，把「应用上下文」存起来，并初始化 3 个全局变量 | 点了图标、进程被创建 |
| `onWindowStageCreate()`             | 15      | `windowStage.loadContent('pages/Index')` —— 加载首页              | 首页开始绘制     |
| `onForeground()` / `onBackground()` | 26 / 29 | 空实现，留作钩子                                                      | 切到后台/切回前台  |

**为什么 `onCreate` 里只存 context 不做数据库初始化？**  
数据库初始化是异步的，会阻塞启动。这里只「记下环境」，真正的加载放到首页去 `await`，用户可以更快看到界面骨架。

**一句话**：`EntryAbility` 是「开门的人」，它不干活，只把门打开、把钥匙交给 `AppInit`。

**`ensure()` 的四步**：

```
DBHelper.init(ctx)        → 建表、建索引、补列
SeedService.seed(ctx)     → 灌入 12 个任务 + 9 枚徽章
CalculationService.init() → 加载 factors.json（19 个因子）
KnowledgeService.init()   → 加载 knowledge.json（16 篇文章）
```

**关键设计：`initPromise` 缓存**

```typescript
if (AppInit.initPromise === null) {
  AppInit.initPromise = (async () => {...})();
}
return AppInit.initPromise;
```

**为什么重要**：5 个 Tab 会同时 `aboutToAppear`，如果没这层缓存，会同时发起 5 次「建表 + 读 JSON」。有了缓存，第 2~5 次直接拿到同一个 Promise，等第一次完成即可。**这是幂等初始化**。

**对应操作**：打开 App 后第一次进任何页面时，这段代码在后台跑；之后再进页面，瞬间返回。

### 两个容易被追问的点

**① `factor` 为什么存在 `BehaviorRecord` 里？**

这是**因子快照**。`t_behavior_record` 表除了存 `reductionG`（算好的结果），还存了 `factor`（当时的系数）。

```
2026-03 录入：骑行 6km × 180 g/km = 1080 g
2026-11 因子库改成 170 g/km
历史详情页显示的是：6km × 180 g/km = 1.08 kg   ← 用快照，不改写
```

**如果没有这个字段**，历史记录会被新因子「追溯改写」，用户三月的账目会莫名其妙变少。

**② `SRC_*` 四个常量（41-44 行）**


### 代码块 2：`ensureColumn()`（81-102 行）★ 高频追问点

```typescript
private static async ensureColumn(store, table, column, ddl): Promise<boolean> {
  const rs = await store.querySql(`PRAGMA table_info(${table})`);
  // 遍历已有列名，命中则直接返回 true
  await store.executeSql(`ALTER TABLE ${table} ADD COLUMN ${column} ${ddl}`);
}
```

**解决什么问题**：

```sql
CREATE TABLE IF NOT EXISTS t_behavior_record (...)
```

**这句 SQL 对已存在的表完全无效**——它不会加新列。老用户升级 App 后，新加的 `source` 列永远不存在，所有带 `source` 的查询都会崩。

**所以要用 `PRAGMA table_info` 先查列，缺了才 `ALTER TABLE ADD COLUMN`。**

**失败也不阻断启动**：返回 `false`，写入时不带该列，读取时兜底成 `manual`。**降级而不是崩溃**。

**对应操作**：老用户从旧版升级后第一次打开 App 时，这段在后台跑。

### 代码块 3：事务三件套（111-121 行）★ 必讲

```typescript
static beginTx(): void { DBHelper.store.beginTransaction(); }
static commitTx(): void { DBHelper.store.commit(); }
static rollbackTx(): void { DBHelper.store.rollBack(); }
```

**为什么单独封三个方法**：

1. 统一入口，避免各处自己 `get().beginTransaction()`
2. `rollBack()` 的 **B 是大写**（鸿蒙 API 就这么拼），封装后调用方不用记这个坑
3. 配合 `BehaviorService` 形成固定的「begin → try → commit / catch → rollback」结构

**对应操作**：只有在「提交一条行为记录」时才用到，见 3.3。

# 三、核算与账务（3 个文件，核心中的核心）

## 3.1 `service/CalculationService.ets`（约 80 行）

**「因子库」的管家 + 两个纯计算函数。**

### 代码块 1：`init()`（25-32 行）

```typescript
const data = context.resourceManager.getRawFileContentSync('factors.json');
const file = JSON.parse(decode(data)) as FactorsFile;
CalculationService.categories = file.categories;
```

从 `resources/rawfile/factors.json` 读因子库，解析成内存数组。

**为什么放 rawfile 而不是数据库**：因子库是**只读的编译期资源**，不入库。改因子要重新发版，这样能保证「同一版本内因子恒定」。

**对应操作**：App 启动时执行一次。

### 代码块 2：`findSub()`（42-54 行）

```typescript
static findSub(type, subType): SubType | null {
  for (const cat of categories) {
    if (cat.name !== type) continue;
    for (const sub of cat.subTypes) {
      if (sub.name === subType) return sub;
    }
  }
  return null;
}
```

**双重循环查找**：先按大类找，再按子类型找。

**返回 `null` 表示「不存在」**——这是校验的第一道关。

**对应操作**：用户在录入页选完类型、还没输数值时就已经在用了（显示单位、上限、说明）。

### 代码块 3：`calculate()`（62-69 行）★ 你举的例子

```typescript
static calculate(type, subType, value): number {
  const sub = CalculationService.findSub(type, subType);
  if (sub === null || !isFinite(value) || value <= 0) {
    return 0;
  }
  return Math.round(value * sub.factor);
}
```

**逐行拆**：

| 行 | 代码                               | 含义                    |
| - | -------------------------------- | --------------------- |
| 1 | `findSub(...)`                   | 查这个子类型的定义             |
| 2 | `sub === null`                   | 类型不存在 → 返回 0（不抛错）     |
| 2 | `!isFinite(value)`               | 拦掉 `NaN` 和 `Infinity` |
| 2 | `value <= 0`                     | 拦掉 0 和负数              |
| 4 | `Math.round(value * sub.factor)` | **核心公式：数值 × 系数，四舍五入** |

**关键点 1：返回 0 而不是抛异常**  
这&#x662F;**「保守取值」**。调用方拿到 0 就知道「算不出来」，可以决定是提示还是跳过。抛异常会让调用链断掉。


**关键点 2：`isFinite` 一个函数拦两种坏值**
`NaN` 的典型来源：`parseFloat('abc')`。`Infinity` 的来源：除零或超大数。这两个都能通过 `typeof === 'number'` 的检查，所以必须用 `isFinite`。

**关键点 3：`Math.round` 而不是 `floor`**
`floor` 会系统性偏小。骑马 0.6 km × 180 = 108 g，`floor` 得 108、`round` 也是 108，但 `0.9 km × 60 = 54 g` 时 `round` 更接近真值。**避免所有记录都少算一点**。

**举例（答辩时可以现场算）**：

```
骑行 6 km，因子 180 g/km
  → 6 × 180 = 1080 g
  → 1080 / 1000 = 1.08 kg
```

**对应 App 操作**：录入页输入数字的瞬间，下方「预计减排 1.08 kg」就是它算的。

### 代码块 4：`valueToPoints()`（71-76 行）

```typescript
static valueToPoints(grams: number): number {
  if (grams <= 0) return 0;
  return Math.max(Constants.POINTS_PER_100G,
                  Math.floor(grams / (100 / Constants.POINTS_PER_100G)));
}
```

代入 `POINTS_PER_100G = 1`，实际就是：

```typescript
Math.max(1, Math.floor(grams / 100))
```

**规则：每 100 克减排 = 1 积分，但最少给 1 分。**

**为什么要 `Math.max(1, ...)` 兜底**：
光盘一餐 50~100 克，`floor(50/100) = 0`。用户认真记录了一条行为，结果 0 分，会产生「记了也白记」的挫败感。**保底 1 分是产品决策，不是技术必需。**

**对应 App 操作**：录入页「预计获得 10 积分」、提交后弹窗「+10 积分」。

### 为什么有两个版本：`addPointsTx` 和 `addPoints` ★ 必讲

```typescript
// 版本 A：调用方已开事务
static addPointsTx(...) { /* 直接插入，不 begin */ }

// 版本 B：自己开事务
static async addPoints(...) {
  DBHelper.beginTx();
  try { ...; DBHelper.commitTx(); }
  catch (e) { DBHelper.rollbackTx(); throw e; }
}
```

**鸿蒙 RDB 不支持事务嵌套。** 如果 `BehaviorService` 里已经 `beginTx()`，再调 `addPoints()` 就会在事务里再开事务，直接报错。

**所以规则是**：

| 场景 | 用哪个 |
|---|---|
| 已在事务内（提交行为记录） | `addPointsTx` |
| 独立加分（读文章、任务达标） | `addPoints` |

**对应 App 操作**：
- 提交行为记录 → 走 `addPointsTx`（和记录同一个事务）
- 读完一篇科普文章 → 走 `addPoints`（独立加分）

**这是「链式余额」**：每笔流水存下「变完之后是多少」。查余额不用 `SUM`，取最后一条即可。

#### 事务边界（43-56 行）★ 必讲

```typescript
DBHelper.beginTx();
try {
  const id = BehaviorRepo.insertSync(record);      // 写 t_behavior_record
  record.id = id;
  if (points > 0) {
    await PointsService.addPointsTx('behavior', id, ..., points);  // 写 t_points_record
  }
  DBHelper.commitTx();
} catch (e) {
  DBHelper.rollbackTx();
  throw e as Error;
}
```

**为什么两笔写必须同一事务**：

```
行为和积分是一对绑定账。
分两次写 → 可能「记录在列表里，但积分没加」
        → 用户看到的账是错的，且无法自愈
```

**类比**：银行转账，扣你 100 和给对方加 100 必须一起成功。中途断电，两边都不能变。

**`if (points > 0)` 的用意**：避免写「0 分」的垃圾流水。什么时候会 0 分？`grams` 极小时（节水 0.001 升 × 0.3 = 0.0003 g，round 成 0）。

#### 事务外两步（58-67 行）

```typescript
const newBadges: string[] = [];
try {
  await TaskService.evaluateAll();       // 判 12 个任务
  const badges = await BadgeService.checkAll();  // 检 9 枚徽章
  for (const b of badges) newBadges.push(b);
} finally {
  bumpTick();
}
```

**三个设计要点**：

**① 顺序不能颠倒**
「任务达人」徽章的判定条件是 `tasks_done >= 10`，依赖 `t_task_completion` 表。任务刚完成，徽章才可能解锁。所以必须先 `evaluateAll` 再 `checkAll`。

**② 必须放事务外**
`evaluateAll()` 内部自己 `beginTx`。放进来就是嵌套事务，鸿蒙不支持。

**③ 用 `try-finally` 而不是 `try-catch`**（第 68 行）
这是修过的缺陷（DF-50）：事务已提交，数据确定落库。如果 `evaluateAll` 抛异常，不能让 `bumpTick` 被跳过——否则数据改了但界面不刷新，用户以为保存失败。

**对应 App 操作**：点「提交」后，如果解锁了徽章，会弹出徽章动画；这个动画的数据就来自 `newBadges`。

#### 最后两步（68-71 行）

```typescript

}
SyncService.scheduleReport();     // 异步推给家庭组（不 await）
```

**`bumpTick()` 是全局广播**，7 个页面监听 `tick` 变量。一次写操作，7 处同时刷新。

**`scheduleReport()` 不 await**：同步是「锦上添花」，失败不该影响本地录入。这是**降级设计**。

### `deleteById()`（81-105 行）

**删除一条记录时，要做三件事，全在一个事务里**：

```
① 删 t_behavior_record 那条
② 冲减对应的积分（写一条负数流水）
③ 撤销该记录参与的任务完成记录（deleteCompletionsBetween）
```

**为什么第 ③ 步重要**：假设「每日骑行 5km」任务是因为这条 6km 记录达标的。删掉它之后，本周实际只骑了 2km，任务不该算完成。所以要把 `t_task_completion` 里那条删掉，否则积分白拿了。

### `updateRecord()`（121-170 行）

**改数值时，做的是「差额补正」而不是「重算」**：

```typescript

const newPoints = valueToPoints(newG);            // 新的积分
```

| **差额补正** | **+5（一条，清晰）** |

## 5.2 `utils/PercentUtil.ets`（约 75 行）★ 极易被追问

**解决「百分比加起来不等于 100」的问题。**

| 方法 | 行 | 干什么 |
|---|---|---|
| `split(values)` | 20 | 把一组数值转成百分比数组，**保证合计恰好 100** |
| `text(values)` | 61 | 转成 `['51%', '39%', '10%']` |

### 问题复现

```
三个值：1/3, 1/3, 1/3
各自 × 100 = 33.33
四舍五入 = 33 + 33 + 33 = 99    ← 少了 1
```

**饼图上就会出现「51% + 39% + 9% = 99%」，用户一眼看出错了。**

### 最大余数法（Hamilton 法）四步

| 步 | 操作 | 为什么这么做 |
|---|---|---|
| ① | 全部 `Math.floor`（向下取整） | 保证总和 ≤ 100，差额一定非负 |
| ② | 算 `100 - 已分配之和` | 得到还要补几个 1 |
| ③ | 按「小数部分」从大到小排序 | 被砍得最多的优先补回来 |
| ④ | 前 `rest` 项各补 1 | 补齐到恰好 100 |

**举例**：

```
原始比例：33.4, 33.3, 33.3
① floor  → 33, 33, 33  （和=99，差 1）
② 差额   → 1
③ 小数排序 → 33.4 (0.4) > 33.3 (0.3) = 33.3 (0.3)
④ 补 1    → 34, 33, 33  （和=100 ✓）
```

**答辩加分点**：这套算法叫**最大余数法（Hamilton 法）**，是美国宪法规定的众议院席位分配方法。被问「你怎么想到的」有得答。

**对应 App 操作**：首页饼图和历史页条形图上的百分比标签。

```typescript
}
```

**解决什么问题**：

|---|---|---|

```typescript
static scheduleReport(): void {
  if (SyncService.reporting) {
    SyncService.pendingReport = true;   // 正在报 → 标记「待补」
```

```
注意：不能用 setTimeout 做延迟合并——应用切到后台后定时器会被冻结，
```

### `mergedStats()` 的去重（370-405 行）★ 必讲

```typescript
}
total += myLocalG;
```

**为什么要跳过自己**：服务器返回的列表**包含你自己**。不去重的话：

### `refresh()` 的并发保护（59-98 行）★ 修过的缺陷

```typescript
const seq = ++this.refreshSeq;    // 领号
...
const rows = await BehaviorRepo.query(...);
if (seq !== this.refreshSeq) {
  return;                          // 已过号，本次结果作废
}
this.rawRecords = rows;
```

**解决什么问题**：`refresh()` 是 async，`@Watch` 触发时不等待。连续两次修改会产生两个并发查询，**先发出的慢查询如果后返回，就会用旧数据覆盖新数据**。

**对应 App 操作**：快速连续改两次数值，最终显示的一定是最后一次的结果，不会闪回旧值。

### `buildGroups()` 分组（114-129 行）

```
① 遍历所有记录
② 用 startOfDay(createdAt) 算出「属于哪一天」
③ 用 Map 按天聚合
④ 转成数组，按时间倒序
```

**对应 App 操作**：历史页的「今天」「昨天」「11-11」分隔标题。

### `detailSheet()` 里的积分展示（190-390 行）

```typescript
const flows = await PointsService.listBySourceRef('behavior', rec.id);
// 把这条记录的所有关联流水加起来
let net = 0;
for (const f of flows) net += f.points;
```

**显示成「本笔积分：净 1 分（含冲减 153 分）」**。

**为什么是这个格式**：如果记录被改过多次，会有多条流水。直接显示「+15」是错的（那是第一次发的），显示「净 X 分」才是真实结果。

# 附：三个最容易讲错的点

**① `week8` / `month12` 这两个名字骗人**

类型名叫「8 周」「12 月」，实际是 **4 周** 和 **6 月**。常量名没跟着改。
**答「近 4 周」「近 6 月」，别说 8 和 12。**

**② `Settings.ets` 里装的是「我的」**

```
Settings.ets        → MineView   （底部第 5 个 Tab「我的」）
SettingsDetail.ets  → 设置详情   （从「我的」点进去的路由页）
```
**问「设置的代码在哪」，答 `SettingsDetail.ets`。**

**③ 首页 `HomeView` 没有独立文件**

它在 `Index.ets` 第 85 行。**别去找 `Home.ets`，不存在。**
