## 1. model/Models.ets

**解决什么问题**：全工程跨层传递的数据结构统一定义。改一个字段名，编译器会告诉你哪些地方要跟着改。

### 1.1 因子元数据：SubType 里的五个说明字段

```typescript
export interface SubType {
  name: string;
  unit: string;
  factor: number;      // 每单位减排量（克 CO₂e）
  max: number;         // 单次录入上限
  note?: string;       // 这个计量单位具体指什么
  basis?: string;      // 适用条件与计算边界
  source?: string;     // 系数出处说明
  year?: number;       // 系数整理年份
}
```

**为什么带 `note/basis/source/year`**：这是「算法透明」的落地。详情页要展示四行说明（计算式、口径、出处、免责），这四个字段就是数据来源。如果只存 `factor`，界面上就只能显示一个孤零零的数字。

**答辩可能问**：*"为什么 `max` 存在因子库里，不写在代码里？"*
→ 因为上限与因子是同一件事的两面（每公里 180 克，最多 100 公里）。放在一起，改系数时上下限同一处调整，不会漏。

### 1.2 行为记录：为什么存 factor 和 reductionG

```typescript
export interface BehaviorRecord {
  id: number;
  type: string;
  subType: string;
  value: number;       // 用户输入的原始数值
  unit: string;
  factor: number;      // ★ 录入当时的因子快照
  reductionG: number;  // ★ 录入时算好的减排量
  createdAt: number;
  note: string;
  source: string;      // manual / ai_ticket / ai_scene / platform
}
```

**`factor` 是快照，不是关联**。如果只存 `subType`，展示时再去因子库查，那因子库一改，历史记录全变。存快照后，历史数据永远反映「录入那一刻的算法」。

**`reductionG` 同样冗余存**。为什么不每次用 `value × factor` 现算？两个原因：
- 统计聚合时不需要跑计算逻辑，直接 `SUM(reduction_g)` 更快
- 若将来计算规则调整（比如加分段系数），历史数据不受影响

**答辩可能问**：*"这不是冗余存储吗？违反范式了吧？"*
→ 这是**有意的反范式**，业界叫「快照冗余」。和订单表存商品当时的价格是同一个道理——订单不能因为商品改价而变金额。

### 1.3 数据来源四常量

```typescript
export const SRC_MANUAL: string = 'manual';
export const SRC_AI_TICKET: string = 'ai_ticket';
export const SRC_AI_SCENE: string = 'ai_scene';
export const SRC_PLATFORM: string = 'platform';
```

用常量而非直接写字符串，是为了避免「手输 maunal」这种拼写错误导致筛选失效。TypeScript 的字符串类型无法穷举检查，靠常量集中管理是次优但实用的做法。

## 2. db/DBHelper.ets

**解决什么问题**：把「数据库连接、建表、事务」三件事收口到一个地方。业务代码永远不直接摸 `relationalStore`。

### 2.1 五张表的 DDL

```typescript
const DDL: string[] = [
  `CREATE TABLE IF NOT EXISTS t_behavior_record (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    type TEXT NOT NULL,
    sub_type TEXT NOT NULL,
    value REAL NOT NULL,
    unit TEXT NOT NULL,
    factor REAL NOT NULL,
    reduction_g INTEGER NOT NULL,
    created_at INTEGER NOT NULL,
    note TEXT,
    source TEXT DEFAULT 'manual'
  )`,
  // ... 其余四张表
  `CREATE INDEX IF NOT EXISTS idx_behavior_time ON t_behavior_record (created_at)`,
  `CREATE INDEX IF NOT EXISTS idx_points_time ON t_points_record (created_at)`
];
```

**逐行要点**：
- `AUTOINCREMENT`：主键自增，但注意——删除记录后 id 不复用。这对 `ref_id` 关联很重要：积分流水的 `ref_id` 指向行为记录 id，如果 id 复用会造成串号。
- `reduction_g INTEGER`：减排量用整数克存，不用 REAL。避免浮点误差累积（1000 条 0.1 克的记录，REAL 相加会得到 99.99999 而不是 100）。
- `source TEXT DEFAULT 'manual'`：给默认值是为了兼容老数据——老版本数据库没有这一列，补列后已有记录自动填 `manual`。
- 两个索引建在 `created_at` 上，因为几乎所有查询都是「某时间区间内的记录」。

**答辩可能问**：*"为什么不存 timestamp 为 TEXT？"*
→ 整数比较比字符串比较快，且范围查询（`BETWEEN`）在整数上没有格式依赖。UUID 式字符串还要考虑时区。

### 2.2 幂等补列迁移（真实升级场景）

```typescript
static async init(context: common.Context): Promise<void> {
  const config: relationalStore.StoreConfig = {
    name: DB_NAME,
    securityLevel: relationalStore.SecurityLevel.S1
  };
  DBHelper.store = await relationalStore.getRdbStore(context, config);
  for (const sql of DDL) {
    await DBHelper.store.executeSql(sql);
  }
  // 老库迁移：CREATE TABLE IF NOT EXISTS 不会给已存在的表加列
  DBHelper.sourceReady = await DBHelper.ensureColumn(DBHelper.store, 't_behavior_record',
    'source', "TEXT DEFAULT 'manual'");
  if (DBHelper.store.version === 0) {
    DBHelper.store.version = 1;
  }
}
```

**这是本项目一个真实的坑**：v1 版本的数据库没有 `source` 列。用户在旧版本装过 App，升级到新版本时，`CREATE TABLE IF NOT EXISTS` 发现表已存在，**直接跳过**，`source` 列永远加不上。后续所有查询都会因为「找不到列」而失败。

```typescript
private static async ensureColumn(store: relationalStore.RdbStore, table: string,
  column: string, ddl: string): Promise<boolean> {
  try {
    // PRAGMA table_info 是 SQLite 查表结构的命令，返回每列的 name/type/...
    const rs = await store.querySql(`PRAGMA table_info(${table})`);
    let exists = false;
    while (rs.goToNextRow()) {
      const name = rs.getString(rs.getColumnIndex('name'));
      if (name === column) {
        exists = true;
        break;
      }
    }
    rs.close();
    if (!exists) {
      await store.executeSql(`ALTER TABLE ${table} ADD COLUMN ${column} ${ddl}`);
    }
    return true;
  } catch (e) {
    // 迁移失败不阻断启动；写库时不带该列，读取按 manual 兜底
    return false;
  }
}
```

**三处设计考量**：
1. **先查再加**，而不是盲目 `ALTER TABLE`。SQLite 的 `ALTER TABLE ADD COLUMN` 在列已存在时会报错，直接执行会中断启动。
2. **失败不抛异常**，只返回 `false`。返回的布尔值存到 `DBHelper.sourceReady`，`Repository.bucket()` 据此决定写入时是否带 `source` 列。整个链路形成「优雅降级」：最坏情况是来源信息丢失，但 App 能用。
3. **`return true` 而不是 `return exists`**。因为 `ALTER` 执行成功后，列一定存在。如果返回 `exists`（此时是 false），就会永远认为列不可用。

**答辩追问**：*"如果 ALTER 失败怎么办？"*
→ 返回 false，`sourceReady` 为 false，`bucket()` 不写 source 列，读取时 `rowToBehavior()` 的 try-catch 兜底成 `manual`。功能不受影响，只是所有记录都显示为"手动录入"。

### 2.3 事务三件套

```typescript
static beginTx(): void  { DBHelper.get().beginTransaction(); }
static commitTx(): void { DBHelper.get().commit(); }
static rollbackTx(): void { DBHelper.get().rollBack(); }
```

**注意 `rollBack` 首字母大写 B**。鸿蒙 API 的拼写就是 `rollBack`，写成 `rollback` 会报方法不存在。这是踩过的坑。

**为什么用同步方法**：事务切换是本地操作，没有 IO 等待，用同步避免「开事务后代码继续跑、异步事务还没生效」的时序问题。

## 3. db/Repository.ets

**解决什么问题**：把所有 SQL 收口到 4 个 Repo 类，业务层只调方法名，不写 SQL。全文件 559 行，是最大的基础设施文件。

### 3.1 行转对象的容错处理

```typescript
function rowToBehavior(rs: relationalStore.ResultSet): BehaviorRecord {
  const noteVal: string = rs.getString(rs.getColumnIndex('note'));
  let src = 'manual';
  try {
    const idx = rs.getColumnIndex('source');
    if (idx >= 0) {
      const v = rs.getString(idx);
      if (v !== null && v !== undefined && v !== '') {
        src = v;
      }
    }
  } catch (e) {
    src = 'manual';
  }
  // ...
}
```

**为什么要 try-catch**：如果数据库是旧版本、`source` 列没补上，`getColumnIndex('source')` 会抛错。这里用 catch 兜底成 `manual`，保证读取不中断。

**`noteVal ? noteVal : ''`**：SQLite 的 TEXT 列允许 NULL，直接赋给 `string` 类型会得到 `null`，导致后续 `.length` 崩。这里做空值归一。

### 3.2 bucket：写入时按列可用性裁剪

```typescript
static bucket(r: BehaviorRecord): relationalStore.ValuesBucket {
  const bucket: relationalStore.ValuesBucket = {
    'type': r.type,
    'sub_type': r.subType,
    'value': r.value,
    'unit': r.unit,
    'factor': r.factor,
    'reduction_g': r.reductionG,
    'created_at': r.createdAt,
    'note': r.note
  };
  if (DBHelper.sourceReady) {
    bucket['source'] = (r.source === undefined || r.source === null || r.source === '') ? 'manual' : r.source;
  }
  return bucket;
}
```

**这是 2.2 里降级策略的落地点**。如果 `source` 列不可用就不写——写了会因「字段不存在」插入失败。同时把空值归一成 `manual`，避免数据库里出现空字符串。

### 3.3 insertWithIdSync：恢复时保留原始 id

```typescript
/** 导入恢复用：保留原始 id 插入，保证积分流水 ref_id 引用不断链 */
static insertWithIdSync(r: BehaviorRecord): void {
  const bucket: relationalStore.ValuesBucket = {
    'id': r.id,   // ★ 手动指定 id，而不是自增
    'type': r.type,
    // ...
  };
  DBHelper.get().insertSync('t_behavior_record', bucket);
}
```

**为什么单独写一个方法**：正常插入让数据库自增 id。但**从备份恢复**时必须保留原 id，否则 `t_points_record.ref_id` 指向的旧 id 在新库里不存在，积分流水的关联就断了。

**答辩可能问**：*"保留 id 会不会和已有记录冲突？"*
→ 恢复流程是「先清空全表，再导入」，所以不会冲突。代码在 `ExportService.restoreJson()` 里，清空在前。

### 3.4 lastBalance：余额从流水推导

```typescript
/** 最新余额 = 最近一笔流水的 balance_after */
static async lastBalance(): Promise<number> {
  const pred = new relationalStore.RdbPredicates('t_points_record');
  pred.limitAs(1).orderByDesc('id');
  const rs = await DBHelper.get().query(pred);
  let balance = 0;
  if (rs.goToNextRow()) {
    balance = rs.getLong(rs.getColumnIndex('balance_after'));
  }
  rs.close();
  return balance;
}
```

**注意**：余额不存在独立字段里，而是「查最后一条流水的 `balance_after`」。这是**事件溯源（Event Sourcing）**的简化版——账本只看流水，余额是流水的推导结果。

**好处**：不可能出现「余额字段和流水对不上」的情况，因为余额本身就是流水算出来的。
**代价**：每次查余额要读一次数据库。数据量小（几千条）可接受。

**答辩追问**：*"为什么不单独存一个余额字段？"*
→ 存了就有两个真相来源，改一个忘改另一个就出 bug。本项目曾出现过「删记录后余额没退」的缺陷（DF 台账里有），根因就是那时候余额是独立维护的。改成从流水推导后这类问题根除。

### 3.5 completionsBetween：任务发奖的幂等依据

```typescript
static async completionsBetween(taskId: number, startTs: number, endTs: number): Promise<number> {
  const pred = new relationalStore.RdbPredicates('t_task_completion');
  pred.equalTo('task_id', taskId).between('completed_at', startTs, endTs);
  const rs = await DBHelper.get().query(pred);
  const n = rs.rowCount;
  rs.close();
  return n;
}
```

**这是「同一任务每周期只发一次」的唯一依据**。判定逻辑在 `TaskService.evaluateAll()` 第 73 行：

```typescript
const done = await TaskRepo.completionsBetween(t.id, start, now);
if (done > 0) {
  continue;  // 本周期已发过，跳过
}
```

**答辩必问**：*"为什么不能直接看行为记录有没有达标？"*
→ 因为达标后用户可能删除记录。如果只看行为记录，删了之后就认为「没完成」，会重复发奖。用独立的完成记录表锁定「已发过」这个事实，与行为记录解耦。

### 3.6 distinctDays：连续天数的数据源

```typescript
static async distinctDays(): Promise<number[]> {
  const list = await BehaviorRepo.all();
  const set = new Set<number>();
  for (const r of list) {
    const d = new Date(r.createdAt);
    d.setHours(0, 0, 0, 0);   // ★ 抹掉时分秒，只留日期
    set.add(d.getTime());
  }
  const arr: number[] = [];
  set.forEach((v: number) => { arr.push(v); });
  arr.sort((a: number, b: number) => b - a);  // 降序，最新在前
  return arr;
}
```

**`setHours(0,0,0,0)` 是关键**。同一天的三条记录时间戳不同，抹掉时分秒后变成同一个值，`Set` 去重后就是「有记录的天数」。返回降序数组，因为连续天数计算从最新往前数。

## 4. service/CalculationService.ets

**解决什么问题**：因子库的唯一访问入口，所有减排量计算都走这里。

### 4.1 因子库加载

```typescript
static async init(context: common.UIAbilityContext): Promise<void> {
  const data: Uint8Array = context.resourceManager.getRawFileContentSync('factors.json');
  const text: string = util.TextDecoder.create('utf-8').decodeToString(data);
  const file = JSON.parse(text) as FactorsFile;
  CalculationService.categories = file.categories;
  CalculationService.meta = file.meta !== undefined ? file.meta : {};
}
```

从 `rawfile` 读 JSON。`rawfile` 是编译期打包进 HAP 的只读资源，不占用户存储、不会被误删。`getRawFileContentSync` 是同步方法，因为只在启动时调一次，不值得为它做异步。

### 4.2 核心计算

```typescript
/** 减排量（克 CO₂e），参数非法返回 0 */
static calculate(type: string, subType: string, value: number): number {
  const sub = CalculationService.findSub(type, subType);
  if (sub === null || !isFinite(value) || value <= 0) {
    return 0;
  }
  return Math.round(value * sub.factor);
}

/** 减排量 -> 积分 */
static valueToPoints(grams: number): number {
  if (grams <= 0) {
    return 0;
  }
  return Math.max(Constants.POINTS_PER_100G, Math.floor(grams / (100 / Constants.POINTS_PER_100G)));
}
```

**`Math.round` 而不是 `Math.floor`**：1080.4 克如果 floor 成 1080，那 0.4 克就被吃掉了。round 更符合直觉，且误差不累积（正负抵消）。

**积分保底 1 分**：`Math.max(1, ...)`。为什么？光盘一餐 50 克，`floor(50/100) = 0`，用户记了行为却得不到积分，会觉得「白记了」。给 1 分保底，维持激励。

**答辩可能问**：*"那不就作弊了？记 100 次 50 克能拿 100 分，而实际只有 5000 克应得 50 分。"*
→ 单次上限拦住了：光盘行动 `max = 3`（三餐），一天最多记 3 次，所以最多多拿 2 分。上限设计就是为这个考虑的。同理每个子类型都有 `max`。

### 4.3 findSub：线性查找够不够快

```typescript
static findSub(type: string, subType: string): SubType | null {
  for (const cat of CalculationService.categories) {
    if (cat.name !== type) { continue; }
    for (const sub of cat.subTypes) {
      if (sub.name === subType) { return sub; }
    }
  }
  return null;
}
```

19 个子类型、4 个大类，最坏情况遍历 19 次。一次录入调一两次，完全可接受。**没有做 Map 缓存**，因为 19 条数据的线性查找比维护缓存的一致性更简单。

## 5. service/PointsService.ets

**解决什么问题**：所有积分变动必须有流水，不允许「凭空加分」。两个方法版本是全文的核心。

### 5.1 双版本设计（关键）

```typescript
/** 事务内使用（调用方需已 beginTx） */
static addPointsTx(source: string, refId: number, action: string, points: number): Promise<void> {
  return (async (): Promise<void> => {
    const balance = await PointsRepo.lastBalance();
    const p: PointsRecord = {
      id: 0,
      source: source,
      refId: refId,
      action: action,
      points: points,
      balanceAfter: balance + points,   // ★ 先读后写
      createdAt: Date.now()
    };
    PointsRepo.insertSync(p);
  })();
}

/** 常规入口：自带事务 */
static async addPoints(source: string, refId: number, action: string, points: number): Promise<void> {
  DBHelper.beginTx();
  try {
    await PointsService.addPointsTx(source, refId, action, points);
    DBHelper.commitTx();
  } catch (e) {
    DBHelper.rollbackTx();
    throw e as Error;
  }
}
```

**为什么要两个版本**：

`addPoints` 内部开了事务。如果外部已经在事务里（比如 `BehaviorService.submit` 的 `beginTx` 之后），再调 `addPoints` 就会**事务嵌套**，鸿蒙 RDB 不支持嵌套事务，会报错或打乱提交时机。

所以拆成两个：
- `addPointsTx`：**不做事务管理**，假定调用方已开事务
- `addPoints`：**自己开事务**，内部调 `addPointsTx`

**`return (async () => {...})()` 这种写法**：让 `addPointsTx` 返回 Promise，同时内部逻辑同步执行到第一个 await。写成 `static async addPointsTx()` 也可以，但显式包一层 async IIFE 更能表达「这是一个包装」。

**答辩必问**：*"`balanceAfter` 是先读后算的，如果并发怎么办？"*
→ 鸿蒙应用单进程单线程 UI 模型，写操作由用户点击串行触发，不存在并发写。若真要多线程，就需要用 `SELECT ... FOR UPDATE` 或数据库级别的原子自增，但本项目场景不需要。

### 5.2 为什么积分流水要存 action 文本

```typescript
action: `骑行 6km，减排1.08kg`
```

存人类可读的描述而非枚举码。好处是**用户能看懂流水**（「为什么给我 10 分」一目了然）。代价是文案改动不影响历史（历史流水保持当时的文案，这是对的）。

## 6. service/BehaviorService.ets ★

**解决什么问题**：三条写链路（提交/修改/删除）的统一编排者。**这是答辩最可能让你逐行讲的类**，152 行，每行都有讲究。

### 6.1 submit：提交链路

```typescript
static async submit(type: string, subType: string, value: number, unit: string,
  factor: number, ts: number, note: string, source: string = 'manual'): Promise<SubmitResult> {
```

**先看参数**：8 个参数，其中 `source` 有默认值 `'manual'`。三个调用方：

| 调用方 | source 传什么 |
|---|---|
| `Record.ets`（手动录入页） | 不传，用默认 `manual` |
| `AiRecognize.ets`（AI 确认后） | `ai_ticket` 或 `ai_scene` |
| `PlatformSourceService`（平台导入） | `platform` |

**三个校验，逐行看**：

```typescript
// 统一防御校验：录入页与 AI 识别链路都经过这里，任何入口都不可绕过上限
const sub = CalculationService.findSub(type, subType);
if (sub === null) {
  throw new Error('未知的行为类型');
}
if (!isFinite(value) || value <= 0) {
  throw new Error('数值必须大于 0');
}
if (value > sub.max) {
  throw new Error(`超出单次上限：最多 ${sub.max} ${sub.unit}`);
}
```

- `findSub` 返回 null → 类型不存在（可能是旧版本的脏数据，或前端传错）
- `!isFinite(value)` → 拦住 `NaN` 和 `Infinity`。`isFinite(NaN)` 是 false，所以这一条同时防住两种
- `value <= 0` → 负数或 0
- `value > sub.max` → 超上限

**为什么校验写在这里而不是页面**：注释写得很清楚——「任何入口都不可绕过」。这是**校验下沉**原则。DF 台账里有一条缺陷就是「AI 识别结果未做上限截断」，根因是校验只写在录入页，AI 那条路绕过去了。

**计算与构造**：

```typescript
const grams: number = Math.round(value * factor);
const record: BehaviorRecord = {
  id: 0,              // 占位，插入后由数据库赋值
  type: type,
  subType: subType,
  value: value,
  unit: unit,
  factor: factor,     // ★ 快照
  reductionG: grams,
  createdAt: ts,
  note: note,
  source: source
};
const points = CalculationService.valueToPoints(grams);
```

**注意 `factor` 是从参数传进来的，不是从 `sub.factor` 取**。为什么？因为 AI 识别或平台导入时，可能带着当时的因子值。保持参数传递，让调用方决定用哪个因子，这个类不擅自替换。

**事务块**：

```typescript
DBHelper.beginTx();
try {
  const id = BehaviorRepo.insertSync(record);
  record.id = id;
  if (points > 0) {
    // 单位与图表、首页保持一致，统一用 kg（内部仍按克存储）
    await PointsService.addPointsTx('behavior', id,
      `${subType} ${value}${unit}，减排${(grams / 1000).toFixed(2)}kg`, points);
  }
  DBHelper.commitTx();
} catch (e) {
  DBHelper.rollbackTx();
  throw e as Error;
}
```

**四行关键**：
1. `insertSync` 返回新 id，立刻赋给 `record.id`——因为积分流水的 `ref_id` 要用它
2. `if (points > 0)` —— 0 分不写流水，避免垃圾数据。什么时候会是 0？`value × factor` 后 `round` 成 0 的场景（比如节水 0.001 升）
3. `addPointsTx` 而不是 `addPoints` —— 已在事务内，不能嵌套
4. `catch` 里 `throw e as Error` —— 不吞异常，让调用方能提示用户

**事务外三步**：

```typescript
// 先评估任务达标，再统一检测徽章（单次调用覆盖行为与任务两类触发，动画名单完整）
await TaskService.evaluateAll();
const newBadges: string[] = await BadgeService.checkAll();
bumpTick();
// 已加入家庭组的话，异步把最新快照推给同步服务
SyncService.scheduleReport();
```

**顺序不能乱**：
- 必须先 `evaluateAll`（可能发任务积分），再 `checkAll` 徽章。因为「任务达人」徽章的判定依赖 `t_task_completion` 记录，任务刚完成才能解锁
- `evaluateAll` 在事务**外**，因为它自己开事务
- `bumpTick()` 通知全局刷新
- `scheduleReport()` 是异步的，不 await。同步失败不影响本地

### 6.2 deleteById：删除链路

```typescript
static async deleteById(id: number): Promise<void> {
  const rec = await BehaviorRepo.getById(id);
  if (rec === null) {
    return;   // 记录不存在，静默返回
  }
  DBHelper.beginTx();
  try {
    await BehaviorRepo.deleteById(id);
    const points = CalculationService.valueToPoints(rec.reductionG);
    if (points > 0) {
      await PointsService.addPointsTx('behavior', id,
        `删除记录：${rec.subType} ${rec.value}${rec.unit}，冲减积分`, -points);
    }
    // 该记录参与的任务若因此不再达标，撤销完成记录并扣回任务积分
    await TaskService.revokeUnmetTasks(rec);
    DBHelper.commitTx();
  } catch (e) {
    DBHelper.rollbackTx();
    throw e as Error;
  }
  bumpTick();
}
```

**关键点**：

1. **先查再删**。要拿到 `rec.reductionG` 才能算该退多少分。所以先 `getById`，再 `deleteById`。
2. **`-points` 负数冲减**。积分流水允许负值，这样「累加所有流水 = 当前余额」这个恒等式成立。
3. **`revokeUnmetTasks` 在事务内**。因为它内部用 `addPointsTx`（也是 tx 版本），且必须在删除记录的同一事务里完成——否则删了记录但任务没退回，就是半成品状态。

**这里有个隐藏的设计**：`CalculationService.valueToPoints(rec.reductionG)` 用记录里的 `reductionG` 反算积分，而不是重新按 `value × factor` 算。因为 `reductionG` 是录入时算好的整数克，反算积分与当时发分完全一致。

**答辩追问**：*"如果当时发的分和现在反算的分不一致怎么办？"*
→ 不可能不一致。`reductionG` 是录入时 `Math.round(value × factor)` 的结果，`valueToPoints` 是纯函数，输入相同输出必相同。这正是「把 reductionG 存下来」的价值。

### 6.3 updateRecord：修改链路（最复杂）

```typescript
static async updateRecord(id: number, newValue: number, newTs: number): Promise<void> {
  const rec = await BehaviorRepo.getById(id);
  if (rec === null) { return; }
  if (!isFinite(newValue) || newValue <= 0) {
    throw new Error('数值必须大于 0');
  }
  const sub = CalculationService.findSub(rec.type, rec.subType);
  if (sub !== null && newValue > sub.max) {
    throw new Error(`超出单次上限：最多 ${sub.max} ${sub.unit}`);
  }
  if (newTs > Date.now()) {
    throw new Error('时间不能晚于当前时刻');
  }
  // 用记录内因子快照重算：因子库后续修订或子类型下架不影响历史记录修订
  const newG = Math.round(newValue * rec.factor);
  const oldPoints = CalculationService.valueToPoints(rec.reductionG);
  const newPoints = CalculationService.valueToPoints(newG);
```

**四道校验**：
1. 记录存在
2. 新数值合法（>0 且有限）
3. 不超上限（子类型可能已下架，所以 `sub !== null` 才检查）
4. **时间不能是未来**。因为未来时间的记录会被计入「今日」统计，污染数据

**用 `rec.factor` 而非 `sub.factor`**：注释说得很明白——「因子库后续修订或子类型下架不影响历史记录修订」。这是因子快照的第二次应用。

**差额计算**：

```typescript
DBHelper.beginTx();
try {
  await BehaviorRepo.updateValue(id, newValue, newG);
  if (newTs > 0 && newTs !== rec.createdAt) {
    await BehaviorRepo.updateTime(id, newTs);
  }
  const diff = newPoints - oldPoints;
  if (diff !== 0) {
    await PointsService.addPointsTx('behavior', id,
      `修改记录：${rec.subType} ${newValue}${rec.unit}，积分${diff > 0 ? '补发' : '扣回'}`, diff);
  }
  await TaskService.revokeUnmetTasks(rec);
  DBHelper.commitTx();
} catch (e) {
  DBHelper.rollbackTx();
  throw e as Error;
}
// 数值调大可能让任务新达标：事务外补发（evaluateAll 自带事务，不可嵌套）
await TaskService.evaluateAll();
bumpTick();
```

**三个精细处理**：

1. **`if (diff !== 0)` 才写流水**。6 公里改成 6.1 公里，如果积分没变（都是 10 分），就不该写一条「补发 0 分」的垃圾流水。
2. **`newTs > 0 && newTs !== rec.createdAt`** 才更新时间。`newTs <= 0` 表示"不修改时间"（调用方约定）；时间没变就不做无谓的 update。
3. **先 revoke 再 evaluateAll**。revoke 处理「改小后不再达标」，evaluate 处理「改大后新达标」。两个方向都覆盖。

**为什么 evaluateAll 在事务外**：因为它自己 `beginTx`。如果在 `beginTx` 里调用，就是事务嵌套。

**答辩必问**：*"为什么修改要用差额，不删了重录？"*
→ 注释给了答案：「避免『删了重录』产生冗余流水」。用户体验上，积分明细里多出「冲减 -10」「发放 +12」两条，看着像系统出错。用差额只有一条「修改记录，补发 2 分」，清晰。

## 7. service/TaskService.ets ★

**解决什么问题**：任务达标判定与回退。核心难点是「回退」。

### 7.1 revokeUnmetTasks：任务回退（最难理解的方法）

```typescript
static async revokeUnmetTasks(rec: BehaviorRecord): Promise<void> {
  const defs: TaskDef[] = await TaskRepo.list();
  const now = Date.now();
  for (const t of defs) {
    if (!t.enabled) { continue; }
    const check = TaskCheckUtil.parse(t.checkJson);
    if (check.subTypes.indexOf(rec.subType) < 0) {
      continue;   // ① 该任务不涉及此子类型，跳过
    }
    if (check.matchType === 'sum' && check.unit !== rec.unit) {
      continue;   // ② 量纲不符（km vs 次），跳过
    }
    const start = TaskService.periodStart(t.period);
    const done = await TaskRepo.completionsBetween(t.id, start, now);
    if (done === 0) {
      continue;   // ③ 本周期压根没完成过，无需回退
    }
    const progress = await TaskService.progressFor(check, start, now);
    if (progress < check.target) {
      await TaskRepo.deleteCompletionsBetween(t.id, start, now);
      await PointsService.addPointsTx('task', t.id,
        `任务回退：${t.title}（删除行为后不再达标）`, -t.points);
    }
  }
}
```

**四道过滤，逐层收窄**：

| 层 | 过滤条件 | 目的 |
|---|---|---|
| ① | `check.subTypes.indexOf(rec.subType) < 0` | 这个任务跟被删的记录无关，不处理 |
| ② | `matchType === 'sum' && unit !== rec.unit` | 「每周回收 5kg」不该被「光盘 1 次」影响 |
| ③ | `done === 0` | 本周期没发过奖，没什么可回退 |
| ④ | `progress < check.target` | 删记录后仍然达标，不该回退 |

**② 为什么只对 `sum` 检查单位**：`count` 类型按笔数算，不涉及量纲。`sum` 类型必须同单位才能累加——「骑行 30 公里」和「光盘 3 次」虽然可能在同一任务里配置了多个子类型，但单位不同不能加。

**这个方法是「删除」和「修改」两个链路的共用逻辑**：
- 删除：删了记录 → 调用 revoke
- 修改：改小了数值 → 调用 revoke（虽然记录还在，但可能不再达标）

**答辩必问**：*"任务已经发过奖了，为什么还能退回去？"*
→ 因为奖是「基于当前数据算出来的」。数据变了，结论就该跟着变。如果不回退，用户就能「先刷满任务拿奖，再删记录」，积分凭空产生。这是 DF 台账里真实修复的缺陷。

### 7.2 evaluateAll：达标发奖

```typescript
static async evaluateAll(): Promise<string[]> {
  const defs: TaskDef[] = await TaskRepo.list();
  const awarded: string[] = [];
  const now = Date.now();
  for (const t of defs) {
    if (!t.enabled) { continue; }
    const start = TaskService.periodStart(t.period);
    const done = await TaskRepo.completionsBetween(t.id, start, now);
    if (done > 0) {
      continue;   // ★ 幂等的核心
    }
    const check = TaskCheckUtil.parse(t.checkJson);
    const progress = await TaskService.progressFor(check, start, now);
    if (progress >= check.target) {
      await TaskRepo.insertCompletion(t.id, now);
      await PointsService.addPoints('task', t.id, `完成任务：${t.title}`, t.points);
      awarded.push(t.title);
    }
  }
  if (awarded.length > 0) {
    bumpTick();
  }
  return awarded;
}
```

**`if (done > 0) continue` 是幂等保证**。每次录入行为都调 `evaluateAll`，如果不判重，一天录 20 条会发 20 次任务奖。

**注意这里用的是 `addPoints`（自带事务）而非 `addPointsTx`**。因为 `evaluateAll` 本身不在任何外部事务里（`BehaviorService` 是在 commit 之后才调它）。

**遍历所有任务而非只检查相关任务**：因为用户可能修改了一条旧记录，导致某个不相关的任务达标状态变化（比如把上周的记录改到本周）。全量检查更稳妥，12 个任务的开销可忽略。

### 7.3 periodStart：周期边界

```typescript
static periodStart(period: string): number {
  const now = Date.now();
  return period === 'weekly' ? DateUtil.startOfWeek(now) : DateUtil.startOfDay(now);
}
```

极简但重要。日任务从今天 0 点算，周任务从本周一 0 点算。所有判定都用这个起点。

**答辩追问**：*"周一算一周开始，那跨年怎么办？"*
→ `DateUtil.startOfWeek` 用 `(getDay() + 6) % 7` 计算偏移，不涉及年份，跨年自动正确。比如 2026-01-01 是周四，`(4+6)%7 = 3`，往前推 3 天到 2025-12-29（周一）。

### 7.4 listProgress：进度展示

```typescript
const done = (await TaskRepo.completionsBetween(t.id, start, now)) > 0;
const check = TaskCheckUtil.parse(t.checkJson);
const progress = done
  ? check.target                                    // 已完成直接显示满进度
  : await TaskService.progressFor(check, start, now);
const tp: TaskProgress = {
  task: t,
  progress: Math.min(progress, check.target),       // ★ 不超上限
  target: check.target,
  done: done
};
```

**`done ? check.target : 实际进度`**：已完成的任务直接显示「5/5」而不是「8/5」。因为用户删了一条记录但任务还没回退的瞬间，实际进度可能是 8。

**`Math.min(progress, check.target)`**：同上，防止进度条溢出。

**排序逻辑**：

```typescript
list.sort((a, b) => {
  const pa = a.task.period === 'daily' ? 0 : 1;
  const pb = b.task.period === 'daily' ? 0 : 1;
  if (pa !== pb) { return pa - pb; }      // 日任务在前
  if (a.done !== b.done) { return a.done ? 1 : -1; }  // 未完成在前
  return a.task.id - b.task.id;           // 按 id 稳定排序
});
```

三级排序：日任务优先 → 未完成优先 → id 升序。**第三级是为了稳定性**，同样的任务列表每次刷新顺序一致，不会跳动。

## 8. service/BadgeService.ets ★

**解决什么问题**：9 枚徽章的解锁检测，以及「连续打卡天数」这个特殊计算。

### 8.1 checkAll：一次查六个聚合值

```typescript
static async checkAll(): Promise<string[]> {
  const badges: BadgeDef[] = await BadgeRepo.list();
  const totalG = await BehaviorRepo.sumAllReduction();
  const recordCount = await BehaviorRepo.countAll();
  const streak = await BadgeService.currentStreak();
  const pointsTotal = await PointsService.totalEarned();
  const tasksDone = await TaskRepo.countCompletions();
  const articlesRead = await PointsService.countSource('read');

  const newly: string[] = [];
  const now = Date.now();
  for (const b of badges) {
    if (b.unlocked) { continue; }     // ★ 已解锁跳过，省一次判定
    let ok = false;
    if (b.conditionType === 'reduction_total') {
      ok = totalG >= b.conditionValue;
    } else if (b.conditionType === 'record_count') {
      ok = recordCount >= b.conditionValue;
    } // ... 其余四类
    if (ok) {
      await BadgeRepo.setUnlocked(b.id, now);
      newly.push(b.name);
    }
  }
  return newly;
}
```

**关键设计：六个聚合值只查一次，而不是每枚徽章查一次**。9 枚徽章如果每枚都查，就是 9 × 6 = 54 次查询。现在只有 6 次。

**`if (b.unlocked) continue`**：已解锁的不再判定。因为徽章一旦解锁不会撤销（即便用户删光记录），这是设计选择——纪念性成就。

**`newly.push(b.name)`**：返回新解锁的徽章名，供页面播放解锁动画。返回名字而非 id，因为 UI 直接用。

### 8.2 currentStreak：连续天数（有坑）

```typescript
static async currentStreak(): Promise<number> {
  const days = await BehaviorRepo.distinctDays();   // 降序，最新在前
  if (days.length === 0) { return 0; }
  const today = DateUtil.startOfDay(Date.now());
  const first = days[0];
  // ★ 第一天必须是今天或昨天，否则连续中断
  if (first !== today && first !== today - DateUtil.DAY_MS) {
    return 0;
  }
  let streak = 1;
  let expected = first;
  for (let i = 1; i < days.length; i++) {
    if (days[i] === expected - DateUtil.DAY_MS) {
      streak++;
      expected = days[i];
    } else {
      break;
    }
  }
  return streak;
}
```

**为什么允许第一天是「昨天」**：如果只允许今天，那用户早上打开 App 还没记录时，连续天数会显示 0，让人误以为断了。允许昨天，用户有一整天的缓冲时间。

**逐日递减检查**：`days[i] === expected - DAY_MS` 严格判断「前一天」。因为 86400000 毫秒是固定值，用减法而非日期运算，避开夏令时等干扰（中国无夏令时，但代码不依赖这个假设）。

**`break` 而非 `continue`**：连续中断就停，不需要检查后面的。因为数组是降序的，一旦出现空缺，后面的都更早，不可能接上。

**答辩追问**：*"如果用户跨时区呢？"*
→ `startOfDay` 用本地时区，跨时区会导致日期边界变化。这是已知限制，单机应用场景下可接受。若要做全球版，需统一用 UTC 或记录时区偏移。

### 8.3 progressList：批量进度

```typescript
/** 批量计算徽章进度（与入参顺序一一对应），聚合值只查一次 */
static async progressList(badges: BadgeDef[]): Promise<BadgeProgressData[]> {
  const totalG = await BehaviorRepo.sumAllReduction();
  // ... 同样六个聚合值
  for (const b of badges) {
    let cur = 0;
    let label = '';
    if (b.conditionType === 'reduction_total') {
      cur = totalG;
      label = DateUtil.gramsToKg(cur) + '/' + DateUtil.gramsToKg(b.conditionValue) + 'kg';
    } else if (b.conditionType === 'record_count') {
      cur = recordCount;
      label = cur + '/' + b.conditionValue + ' 笔';
    }
    // ...
    const pct = b.conditionValue > 0 ? Math.min(100, Math.round(cur / b.conditionValue * 100)) : 0;
  }
}
```

**`label` 按类型定制单位**：减排类显示「3.2/10kg」，记录数显示「4/7 笔」，天数显示「4/7 天」。如果统一显示数字，用户不知道「4/7」是什么意思。

**`Math.min(100, ...)`**：进度百分比封顶 100，防止「15/10kg」显示 150%。

## 9. service/StatsService.ets

**解决什么问题**：所有统计聚合。核心是 `trend()` 的分桶算法。

### 9.1 四档周期的真实含义（答辩要准）

```typescript
export type TrendKind = 'day7' | 'week8' | 'month12' | 'year5';

static kindLabel(kind: TrendKind): string {
  if (kind === 'day7')   { return '近7天'; }
  if (kind === 'week8')  { return '近4周'; }
  if (kind === 'month12'){ return '近6月'; }
  return '近5年';
}

static shortLabel(kind: TrendKind): string {
  if (kind === 'day7')   { return '日'; }
  if (kind === 'week8')  { return '周'; }
  if (kind === 'month12'){ return '月'; }
  return '年';
}
```

**这里有一个必须提前准备的细节**：UI 上按钮写「日/周/月/年」，但实际数据是「近 7 天 / 近 4 周 / 近 6 月 / 近 5 年」。类型名 `week8`/`month12` 是历史遗留（原本想做 8 周 12 月），后来改成 4 周 6 月但常量名没改。

**答辩如果问**：*"周视图是几周？"*
→ 答「近 4 周」，并说明按钮标签是简写。**不要说 8 周**，代码里 `n = 4`。

### 9.2 trend：倒序生成桶再反转

```typescript
// 生成从旧到新的桶
const starts: number[] = [];
let cur = bucketStart(now);
for (let i = 0; i < n; i++) {
  starts.push(cur);
  if (kind === 'month12') {
    const d = new Date(cur);
    d.setDate(0);                          // ★ 上个月最后一天
    cur = DateUtil.startOfMonth(d.getTime());
  } else if (kind === 'year5') {
    const d = new Date(cur);
    d.setFullYear(d.getFullYear() - 1);
    cur = DateUtil.startOfYear(d.getTime());
  } else {
    cur -= stepMs;                         // 日/周直接减毫秒
  }
}
starts.reverse();                          // ★ 变成从旧到新
```

**为什么要先倒序生成再反转**：从「今天」开始往前推更容易写（每次减一个周期）。但图表 x 轴要从旧到新，所以最后 `reverse()`。

**月份为什么不用 `-30 天`**：各月天数不同（28/29/30/31），减 30 天会错位。`d.setDate(0)` 是 JS 的技巧——把日期设成「0 号」等于上个月最后一天，再取月初就精确了。

**年份同理**：`setFullYear(year - 1)` 而非减 365 天，避开闰年。

### 9.3 分桶填充

```typescript
const rangeStart = starts[0];
for (const r of records) {
  if (r.createdAt < rangeStart) { continue; }   // ★ 早于范围的记录直接跳过
  const key = bucketStart(r.createdAt);          // 算这条记录属于哪个桶
  const prev = buckets.get(key);
  if (prev !== undefined) {
    buckets.set(key, prev + r.reductionG);
  }
}
```

**`if (prev !== undefined)` 的作用**：如果算出的 `key` 不在 `buckets` 里（理论上不会，但防御性编程），就忽略这条记录而不是新建桶。保证输出桶数固定为 n 个。

**为什么用 `bucketStart` 而不是比较区间**：`DateUtil.startOfDay/Month/Week` 把任意时间戳归一化到区间起点，直接用 Map 查表，O(1)。比「遍历所有桶做区间判断」快得多。

## 10. utils/PercentUtil.ets ★

**解决什么问题**：保证饼图百分比标签合计恒等于 100%。**这是答辩最有话讲的一个工具类，69 行**。

### 10.1 问题复现

三个类各占 51.1%、39.4%、9.5%：

```
逐项四舍五入：51 + 39 + 10 = 100  ✓ 碰巧对了
换成 51.1% / 39.5% / 9.4%：
            51 + 40 + 9  = 100  ✓ 也对
再换 33.3% / 33.3% / 33.4%：
            33 + 33 + 33 = 99   ✗ 少了 1
```

**根因**：每个数独立取整，误差（-0.3、-0.3、+0.4）相加不为零。

### 10.2 最大余数法（Hamilton 法）

```typescript
static split(values: number[]): PctShare[] {
  const n = values.length;
  let sum = 0;
  for (const v of values) { sum += v; }

  const nums: number[] = [];
  const fracs: number[] = [];
  const smalls: boolean[] = [];
  let assigned = 0;

  for (let i = 0; i < n; i++) {
    const raw = sum > 0 ? values[i] / sum * 100 : 0;
    const small = values[i] > 0 && raw < 1;
    const f = small ? 0 : Math.floor(raw);     // ★ 先全部向下取整
    nums.push(f);
    // small 项的小数部分记为 -1，排序时永远排最后，不会被补 1
    fracs.push(small ? -1 : raw - f);
    smalls.push(small);
    assigned += f;
  }

  const rest = 100 - assigned;                  // ★ 差额（一定是 0~n-1）
  if (rest > 0) {
    const order: number[] = [];
    for (let i = 0; i < n; i++) {
      if (!smalls[i]) { order.push(i); }
    }
    order.sort((a, b) => fracs[b] - fracs[a]);  // ★ 按小数部分降序
    for (let k = 0; k < rest && k < order.length; k++) {
      nums[order[k]] += 1;                      // ★ 差额逐项补 1
    }
  }
  // ...
}
```

**四步走**：

| 步 | 操作 | 为什么 |
|---|---|---|
| 1 | 全部 `Math.floor` 向下取整 | 保证总和 ≤ 100，差额非负 |
| 2 | 算 `rest = 100 - assigned` | 差额一定在 `[0, n-1]` 之间（每项最多损失 <1） |
| 3 | 按小数部分降序排序 | 小数部分越大，说明「被砍掉得越多」，该优先补回 |
| 4 | 前 `rest` 项各补 1 | 补齐到恰好 100 |

**为什么差额一定小于 n**：每项 `floor` 最多损失 <1，n 项最多损失 <n。即使全部损失 0.99，总和损失 < n。

### 10.3 small 项的特殊处理

```typescript
const small = values[i] > 0 && raw < 1;
const f = small ? 0 : Math.floor(raw);
fracs.push(small ? -1 : raw - f);
```

**`small` 判定**：值 > 0 但百分比 < 1%。如果不特殊处理，`floor(0.4) = 0`，用户看到「0%」但明明有数值，会质疑算错。

**`fracs.push(-1)`**：把 small 项的小数部分设成 -1，排序时永远排最后，**绝不会被补 1**。这样它保持 0，UI 层显示「<1%」。

**输出层**：

```typescript
static text(values: number[]): string[] {
  const shares = PercentUtil.split(values);
  const out: string[] = [];
  for (const s of shares) {
    out.push(s.small ? '<1%' : s.num + '%');
  }
  return out;
}
```

`small` 项显示「<1%」而不是「0%」。这是用户体验细节——「<1%」表达「有但很小」，「0%」表达「没有」。

### 10.4 答辩话术

如果被问「这个算法叫什么名字」：
→ **最大余数法（Largest Remainder Method）**，也叫 **Hamilton 法**，是美国宪法规定的众议院席位分配方法，也是很多国家议会选举的席位分配规则。本项目借用来解决百分比取整。

**追问**：*"两只手算一下就够了吧，为什么要专门写个类？"*
→ 因为不止饼图用。分类占比、子类型占比、周报环比都可能用到。而且这是个有数学保证的算法，测试用例能穷举验证。

## 11. utils/DateUtil.ets

**解决什么问题**：所有日期边界计算与格式化。核心是 `startOfWeek`。

### 11.1 startOfWeek：周一为一周开始

```typescript
static startOfWeek(ts: number): number {
  const dayStart = DateUtil.startOfDay(ts);
  const dow = (new Date(dayStart).getDay() + 6) % 7;  // 周一为一周开始
  return dayStart - dow * DateUtil.DAY_MS;
}
```

**`(getDay() + 6) % 7` 是核心技巧**：

| `getDay()` | 含义 | `+6` | `%7` | 结果 |
|---|---|---|---|---|
| 0 | 周日 | 6 | 6 | 往前推 6 天到周一 |
| 1 | 周一 | 7 | 0 | 不推，就是周一 |
| 2 | 周二 | 8 | 1 | 往前推 1 天 |
| 6 | 周六 | 12 | 5 | 往前推 5 天 |

JS 的 `getDay()` 是周日=0，而中国习惯周一为一周开始。这个公式完成转换，且对跨年跨月无依赖。

### 11.2 startOfMonth 的陷阱

```typescript
static startOfMonth(ts: number): number {
  const d = new Date(ts);
  d.setDate(1);           // ★ 先设日期为 1
  d.setHours(0, 0, 0, 0);
  return d.getTime();
}
```

**必须先 `setDate(1)` 再 `setHours`**。如果反过来，遇到 3 月 31 日 `setMonth` 相关操作会因「4 月没有 31 日」跳到 5 月 1 日。这里虽然只调 `setDate`，但顺序保持「先日期后时间」的习惯能避免类似坑。

### 11.3 gramsToKg：统一两位小数

```typescript
static gramsToKg(g: number): string {
  return (g / 1000).toFixed(2);
}
```

全站减排量展示都用这个。`toFixed(2)` 保证「1.08」而不是「1.0800000001」。**只在展示层用，存储永远是整数克**。

## 12. utils/EcoUtil.ets

**解决什么问题**：把「克」换算成人有体感的参照物。这是产品体验的关键设计。

### 12.1 三个换算基准

```typescript
/** 单株乔木年均固碳量（克） */
static readonly TREE_G_PER_YEAR: number = 12000;
/** 私家车每公里排放（克），与因子库出行基线一致 */
static readonly CAR_G_PER_KM: number = 180;
/** 每度电排放（克），与因子库节电因子一致 */
static readonly POWER_G_PER_KWH: number = 785;
```

**三个数字都有来历**：
- 180 g/km 与因子库「骑行」的系数一致——因为骑行的减排量本质就是「少开车的排放」
- 785 g/kWh 与因子库「节电」一致
- 12000 g/年 是乔木年均固碳量的中位取值

**答辩可能问**：*"种树换算准吗？"*
→ 不准。树木固碳量差异极大（树种、树龄、地域），12kg 是常见口径的中位值。明确标注是「参照」而非「等值」。界面上写的是「≈ 种下 0.9 棵树」，带约等号。

### 12.2 dailyText：按量级选择参照物

```typescript
static dailyText(g: number): string {
  if (!isFinite(g) || g <= 0) { return ''; }
  const km = g / EcoUtil.CAR_G_PER_KM;
  if (km >= 0.5) {
    return `≈ 少开 ${EcoUtil.fmt(km)} 公里车`;
  }
  const kwh = g / EcoUtil.POWER_G_PER_KWH;
  if (kwh >= 0.1) {
    return `≈ 省下 ${EcoUtil.fmt(kwh)} 度电`;
  }
  return `≈ 少开 ${EcoUtil.fmt(km)} 公里车`;
}
```

**分流逻辑**：先看公里数，≥0.5 公里就用公里表达。不足半公里改用度电（因为「少开 0.3 公里」念起来别扭）。度电也不足 0.1 度，退回公里（哪怕数字很小，至少单位合适）。

**`return ''`**：无有效减排时返回空串，调用方据此决定不显示这一行，避免「≈ 少开 0.0 公里车」。

### 12.3 fmt：按量级选精度

```typescript
private static fmt(n: number): string {
  if (n >= 100) { return '' + Math.round(n); }      // 100+ 取整
  if (n >= 10)  { return n.toFixed(0); }            // 10-99 取整
  return n.toFixed(1);                              // <10 保留一位
}
```

大数字不需要小数（「少开 156 公里」比「156.3 公里」清爽），小数字需要一位（「少开 0.7 公里」比「少开 1 公里」准确）。

### 14.2 ensure：延迟初始化 + Promise 缓存

```typescript
private static initPromise: Promise<void> | null = null;

static ensure(): Promise<void> {
  if (AppInit.initPromise === null) {
    const ctx = AppInit.getContext();
    AppInit.initPromise = (async (): Promise<void> => {
      await DBHelper.init(ctx);
      await SeedService.seed(ctx);
```

| 2 | `SeedService.seed` | 依赖表已建好 |
| 3 | `CalculationService.init` | 读因子库，独立于数据库，但徽章/任务要算减排量 |

## 15. common/SecureStore.ets

**解决什么问题**：API Key 的安全存储。用系统级加密而非明文 preferences。

### 15.1 优先级：Asset Store Kit → 降级

```typescript
/** 写入失败过一次就不再重试，避免每次读 Key 都卡在不可用的 Asset 上 */
private static unavailable: boolean = false;

static async save(secret: string): Promise<boolean> {
  if (secret === '') {
    await SecureStore.remove();
    return true;
  }
  if (SecureStore.unavailable) {
    return false;   // 已知不可用，直接返回失败让调用方降级
  }
  try {
    const attr: asset.AssetMap = new Map();
    attr.set(asset.Tag.SECRET, SecureStore.toBytes(secret));
    attr.set(asset.Tag.ALIAS, SecureStore.toBytes(SecureStore.ALIAS));
    attr.set(asset.Tag.ACCESSIBILITY, asset.Accessibility.DEVICE_POWERED_ON);
    try {
      await asset.add(attr);
    } catch (e) {
      // 已存在则改为更新
      const q: asset.AssetMap = new Map();
      q.set(asset.Tag.ALIAS, SecureStore.toBytes(SecureStore.ALIAS));
      const upd: asset.AssetMap = new Map();
      upd.set(asset.Tag.SECRET, SecureStore.toBytes(secret));
      await asset.update(q, upd);
    }
    return true;
  } catch (e) {
    SecureStore.unavailable = true;
    return false;
  }
}
```

**三个设计**：

1. **`unavailable` 标志**：第一次失败就记住，后续不再尝试。否则每次读 Key 都要等 Asset 超时，界面卡顿。
2. **`add` 失败改 `update`**：Asset 的 `add` 在别名已存在时会抛错。所以先试 add，失败说明已有记录，改 update。这是 Asset API 的标准用法。
3. **`DEVICE_POWERED_ON` 可访问性**：设备开机即可读，不要求解锁屏幕。因为 App 可能在锁屏时被卡片调用。

**返回值语义**：`true` 表示安全存储成功，`false` 表示降级。调用方（`AppConfig.setAiApiKey`）据此决定是否回退到 preferences 并提示用户「安全性降低」。

**答辩可能问**：*"为什么不全部用 preferences？"*
→ preferences 是明文存储（虽然应用沙箱隔离，但 root 或被备份提取就能读到）。API Key 是付费资源，泄露会造成损失。Asset Store Kit 是系统级加密，密钥不与数据同存。

## 16. network/HttpClient.ets

**解决什么问题**：统一 HTTP 封装，支持按 tag 中止请求。

### 16.1 在途请求登记

```typescript
private static inflight: Map<string, http.HttpRequest> = new Map();

/** 中止指定 tag 的在途请求（未登记的 tag 静默忽略） */
static abort(tag: string): void {
  const req = HttpClient.inflight.get(tag);
  if (req !== undefined) {
    HttpClient.inflight.delete(tag);
    try {
      req.destroy();
    } catch (e) {
      // 已结束的请求 destroy 会抛错，忽略
    }
  }
}
```

**为什么需要这个**：AI 识别要调外部接口，可能耗时 10~20 秒。用户点了「取消」如果只是改 UI 状态，请求还在跑，会浪费流量并可能返回后覆盖新状态。

**实现方式**：请求开始时 `inflight.set(tag, req)`，结束时删除。取消时按 tag 找到 `HttpRequest` 对象，调 `destroy()` 真正中止底层连接。

**`try-catch` 包住 `destroy`**：请求可能刚好在此刻自然结束，此时 `destroy` 会抛错。这是正常的竞态，忽略即可。

### 16.2 finally 里必清理

```typescript
static async postJson(url: string, body: string,
  extraHeaders: Record<string, string>, timeoutMs: number, tag: string = ''): Promise<HttpResponse> {
  const req = http.createHttp();
  if (tag !== '') {
    HttpClient.inflight.set(tag, req);
  }
  try {
    const options: http.HttpRequestOptions = {
      method: http.RequestMethod.POST,
      header: HttpClient.headerOf(extraHeaders),
      extraData: body,
      expectDataType: http.HttpDataType.STRING,
      connectTimeout: timeoutMs,
      readTimeout: timeoutMs
    };
    const resp = await req.request(url, options);
    const code = resp.responseCode;
    const text: string = HttpClient.resultToString(resp.result);
    return { code: code, body: text };
  } finally {
    if (tag !== '') {
      HttpClient.inflight.delete(tag);
    }
    req.destroy();
  }
}
```

**`finally` 里做两件事**：从 `inflight` 移除、销毁请求对象。无论成功失败都执行，防止内存泄漏（`HttpRequest` 不销毁会一直占资源）。

**`connectTimeout` 与 `readTimeout` 分开设置但用同一个值**：连接超时和读取超时是两个阶段。AI 识别场景读取耗时长（模型推理），所以给较大值（代码里是 30 秒）。

## 17. components/Chart.ets ★

**解决什么问题**：776 行手写四个图表组件，零图表库依赖。**这是答辩很好讲的一块**。

### 17.1 为什么不用图表库

**三个理由**：

1. **包体**：主流图表库（如 ECharts、Chart.js）压缩后 200KB~1MB，而本项目全部图表代码 776 行约 30KB。
2. **渲染机制**：图表库普遍基于 DOM 或 WebView，在 ArkUI 上要额外桥接，性能损耗大。原生 Canvas 直接调鸿蒙图形 API。
3. **样式一致性**：自绘能精确复用 `Theme` 里的色板与字号令牌，第三方库要覆盖一堆默认样式。

**答辩如果被问「自己画有什么技术含量」**：
→ 坐标系换算、点击命中检测、选中态管理、空数据态、密度适配（fp 转 px）都要自己处理。776 行里大约 40% 是这类「工程细节」。

### 17.2 fpFont：Canvas 字号与 UI 字号对齐

```typescript
/** Canvas 的 font 单位是物理 px，需乘屏幕密度才能达到 Text fontSize 的 fp 视觉大小 */
export function fpFont(n: number): string {
  const d = display.getDefaultDisplaySync();
  const density = d.densityPixels;    // 例如 3.5
  return Math.round(n * density) + 'px';
}
```

**这是必讲的细节**。ArkUI 里 `Text().fontSize(16)` 的 16 是 **fp**（随系统字号缩放）。但 `Canvas.fillText()` 的 `font` 属性要的是 **px**（物理像素）。

不转换的话，Canvas 上 16px 的字在高密度屏（density 3.5）上，视觉大小只有 `Text` 的 1/3.5，小得看不清。

**答辩追问**：*"为什么不用 vp？"*
→ `CanvasRenderingContext2D.font` 只接受 `px` 单位。这是 API 限制，必须手动乘密度。

### 17.3 首帧延迟绘制（性能关键）

```typescript
build() {
  Canvas(this.ctx)
    .width('100%')
    .height(220)
    // 延迟到进入可视区再首次绘制：首页一次挂多个 Canvas，
    // 同时绘制会抢占首帧，造成撕裂
    .onVisibleAreaChange([0.0, 1.0], (isVisible: boolean) => {
      if (isVisible) {
        this.drawn = true;
        this.draw();
      }
    })
}
```

**问题背景**：首页有 4 个 Canvas（柱状、折线、环形、目标环）。如果都在 `aboutToAppear` 时绘制，首帧要做 4 次完整的 Canvas 绘制，实测超 300ms，用户看到白屏后突然全出现，且滚动时出现横向撕裂。

**解法**：`onVisibleAreaChange` 监听可见性，进入可视区才画。首屏只画第一个，滚动到时再画后面的。

**答辩可能问**：*"`[0.0, 1.0]` 是什么意思？"*
→ 是可见比例的阈值数组。`[0.0, 1.0]` 表示「从完全不可见到完全可见」的整个区间都触发回调。回调参数 `isVisible` 表示当前是否进入该区间。

**另一个细节**：

```typescript
// 每次回到可见区都重绘：后台期间数据可能已变，只画首帧会停在旧画面
.onVisibleAreaChange([0.0, 1.0], (isVisible: boolean) => {
  if (isVisible) {
    this.drawn = true;
    this.draw();      // ★ 每次可见都重绘，不只是首次
  }
})
```

注释说明了原因：App 切到后台再回来，数据可能已变（用户在其他页面删了记录），如果只在首帧画，会一直显示旧数据。每次都重绘保证新鲜。

### 17.4 点击命中检测

```typescript
/** 把点击的 x 坐标换算成柱子下标；点在绘图区外返回 -1 */
private pickIndex(x: number): number {
  const n = this.points.length;
  const w = this.ctx.width;
  if (n === 0 || w <= 0) { return -1; }
  const padL = 12;
  const padR = 12;
  const plotW = w - padL - padR;
  if (x < padL - 6 || x > w - padR + 6) {
    return -1;      // ★ 容差 6px，点在边缘附近不算误触
  }
  const i = Math.floor((x - padL) / (plotW / n));
  return Math.max(0, Math.min(n - 1, i));   // ★ 夹紧到合法范围
}
```

**四步**：

1. 边界检查：数据为空或画布未布局时返回 -1
2. **容差判断**：`padL - 6` 和 `w - padR + 6` 允许在绘图区外 ±6px 内点击也算命中，提升手感
3. 等分计算：`(x - padL) / (plotW / n)` 得到浮点下标，`floor` 取整
4. **夹紧**：`Math.max(0, Math.min(n-1, i))` 防止浮点误差导致越界

**答辩追问**：*"为什么用等分而非柱子的实际边界？"*
→ 柱子之间有间距（`barW = slot × 0.72`），如果按柱子实际边界判断，点在间隙里就没反应，用户会觉得「点不动」。等分让整个 slot 都可点，体验更好。

### 17.5 数据签名：自动清除选中态

```typescript
private draw(): void {

  // 数据变了就清掉选中：新增/删除记录后不应继续标着原来那一天

```

**这是 DF 台账里修复过的缺陷**：用户点击某根柱子选中它，然后去删了一条记录，回到首页发现柱子高度变了但「选中的还是那一天」，视觉上错位。

**`chartSig` 是数据的指纹**（label + value 拼接）。数据变则签名变，签名变就清空 `selIdx`。

**这个设计思路值得讲**：不是「在删除时通知图表清选中」（要改多处代码），而是「图表自己检测数据变化」（自封闭）。这是更健壮的写法。

### 17.6 环形图绘制

```typescript
let start = -Math.PI / 2;        // ★ 从 12 点方向开始
for (const it of this.items) {
  const angle = it.value / total * Math.PI * 2;
  this.ctx.beginPath();
  this.ctx.moveTo(cx, cy);       // 从圆心出发
  this.ctx.arc(cx, cy, r, start, start + angle);
  this.ctx.closePath();          // 回到圆心，形成扇形
  this.ctx.fillStyle = it.color;
  this.ctx.fill();
  // 白色描边形成扇区间留白，更精致
  this.ctx.strokeStyle = '#FFFFFF';
  this.ctx.lineWidth = 3;
  this.ctx.stroke();
  start += angle;
}
// 中心挖空成环
this.ctx.beginPath();
this.ctx.arc(cx, cy, r * 0.64, 0, Math.PI * 2);
this.ctx.fillStyle = '#FFFFFF';
this.ctx.fill();
```

**四个技术点**：

1. **`-Math.PI / 2` 起始角**：Canvas 的 0 度在 3 点方向，减 90 度到 12 点方向。饼图习惯从 12 点开始顺时针画。
2. **`moveTo(cx, cy)` + `closePath()`**：先移到圆心，画弧，再闭合回圆心，形成扇形。
3. **白色描边 3px**：相邻扇形之间的白色缝隙。不用留空隙而是在扇形上描白边，因为描边能适配任意角度。
4. **`r * 0.64` 挖空**：中心画一个白色圆覆盖成环。0.64 是视觉调试出来的比例——太薄看不出环，太厚挤压扇区。

### 18.1 saveAs：先落沙箱，再让用户选位置

```typescript
/**
 * 早期版本直接写应用沙箱（files/backup、files/export），路径虽复制到剪贴板，
 * 但普通用户进不了沙箱，导入时文件选择器里也看不到这些文件——备份等于白做。
 */
private static async saveAs(fileName: string, content: string): Promise<string> {
  const ctx = AppInit.getContext();
  const cacheDir = ctx.cacheDir + '/export_tmp';
  if (!fs.accessSync(cacheDir)) {
    fs.mkdirSync(cacheDir, true);
  }
  const tmpPath = cacheDir + '/' + fileName;
  const f = fs.openSync(tmpPath, fs.OpenMode.READ_WRITE | fs.OpenMode.CREATE | fs.OpenMode.TRUNC);
  fs.writeSync(f.fd, content);
  fs.closeSync(f.fd);

  const options = new picker.DocumentSaveOptions();
  options.newFileNames = [fileName];
  const viewPicker = new picker.DocumentViewPicker(ctx);
  const uris = await viewPicker.save(options);
  if (uris === undefined || uris.length === 0) {
    throw new Error('未选择保存位置');
  }
  // 目标文件由选择器创建，直接整段写入
  const dest = fs.openSync(uris[0], fs.OpenMode.READ_WRITE | fs.OpenMode.TRUNC);
  fs.writeSync(dest.fd, content);
  fs.closeSync(dest.fd);
  return uris[0];
}
```

**这段注释本身就是答辩素材**。它记录了一个真实的认知修正：

| 阶段 | 做法 | 结果 |
|---|---|---|
| 早期 | 写沙箱 `files/backup`，路径复制到剪贴板 | 用户看不到文件，导入时选择器里也没有 → 备份等于不存在 |
| 现在 | 先写沙箱缓存 → 弹系统文件选择器 → 用户选位置 → 再写入 | 文件落在用户可见的「文件管理」里 |

**为什么还要先写沙箱**：因为 `picker.save()` 只返回一个「空的文件 URI」，不返回内容。必须自己把内容写进那个 URI。而写 URI 需要内容已准备好。所以流程是「先备好内容 → 让用户选位置 → 写入」。

**`fs.OpenMode.TRUNC`**：截断模式。如果用户选了已有文件，先清空再写，避免旧内容残留。

### 19.1 三候选地址回退

```typescript
private static readonly EMULATOR_HOST: string = 'http://10.0.2.2:8081';
private static readonly LOOPBACK_HOST: string = 'http://127.0.0.1:8081';

/** 同步服务候选地址：配置 → 模拟器宿主别名 → 本机回环 */
private static candidates(configured: string): string[] {
  const raw: string[] = [configured.trim(), SyncService.EMULATOR_HOST, SyncService.LOOPBACK_HOST];
  const out: string[] = [];
  for (const u of raw) {
    if (u !== '' && out.indexOf(u) < 0) {   // ★ 空值过滤 + 去重
      out.push(u);
    }
  }
  return out;
}
```

**`10.0.2.2` 是什么**：QEMU 虚拟机的特殊地址，固定指向宿主机（你的电脑）。模拟器里 `127.0.0.1` 指向模拟器自己，必须用 `10.0.2.2` 才能访问电脑上的服务。

**三层回退**：用户配置的地址 → 模拟器宿主别名 → 本机回环。按顺序尝试，第一个通的就用。

**为什么要去重**：如果用户配置的正好是 `http://10.0.2.2:8081`，不去重会尝试两次。

### 19.2 设备标识持久化

```typescript
/** 设备唯一标识：首次生成后持久化，用于区分"我"和"别人" */
static async deviceId(): Promise<string> {
  const store = await SyncService.getStore();
  let id = await store.get(SyncService.KEY_DEVICE, '') as string;
  if (id === '') {
    id = 'dev-' + Date.now().toString(36) + '-' + Math.floor(Math.random() * 1000000).toString(36);
    await store.put(SyncService.KEY_DEVICE, id);
    await store.flush();
  }
  return id;

```

**`toString(36)` 是 base36 编码**：把时间戳和随机数转成字母数字混合串，比十进制短。`dev-m5k2p1-a3f9` 这种格式。

**为什么必须持久化**：服务端按 `deviceId` 判断「这是同一个设备的重复上报」还是「新成员加入」。如果每次启动重新生成，服务端会认为每次都有人新加入，成员列表越来越长（幽灵成员）。

**答辩必问**：*"为什么不用设备的硬件 ID？"*
→ 鸿蒙对硬件标识的获取有严格权限限制（隐私合规要求）。应用自己生成并持久化一个 UUID 是标准做法。

### 19.3 立即上报而非防抖（重要设计决策）

```typescript
private static reporting: boolean = false;
private static pendingReport: boolean = false;

/**
 * 录入后触发上报。
 * 注意：不能用 setTimeout 做延迟合并——应用切到后台后定时器会被冻结，
 * 用户"录完就切到另一台设备"时上报会永远发不出去。这里改为立即上报，
 * 用 reporting 标志把并发调用合并成"进行中 + 结束后补一次"。
 */
static scheduleReport(): void {
  if (SyncService.reporting) {
    SyncService.pendingReport = true;
    return;
  }
  SyncService.runReport();
}

private static async runReport(): Promise<void> {
  SyncService.reporting = true;
  try {
    const g = await SyncService.getGroup();
    if (g !== null) {
      await SyncService.reportSnapshot();
    }
  } catch (e) {
    // 静默失败：家庭页仍可手动「立即同步」
  } finally {
    SyncService.reporting = false;
    if (SyncService.pendingReport) {
      SyncService.pendingReport = false;
      SyncService.scheduleReport();   // ★ 递归补发
    }
  }
}
```

**这段注释是答辩的黄金素材**，它记录了一个真实的 bug 与修正：

| 阶段 | 做法 | 问题 |
|---|---|---|
| 早期 | `setTimeout(800ms)` 防抖 | 应用切后台后定时器被系统冻结 | 
| 现象 | 用户「录完马上切到另一台设备」 | 上报永远发不出去，另一台看不到新数据 |
| 现在 | 立即上报 + `reporting` 标志合并并发 | 数据一定发出 |

**「进行中 + 结束后补一次」的模式**：如果上报正在进行中又来新请求，不并发发起（会造成服务端乱序），而是标记 `pendingReport = true`。当前上报结束的 `finally` 里检查该标志，有就再跑一次。

**递归调用 `scheduleReport()` 而非 `runReport()`**：因为在 `finally` 里 `reporting` 已被设为 false，再调 `scheduleReport` 会正常走「非并发」分支。

### 20.1 图片压缩：1600 长边的取舍

```typescript
/**
 * 读取图片并压到长边 1600 的 JPEG，转 Base64。
 * 票据 OCR 需要看清小字，1024 偏低会把里程/度数糊掉；1600 在清晰度与体积间折中。
 */
static async imageToBase64(uri: string): Promise<string> {
  const f = fs.openSync(uri, fs.OpenMode.READ_ONLY);
  let raw: ArrayBuffer;
  try {
    const stat = fs.statSync(f.fd);
    raw = new ArrayBuffer(stat.size);
    fs.readSync(f.fd, raw);
  } finally {
    fs.closeSync(f.fd);      // ★ finally 保证文件句柄释放
  }
  const source: image.ImageSource = image.createImageSource(raw);
  try {
    const info: image.ImageInfo = await source.getImageInfo();
    const longSide = Math.max(info.size.width, info.size.height);
    const scale = longSide > 1600 ? 1600 / longSide : 1;
    const pm: image.PixelMap = await source.createPixelMap({
      desiredSize: {
        width: Math.max(1, Math.round(info.size.width * scale)),
        height: Math.max(1, Math.round(info.size.height * scale))
      }
    });
    try {
      const packer: image.ImagePacker = image.createImagePacker();
      try {
        const jpeg = await packer.packing(pm, { format: 'image/jpeg', quality: 85 });
        return new util.Base64Helper().encodeToStringSync(new Uint8Array(jpeg));
      } finally {
        packer.release();     // ★ 三层 finally 逐层释放
      }
    } finally {
      pm.release();
    }
  } finally {
    source.release();
  }
}
```

**为什么 1600**：注释给了答案。1024 会把票据上的里程数字糊掉，导致 OCR 读错。1600 是清晰度和传输体积的折中（Base64 后约 300KB~500KB）。

**三层嵌套 try-finally**：`ImageSource`、`PixelMap`、`ImagePacker` 三个对象都要 `release()`。任何一个不释放都会造成内存泄漏（图片对象占用 Native 内存，GC 管不到）。**这是鸿蒙图像 API 的标准写法**。

**`quality: 85`**：JPEG 压缩质量。95 以上体积翻倍但肉眼无差异，80 以下文字边缘会糊。

### 20.2 Prompt 设计：把上限一起告诉模型

```typescript
const categories: BehaviorCategory[] = CalculationService.getCategories();
const typeList: string[] = [];
for (const c of categories) {
  for (const s of c.subTypes) {
    // 把单位与单次上限一并告诉模型，省得它返回 500 公里这类离谱数值
    typeList.push(`${c.name}/${s.name}(${s.unit}，上限${s.max})`);
  }
}
const prompt = '你是低碳行为识别助手。先判断图片类型，再输出结构化结果，只输出 JSON，不要解释：' +
  '{"docType":"metro|bus|takeout|electric|water|none","km":数字,"kwh":数字,"waterL":数字,' +
  '"count":数字,"date":"YYYY-MM-DD","evidence":"原文关键字段",' +
  '"candidates":[{"type":"大类","subType":"子类型","conf":0到1}]}。' +
  '规则：1) 行程/乘车记录截图 → docType=metro 或 bus，km 填里程（公里）；' +
  // ... 七条规则
  '8) 完全无关时 candidates 返回空数组。可选行为（含单位与单次上限）：' +

```

**三个设计要点**：

1. **`typeList` 动态拼接**：从因子库实时生成，而不是硬编码在 prompt 里。这样改因子库，prompt 自动跟着变。
2. **把上限告诉模型**：「上限100」写在 prompt 里，模型就不会返回「500 公里」这种离谱值。**这是 prompt 工程里的「约束前置」**。
3. **要求输出 `evidence` 字段**：让模型说出「原文关键字段是什么」，用户能在界面上核对「模型是不是真的读到了」。

**答辩可能问**：*"为什么要求输出 JSON 而不是自然语言？"*
→ 自然语言要写正则提取，脆弱。JSON 直接 `JSON.parse`，且有 schema 约束。代码里还用 `response_format: json_object` 进一步约束。

### 20.5 票据组装：超上限截断 + 依据写入

```typescript
private static ticketOf(p: ParsedAi, dt: string): AiTicket | null {
  let type: string = '';
  let sub: string = '';
  let label: string = '';
  let raw: number = 0;
  if (dt === 'metro') {
    type = '出行'; sub = '地铁'; label = '地铁行程'; raw = Number(p.km);
  } else if (dt === 'bus') {
    type = '出行'; sub = '公交'; label = '公交行程'; raw = Number(p.km);
  } else if (dt === 'electric') {
    type = '节水节电'; sub = '节电'; label = '电费账单'; raw = Number(p.kwh);
  } else if (dt === 'water') {
    type = '节水节电'; sub = '节水'; label = '水费账单'; raw = Number(p.waterL);
  } else {
    // 一份外卖订单按 1 次计（订单里几份菜仍是一顿饭），份数只写进依据
    type = '光盘行动'; sub = '午餐'; label = '外卖订单'; raw = 1;
  }
  const s: SubType | null = CalculationService.findSub(type, sub);
  if (s === null) { return null; }

  // 模型可能把数字写成字符串，统一 Number() 后再判有效
  let v = isFinite(raw) && raw > 0 ? raw : 0;
  const parts: string[] = [];
  if (p.evidence !== undefined && p.evidence !== null && p.evidence !== '') {
    parts.push('' + p.evidence);
  }
  if (p.date !== undefined && p.date !== null && p.date !== '') {
    parts.push('' + p.date);
  }
  if (dt === 'takeout') {
    const n = Number(p.count);
    if (isFinite(n) && n > 1) {
      parts.push('订单 ' + n + ' 份，按 1 次计');
    }
  }
  if (v <= 0) {
    v = 1;
    parts.push('未读到具体数值，按 1 次估算');
  }
  if (v > s.max) {
    v = s.max;
    parts.push('已按单次上限 ' + s.max + s.unit + ' 截断');
  }
  // ...
}
```

**三个精细处理**：

1. **`Number(p.km)` 转换**：模型可能返回字符串 `"12.6"` 而非数字 `12.6`。统一 `Number()` 后再判 `isFinite`。
2. **外卖按 1 次而非份数**：「点了 3 个菜」仍是一顿饭，按 1 次光盘记。份数只写进 `evidence` 让用户看到。
3. **超上限截断并记录依据**：`v > s.max` 时截断，同时在 `evidence` 里追加「已按单次上限截断」。用户能看到「模型读到 500 公里，但系统按 100 公里记」。

**`v <= 0` 时按 1 估算**：模型可能没读到数值。这时按最小单位记 1 次，而不是报错。同时在 `evidence` 里说明「未读到具体数值，按 1 次估算」——**绝不编造具体数字**。

**答辩必问**：*"AI 读错了怎么办？"*
→ 三层防护：① 结果必须用户确认才入库；② `evidence` 字段让用户核对原文依据；③ 任何估算/截断都在依据里写明。**AI 只提供建议，用户做决定**。

## 21. service/RecommendService.ets

**解决什么问题**：基于历史行为的任务推荐。规则引擎，不是机器学习。

### 21.1 打分逻辑

```typescript
static async recommendTasks(): Promise<TaskProgress[]> {
  const all: TaskProgress[] = await TaskService.listProgress();
  const records = await RecommendService.recentRecords(14);    // 近 14 天
  const score = await RecommendService.subTypeScores(records); // 各子类型得分
  const counts = new Map<string, number>();
  for (const r of records) {
    const prev = counts.get(r.subType);
    counts.set(r.subType, (prev !== undefined ? prev : 0) + 1);
  }
  const scored: ScoredTask[] = [];
  for (const p of all) {
    if (p.done) { continue; }        // ★ 已完成的不推荐
    const check = TaskCheckUtil.parse(p.task.checkJson);
    let s = 0;
    for (const st of check.subTypes) {
      s += score.get(st) !== undefined ? score.get(st) as number : 0;
    }
    // 与任务相关子类型中，近 14 天出现最多的作为"主导行为"
    let dominant = check.subTypes.length > 0 ? check.subTypes[0] : '';
    let cnt = counts.get(dominant) !== undefined ? counts.get(dominant) as number : 0;
    for (const st of check.subTypes) {
      const c = counts.get(st) !== undefined ? counts.get(st) as number : 0;
      if (c > cnt) { cnt = c; dominant = st; }
    }
    const item: ScoredTask = { progress: p, score: s, dominant: dominant, count: cnt };
    scored.push(item);
  }
  scored.sort((a: ScoredTask, b: ScoredTask) => b.score - a.score);
  // 取前 3
}
```

**逻辑链条**：

1. 统计近 14 天每个子类型的「得分」（频次 × 减排量，代码在 `subTypeScores`）
2. 每个未完成的任务，把它涉及的子类型得分加起来，作为任务得分
3. 按得分降序取前 3

**为什么「已完成的不推荐」**：已完成的本周期不会再发奖，推荐无意义。

**`dominant` 的用途**：生成推荐理由。比如「你最近骑行了 5 次，完成「每日骑行 5 公里」只差 2 公里」。这个理由比干巴巴的任务名有说服力。

### 21.2 为什么叫「规则引擎」而不是「AI 推荐」

```typescript
/**
 * 智能服务（创新拓展 4）：基于用户历史行为数据做个性化任务推荐与生活建议。
 * 规则引擎：统计近 14 天各子类型的频次与减排量，
 *  - 高频强项 -> 推荐加码挑战（保持习惯）
 *  - 低频弱项 -> 推荐补短任务（引导养成）
 */
```

注释明确说了是「规则引擎」。**答辩时必须诚实**：

> 这不是机器学习模型，是基于统计的规则引擎。数据量（单用户几十条记录）不足以训练模型，硬套「AI 推荐」既不准确也不诚实。规则引擎可解释、可预测，用户能理解「为什么推荐这个任务」。

## 23. entryability/EntryAbility.ets

**解决什么问题**：应用生命周期入口。31 行，但职责划分清晰。

```typescript
export default class EntryAbility extends UIAbility {
  onCreate(want: Want, launchParam: AbilityConstant.LaunchParam): void {
    AppInit.bootstrap(this.context);     // ★ 轻量同步初始化
  }

  onWindowStageCreate(windowStage: window.WindowStage): void {
    windowStage.loadContent('pages/Index', (err) => {
      if (err.code !== 0) {
        console.error('loadContent failed: ' + JSON.stringify(err));
      }
    });
  }
  // onDestroy / onWindowStageDestroy / onForeground / onBackground 为空
}
```

**职责划分**：

| 生命周期 | 做什么 | 不做什么 |
|---|---|---|
| `onCreate` | 存上下文、初始化 AppStorage 默认值 | **不碰数据库**（会拖慢启动，超时会被系统杀） |
| `onWindowStageCreate` | 加载首页 | 不管数据初始化（`Index` 页面自己调 `AppInit.ensure()`） |

**为什么不在这里做数据库初始化**：`onCreate` 有执行时间限制（约 5 秒），超时系统会认为启动失败。数据库建表 + 种子插入在慢设备上可能超时。改成「页面挂载时 ensure」，用户看到加载态但不会启动失败。

**答辩可能问**：*"如果数据库初始化失败，App 能起来吗？"*
→ 能起来，但首页会显示错误提示。因为 `AppInit.ensure()` 是 Promise，页面可以 catch 后展示错误态。这比「启动直接崩溃」用户体验好。
